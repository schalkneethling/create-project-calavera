# Pull request guidance

Read this document when scoping an issue, planning a task, or starting a new implementation.

This guidance is written around the idea of a pull request, as this is a common workflow. However, the essence captured here applies more broadly to how work is done, with the overall goal of improving the quality of the project as a whole.

- Every pull request needs an associated issue, and each issue needs testable acceptance criteria. Acceptance criteria do not have to be exhaustive, but they need to make it clear what is and is not expected. The exception is a trivial change, such as a typo fix or minor maintenance, that has no effect on behavior. When in doubt, propose creating an issue.
- Prefer vertical slices unless the associated issue is specifically scoped differently.
- Before writing logic that formats, parses, lints, or lays out code or content, check whether the project's existing toolchain, such as Vite+ or Oxc, can already do it, or explain why none does.
- Use GitHub's stacked pull requests when working on a change set a reviewer cannot reasonably review in a single sitting. Refer to the official GitHub documentation on using `gh stack` if you are unsure about this feature.
- If splitting would leave a PR broken, misleading, or impossible to validate, keep the necessary pieces together and explain that constraint in the PR.
- When a test is written first, run it once against the code before the change and confirm that it fails on its assertion, not on a missing import, a missing export, or a type error. In the PR, give an overview of what the new and changed tests cover, rather than each failure message.
- Where the project has Stryker configured, run it with `--mutate` limited to the files the change touched, and report the mutants that survived. For each survivor, add a test that kills it or explain in the PR why it does not matter. A passing suite or a coverage number shows that the code ran, but only a killed mutant shows that a test notices when the code changes. If the project has relevant tests but no Stryker configuration, tell the user and offer to add it through Project Calavera.
- Before requesting adversarial review, search the repository for the old name, value, or behavior that the change replaces. Check docs, plans, comments, test descriptions, and READMEs, and update every place that still describes the old state as current. Do not change records of past states, such as changelog entries, release notes, or decision records. The review should not be where these are found. Delegate this search to a smaller model, such as Haiku or Luna, if one is available.
- Before requesting adversarial review, run the full test, lint, type check, and build suites for the whole repository, not only for the changed files or the project the change touched. Every check must pass, except failures that also occur on the base branch. A scoped run helps to diagnose a failure, but it is not evidence that the change is ready. If a suite cannot run in your environment, for example because it needs credentials, mark it as not run in the PR and say why. Run the full suites again after addressing review findings and before opening the pull request.
- To show that a failure existed before the change, run the same suite on the base branch and confirm that it fails there too. Never ignore such a failure. List each one in the PR description, then either fix it in a separate commit or open an issue and link it.
- Before opening a pull request, ask a local subagent for an adversarial review of the code. Ensure the subagent has the needed context to enable an effective review. Context should include the issue, the acceptance criteria, and the diff to review.
- Unless the issue calls for a different focus, the review covers regressions, accessibility, security, missing tests, and scope creep, omitting any that clearly do not apply.
- Review findings are considered by the agent coordinating the work, and valid findings are delegated back to the agent that implemented the change to address.
- Review findings deemed invalid must be reported in the PR description along with the reasoning for why they were marked as such.
- Start the PR description by answering what this pull request does and which issue or issues it fixes using the "Fixes #xxx" syntax. Make it specific enough to focus the review on the proposed solution or decision. Then explain what changed, why it changed, and how you validated it. Include relevant commands, results, and any limitations. Prefer concise, useful evidence over a prescribed reporting format.
- Steps that people follow outside the repository, such as settings in GitHub, Apple, Homebrew, or 1Password, must be checked against the vendor's current documentation, with the link in the PR. Mark any step that the agent could not run itself as not run.
- When a tool hangs, or fails without a clear message, find the cause before building a workaround. If the cause is in the tool, search its issue tracker for an existing report and link it from the PR. If there is none, tell the user about the problem and offer to draft an issue with steps to reproduce, using the tool's own issue template. Do not file it upstream without the owner's approval.
- Create follow-up issues for deferred work that might otherwise be forgotten.
- When feedback on a pull request has been addressed, ensure that threads are resolved unless there are open questions.
