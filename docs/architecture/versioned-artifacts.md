# Versioned artifact contracts

Calavera skills, hooks, and agents are independently versioned npm packages. A package contains one artifact payload plus a `calavera-artifact.json` manifest conforming to [`schemas/calavera-artifact.schema.json`](../../schemas/calavera-artifact.schema.json).

## Package identity

First-party packages use these names:

- `@schalkneethling/calavera-skill-<name>`
- `@schalkneethling/calavera-hook-<name>`
- `@schalkneethling/calavera-agent-<name>`

Artifact IDs retain their existing `skill-`, `hook-`, or `agent-` prefix. IDs are stable recipe and catalog identifiers; npm package names are distribution identifiers. The catalog maps IDs and legacy `src/ai` paths to package names.

## Dependency isolation

The artifact catalog contains only identity, routing, target, and compatibility metadata. Neither `create-project-calavera` nor `@schalkneethling/calavera-artifact-core` declares independently versioned artifact packages as runtime dependencies. They therefore do not appear transitively in a consumer's `package.json`, dependency lockfile, or `node_modules` through a Calavera CLI installation.

Artifact packages enter the project only through the explicit artifact lifecycle and are extracted into `.calavera`. Install and update may resolve from npm; ordinary apply only reuses or restores an exact locked version offline.

Each manifest declares:

- schema version and stable artifact ID;
- artifact type and display name;
- package-relative payload path;
- supported target names when target adaptation is meaningful;
- the compatible `create-project-calavera` semver range.

The manifest never names an installed project destination. Destination selection belongs to the recipe and target adapter.

## npm registry configuration

Artifact resolution and extraction use the registry and proxy that the package manager that started Calavera would use for the artifact's package scope. Calavera reads them itself because pacote does not read `.npmrc` files. Calavera reads, expands, and sends no registry credential (ADR-0021).

- **What is read.** `registry`, the `@scope:registry` of the artifact scope, `proxy`, `https-proxy`, and `noproxy`. Every other key is dropped as each file or variable is read, before its value is looked at, so Calavera never reads, expands, returns, or names a `//host/:_authToken`, `_auth`, `username`, `_password`, `certfile`, or `keyfile` key, and gives no warning about one. A registry for any other scope is not read, so a broken one cannot stop an unrelated install. A blank registry for the artifact scope is skipped with a warning.
- **Where it is read from.** The user `.npmrc`, then the project `.npmrc`, then `npm_config_*` environment variables; later sources win. The user `.npmrc` is `~/.npmrc` or the file named by `npm_config_userconfig`, which may use `~` and `${VAR}`. A `userconfig` key in a project `.npmrc` is ignored. npm passes such a key on as `npm_config_userconfig`, which Calavera cannot tell apart from one you set, so it still chooses the user `.npmrc` for the registry and the proxy, as before #1064. Calavera expands no variable in that file, though, unless it is your own `~/.npmrc` (see "Variables"). This is accepted (owner decision on #1186). Such a file keeps user trust, so a repository that ships it can give Calavera a proxy and a plain-`http` registry, which its project `.npmrc` alone cannot; it cannot expand a variable or reach a credential. npm honors only the exact key `userconfig`, but exports every spelling of it in lowercase, so a project key such as `USERCONFIG` replaces your own `npm_config_userconfig` although npm read your file. When a project `.npmrc` sets `userconfig` in any other spelling, or with a variable in the key, Calavera cannot find the file npm read, so the user `.npmrc` it reads follows the project rules. The project `.npmrc` is the one in the current directory, and parent directories are not searched, except when npm starts Calavera (`npx`, `npm exec`, `npm run`). npm then reads the project `.npmrc` at its local prefix, which is the nearest folder above the current directory with a `package.json` or `node_modules`, or the workspace root when that folder is a workspace member (`loadLocalPrefix` in @npmcli/config). npm exports that folder as `npm_config_local_prefix`, and Calavera reads the project `.npmrc` there, so the values npm passes on from it keep the project rules. Before #1064, Calavera read the current directory instead, so a `registry` that npm passed on from a workspace root `.npmrc` was trusted as environment. Built-in npm configuration files and command-line flags are not read. The global npm configuration file is read only when npm starts Calavera, because npm then exports its values (see "Variables").
- **Variables.** A registry value is never expanded. A `registry` or `@scope:registry` value that contains a variable reference, such as `${VAR}` in an `.npmrc` file or a `npm_config_*` variable, `${NAME}` in a `.yarnrc.yml`, or a leading `$` in a `bunfig.toml`, stops the command with an error that names the setting and its file, never the value. Calavera does not fall back to another file or to `registry.npmjs.org`, because that would bypass a registry you configured. A variable in a registry URL is in practice a way to inject a secret, such as a path token; write the registry URL literally instead. `${VAR}` is still expanded in proxy values of `npm_config_*` variables and of your own `~/.npmrc`: the `.npmrc` in your operating system account's home folder, which Calavera takes from `os.userInfo()`, not from `HOME` (#1186). A user `.npmrc` anywhere else, named by `npm_config_userconfig` or by a changed `HOME`, can be chosen by repository content, such as a project `.npmrc` `userconfig` key or a Yarn 4 `.env.yarn`, so its proxy entries that contain `${...}` are ignored with a warning that names the key, never a value. Otherwise a proxy such as `https-proxy=http://${CI_SECRET}.example.com/` in a file that a repository chose would send an environment secret to a host that the repository chose. It is never expanded in a project `.npmrc`, which is repository content and must not read the caller's environment: a project proxy entry that contains `${...}` is ignored with a warning that names the key, never a value. A proxy entry that references an unset variable is ignored. When npm starts Calavera (`npx`, `npm exec`, `npm run`), npm exports its resolved settings as `npm_config_*` variables, with `.npmrc` values already expanded. Calavera recognizes this by the `npm_command`, `npm_lifecycle_event`, or `npm_config_local_prefix` variable. It then compares each such variable with the project, user, and global files, expanding the file's value only for the comparison: a value equal to the project file's value, under the same key or another spelling of it that npm exports under the same variable, such as `https_proxy`, is project content, not environment. A value equal to the user file's value is the user's, and so was applied, ignored, or stopped by the user layer; under another spelling, such as `https_proxy`, npm does not use it, so Calavera does not either. npm also expands `${VAR}` in keys, so a key such as `https-proxy${UNSET?}` exports as `npm_config_https_proxy`; the comparison expands the file's keys the same way, so such a key in the project `.npmrc` follows the project rules, and a registry key such as `registry${UNSET?}` stops the command when its value holds a variable and must use `https`. So npm's expanded copy of a registry that holds a variable counts as the file's value, and the command stops. npm also reads a global configuration file, which it exports as `npm_config_globalconfig`: the file a `globalconfig` setting names, or `etc/npmrc` in the prefix. A project `.npmrc` can choose that file with `globalconfig=./g.npmrc`, or with `prefix=./pfx`, which npm reports as an error but still applies (`loadGlobalConfig` in @npmcli/config). Calavera reads the same file as the lowest layer and compares the exported variables with it too. When a project `.npmrc` sets `globalconfig` or `prefix`, or a user `.npmrc` that the project `.npmrc` chose with `userconfig` does (unless it is your own `~/.npmrc`), or the file is inside the project after symbolic links are resolved, the file follows the project rules: its proxy is ignored, its registry must use `https`, and a variable in its values is not expanded. Otherwise it is your npm installation's global file and is trusted like a user file, but a variable in its values is still not expanded: a proxy entry with `${...}` in it is ignored with a warning that says how to keep the proxy: write it without a variable, or remove the entry and set the proxy in your own `~/.npmrc` or an environment variable. npm expands a file's keys and values with the environment it had when it loaded the file, before it exports its settings and `INIT_CWD`, so Calavera cannot always reproduce that expansion. In a file whose variables Calavera does not expand, such as a project `.npmrc`, each `${...}` in a key may therefore stand for any text, so `https-proxy${INIT_CWD?}` counts as `https-proxy`, and the file counts as the source of an exported value whenever its entry for that key contains `${...}`, whatever the value. Such an entry follows that file's rules. npm exports a list entry such as `https-proxy[]=…` as its items joined with blank lines, without expanding them, and Calavera compares lists the same way; npm does expand the items of a `noproxy` list. A value that matches none of these files came from somewhere Calavera does not read, such as the caller's environment, which npm passes on unchanged, or an npm command-line flag, so it is trusted as environment. One exception: when an npm started by another npm runs Calavera, as `npm exec -c "cd sub && npm exec …"` does, the outer project's exported values reach the inner npm as environment, and Calavera, which reads only the inner project's files, trusts them; running that command already runs the outer repository's scripts, and `${VAR}` in it is expanded. This errs toward ignoring: while a file entry for a key holds a variable, an `npm_config_*` variable that the caller sets for the same key is ignored too, so remove the entry to use the variable. Registry failures name the ignored keys and unset variables, because an MCP client often passes a minimal environment.
- **Registry URLs.** A `registry` or `@scope:registry` value must be an `http` or `https` URL, in the user `.npmrc`, the project `.npmrc`, and the environment alike. A username and password in the URL are removed, under npm, Yarn 2 or later, and Bun alike, with a warning that names the setting and its file, never the value, and says that Calavera sends no credentials; minipass-fetch would otherwise send them as basic authentication. A project `.npmrc` must use `https`: a tarball's integrity comes from the same package document as the tarball, so on an `http` registry anyone on the network path can replace both together, and the artifact still passes verification. To use an `http` registry, set it in your user configuration, such as your user `.npmrc`. Calavera cannot tell a token written literally into a registry URL's path or query from an ordinary path segment, so such a token travels with the URL; Calavera does not support registries that need one.
- **Downloads.** pacote moves a tarball URL on `registry.npmjs.org` onto its `registry` option before it downloads it (`replaceRegistryHost`), keeping the tarball's path and dropping any path of the registry URL. Calavera passes the artifact scope's registry as that option: the `@scope:registry` value when one applies, and the default registry otherwise, which is the registry the package document came from. The lookup and the download therefore use the same registry. A tarball URL on any other host is downloaded as the package document names it.
- **Authentication failures.** A registry or tarball host that answers 401 or 403 stops the command with an error that names the origin (protocol, host, and port) that answered, says that Calavera sends no credentials, and names the setting and file that chose the registry. It never prints the URL path, the query, or the registry's own text. The error keeps its `code` (`E401`, `E403`, `EOTP`, or `EAUTHIP`) and `statusCode`, and its cause, which holds only the method, code, status, and origin, is printed only with `CALAVERA_DEBUG`. `artifacts status --check-updates` and `artifacts doctor --check-updates` report the same facts for each artifact, with the failing origin in the `origin` field of the `--json` failure object. A private registry or mirror that requires authentication for Calavera's packages does not work with Calavera. When only the default `registry` requires authentication, add `@schalkneethling:registry=https://registry.npmjs.org/` to your user `.npmrc`, which sends only Calavera's artifact scope, for both the lookup and the download, to the public registry.
- **What is shown.** The dry run of `apply`, `artifacts install`, and `artifacts update` reports the registry that artifacts resolve from, with its protocol, host, and port (`https://registry.npmjs.org`), and says when it comes from the project `.npmrc`. The `dry_run_apply` MCP tool returns the same fields (`artifactRegistries` and `artifactWarnings`).
- **Proxies.** `proxy`, `https-proxy`, and `noproxy` pass to npm-registry-fetch as `proxy`, `httpsProxy`, and `noProxy`, which uses `https-proxy` when it is set and `proxy` otherwise, and skips both for the hosts in `noproxy`. A proxy URL must use `http`, `https`, or a `socks` protocol; any other value is ignored with a warning that names the key, never the value, because a proxy URL can carry credentials. Proxy authentication, such as a username and password in a proxy URL, is out of scope of ADR-0021 and still applies. A `noproxy` list (`noproxy[]=host`) is joined with commas, as npm joins it, and so is the list that npm exports as `npm_config_noproxy`, whose entries it separates with blank lines (`envVal` in @npmcli/config `set-envs.js`).
  - **Project files.** Calavera reads proxy URLs (`proxy` and `https-proxy`, or Yarn's `httpProxy` and `httpsProxy`) only from user configuration files and the environment, and ignores them in a project `.npmrc` or `.yarnrc.yml` with a warning. This follows the owner decision on #1064: a proxy that a cloned repository chooses would see which packages Calavera fetches, and for an `http` registry it could change the package documents and tarballs together. An ignored project proxy never replaces a proxy from a user file. A `noproxy` or an empty proxy value in a project file still applies, because it only removes the proxy. This includes a proxy that npm passes on as `npm_config_https_proxy` or `npm_config_proxy` from the project `.npmrc` it read, also when the file spells the key differently, such as `https_proxy`, because npm exports it under the same variable.
  - **Warnings and fallbacks.** The warning names the proxy setting or environment variable that requests use instead, says when the registry host is excluded from proxies, or suggests setting it in the user configuration. Under Yarn, it also says when the ignored proxy is for the other protocol, which Yarn would not use for the registry. When no proxy is configured, the `HTTPS_PROXY` and `HTTP_PROXY` variables of the Calavera process apply through @npmcli/agent, and `NO_PROXY` excludes hosts when no `noproxy` setting applies, because a `noproxy` setting replaces it.
- **Yarn 2 or later and Bun.** Calavera recognizes the package manager from `npm_config_user_agent`, which Yarn and Bun set for the binaries they run. Repository content cannot change which package manager's settings Calavera reads (#1186): npm exports a project `.npmrc` `user-agent`, and pnpm its `userAgent` setting, as `npm_config_user_agent`, but both also set `npm_execpath` to their own binary (`npm-cli.js`, or `pnpm` with no extension or with `.exe`, `.cjs`, `.mjs`, or `.js`), which no project setting changes. When `npm_execpath` names npm or pnpm, Calavera reads the npm settings, whatever the user agent says. Yarn 4 and Bun set both variables themselves, and Yarn 4 sets them after it applies a `.env.yarn` file, so a repository cannot change them under Yarn 4 or Bun either. Yarn 1 counts as npm, as before #1064; #1175 removes Yarn 1 support.
  - Under Yarn 2 or later, the registry and proxy come from `.yarnrc.yml` files only, and no `.npmrc` file or `npm_config_*` variable is read: `npmRegistryServer`, `npmScopes.<scope>.npmRegistryServer` (the scope without its `@`), `httpsProxy` for an `https` registry, and `httpProxy` for an `http` registry. Calavera reads `~/.yarnrc.yml` and every `.yarnrc.yml` from the file system root down to the current directory, where the nearest file wins, and then the `YARN_NPM_REGISTRY_SERVER`, `YARN_HTTP_PROXY`, and `YARN_HTTPS_PROXY` variables, which win over every file. `YARN_RC_FILENAME` renames the searched files, but not `~/.yarnrc.yml`. Without a registry setting, the registry is Yarn's default, `https://registry.yarnpkg.com`. `${NAME}`, `${NAME:-fallback}`, and `${NAME-fallback}` are expanded in proxy values of the variables and of `~/.yarnrc.yml` only, and only when that file is in your operating system account's home folder: a Yarn 4 `.env.yarn` can set `HOME` for the binaries Yarn runs, so a `~/.yarnrc.yml` in any other `HOME` is still read, but its proxy entries that contain `${...}` are ignored with a warning. Every other `.yarnrc.yml` can be repository content, so its proxy entries that contain `${...}` are ignored with a warning too. A repository's `.env.yarn` file can also set the `YARN_NPM_REGISTRY_SERVER`, `YARN_HTTP_PROXY`, `YARN_HTTPS_PROXY`, `HTTPS_PROXY`, and `HTTP_PROXY` variables, with any variables in their values already expanded by Yarn. This is accepted (owner decision on #1186): it is a repository choosing its registry or proxy, as a project `.npmrc` can already choose its registry. Yarn expands `${VAR}` in `.env.yarn` from the caller's environment, so such a value can carry an environment value, such as a token, to the registry or proxy that the repository chose. Yarn's own requests in that repository send it the same way. Calavera cannot tell these variables apart from variables that you set, so they follow the rules for environment variables, and the `https` rule for project files does not apply to them. Calavera reads no other key, such as `npmAuthToken` or `npmAuthIdent`.
  - Under Bun, the registry comes from the `.npmrc` files, then `[install] registry` and `[install.scopes]` (with or without the `@`) in the global `bunfig.toml` and then the project `bunfig.toml` in the current directory, then the registry variables; later sources win. Like Bun 1.3.9 (`PackageManagerOptions.zig`), Calavera reads `BUN_CONFIG_REGISTRY`, then `NPM_CONFIG_REGISTRY`, then `npm_config_registry`, skips any value that does not start with `https://` or `http://`, and uses the first one that does. The global file is `$XDG_CONFIG_HOME/.bunfig.toml` when that variable is an absolute path, and `~/.bunfig.toml` otherwise. The user `.npmrc` is `$XDG_CONFIG_HOME/.npmrc` when it exists and no `userconfig` is set. A registry table is read for its `url` only; `token`, `username`, and `password` are not read. Bun reads a registry URL that starts with `$`, such as `$MY_REGISTRY`, from the variable it names; Calavera stops with an error on such a value instead, as on any registry variable. The `.npmrc` proxy keys are not read under Bun, because Bun does not support them. When Bun itself runs Calavera, as `bunx --bun` or `bun calavera.js` do, Bun first loads the project's `.env` file into the environment and expands `${VAR}` in it, so a registry or proxy variable that file sets, such as `BUN_CONFIG_REGISTRY` or `npm_config_https_proxy`, applies as environment, like a Yarn 4 `.env.yarn`.
  - A project `.yarnrc.yml` or `bunfig.toml` must use an `https` registry, like a project `.npmrc`. A file that cannot be read or parsed is skipped with a warning that names its path and, for a parse error, the line and column, never its content.
- **Not read.** `cafile`, `ca`, and `strict-ssl` from an `.npmrc` are not loaded. `NODE_EXTRA_CA_CERTS` does apply.
- **Secrets.** Calavera reads no registry credential, so none can appear in logs, warnings, or error messages. The loader still parses whole `.npmrc` files, because the registry and proxy keys live in them, so a token's text passes through memory while the file is parsed, but no code path keeps, expands, logs, or sends it. Proxy credentials are the stated exception.

A project `.npmrc` can choose the registry that artifacts resolve from. Extraction verifies each tarball against the integrity that registry reported for the resolution. Re-checking that integrity against the lock when an artifact is restored is not part of this behavior.

Calavera fetches an artifact tarball only from an `https` URL, or from an `http` URL on `localhost`, `127.0.0.1`, or `::1`, which the release rehearsal's registry and the tests use (owner decision on #1194). pacote chooses how to fetch from the text of the spec (`FetcherBase.get` in `pacote/lib/fetcher.js`, through npm-package-arg): a `git+ssh:`, `git+https:`, or `git:` URL, an scp-style `git@host:path`, or an `https` URL on a git host such as `https://github.com/owner/repo` runs git with the person's SSH agent and credential helpers, and a `file:` URL or a path reads this machine. `extractArtifactPackage` therefore checks the package document's `dist.tarball`, and also the URL pacote requests after it moves a `registry.npmjs.org` tarball onto the artifact scope's registry, which it passes to pacote as `registry`, before it calls pacote. It also passes `allowGit: "none"`, so pacote refuses an `https` URL that npm-package-arg reads as a git repository. A refusal stops with the error code `EBADTARBALLURL` and a reason that tells the refused forms apart, such as a protocol, a URL that does not start with its protocol, or an scp-style git address. The message names the package and quotes the URL's protocol only when the protocol has at most 16 characters, and never the rest of the URL. A registry on another host that serves its tarballs over plain `http` therefore cannot install artifacts. The check covers the URL that Calavera hands to pacote, not a redirect: make-fetch-happen follows a redirect from that URL, including one to plain `http`, and the integrity check still applies to what it downloads. pacote's fetch stack cannot reach an `http://[::1]` URL (`getaddrinfo ENOTFOUND [::1]`), so a tarball on `::1` passes the check but fails to download; use `127.0.0.1` or `localhost` instead.

## Project records

The three project records deliberately answer different questions:

| File                            | Question answered                                          | Update authority                            |
| ------------------------------- | ---------------------------------------------------------- | ------------------------------------------- |
| `calavera.config.json`          | Which artifacts and targets does the project want?         | User, Composer, or approved CLI composition |
| `.calavera/artifacts.lock.json` | Which exact packages and payloads were resolved?           | Artifact install or update command          |
| `.calavera/state.json`          | Which files were installed, and have they changed locally? | Existing managed-file application flow      |

The lockfile conforms to [`schemas/artifacts-lock.schema.json`](../../schemas/artifacts-lock.schema.json). It is deterministic and checked in. It records exact versions, registry resolution and integrity, the selected npm tag, manifest schema version, install destination, and payload hash. It contains no generated timestamp.

The state file remains the authority for installed hashes and overwrite protection. A lockfile payload hash verifies resolved package content; it does not prove that the installed copy is still unedited.

## Compatibility and updates

- Ordinary `apply` and top-level `update` install exact locked versions.
- Only the explicit artifact update workflow advances versions.
- `latest` is the default channel; `next` requires explicit selection.
- Resolution rejects a manifest whose Calavera compatibility range excludes the running CLI. The range is a lower bound only: it names the first CLI that can install the artifact, and the hosted Composer uses the same range to withhold an artifact until that CLI is published. It carries no upper bound, because a CLI major does not change the manifest contract; a change to that contract bumps `schemaVersion`. `packages/artifact-core/test/compatibility.test.mjs` fails when any range is invalid or excludes the workspace CLI version. `packages/cli/scripts/release-integration.test.mjs`, run by `release:fixture`, packs every workspace artifact and installs it through the real `artifacts install` path and `extractArtifactPackage` with the workspace CLI version, one artifact per fixture and all artifacts together.
- Integrity, identity, manifest, and payload checks complete before any project files or lock entries change.
- Lock and state writes are atomic. A failed multi-artifact operation leaves the previous project records intact.
- Existing local-edit protection applies to every package-backed installation.

Legacy `{ "type", "src", "target" }` recipe entries remain readable for one major-version compatibility window. Migration uses the catalog mapping to produce stable `{ "id", "target" }` entries before resolving an exact lock.

Issue #160 remains historical input for vendor-neutral naming and content decisions. Package extraction must not reintroduce vendor-specific names that the completed consolidation removed.
