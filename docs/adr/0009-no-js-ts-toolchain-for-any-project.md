# ADR-0009: Calavera Provides No JavaScript or TypeScript Toolchain to Any Project

- **Status:** Proposed (2026-09-27)
- **Date:** 2026-09-27
- **Issue:** https://github.com/schalkneethling/create-project-calavera/issues/528
- **Decides:** CQ1 (`docs/evolution-brief.md` Section 4), non-`vp` projects. Records, with the audit evidence, that Calavera offers no JavaScript or TypeScript toolchain integration to any project, `vp`-managed or not, and that a project which has not adopted Vite+ runs `vp create` or `vp migrate` first.

## Context

The evolution brief's CQ1 asked what Calavera offers a project that has not adopted Vite+, after delegation: the Minimal profile plus the kept integrations and a recommendation to run `vp create` or `vp migrate`, or a reduced Classic path (`docs/evolution-brief.md` Section 4). Decision C9 assigned the answer to the audit rather than to a default: the Classic profile's components are candidates for removal under C1, the audit classifies each, and CQ1 covers what, if anything, remains for a project without `vp` (`docs/evolution-brief.md` Section 3).

`docs/cross-repo/sequencing-map.md` Section 0 already resolved the question in prose, ahead of this ADR: "CQ1 is resolved by this increment: Calavera provides no JS or TS toolchain to any project; a project that has not adopted Vite+ runs `vp create` or `vp migrate` first." The evolution brief's CQ1 entry records the same outcome and, for the record, the original question and the brief's own default proposal (the Minimal-plus-recommendation path, on the reasoning that maintaining two toolchain worlds is the failure mode C1 exists to prevent). Checkpoint 0 names an accepted CQ1 ADR as an acceptance criterion (`docs/evolution-brief.md` Section 6, Phase 0), and no ADR file existed to satisfy it before this one. This ADR is that record: it does not decide CQ1 afresh, it writes down the decision already implemented by the removal stack and states the evidence and the rejected alternatives.

## Evidence

`docs/catalog-audit.md` classifies every JavaScript and TypeScript toolchain row in the reduced Increment 1 scope as `remove`, not `delegate`. The audit's own classification rules explain why: a `delegate` row is one where "the CQ1 ADR decides what happens in non-`vp` projects" (`docs/catalog-audit.md` Section 1), and every one of these rows carries the note "Delegate versus remove, stated once and referenced by the other JS and TS toolchain rows: Section 1 defines `delegate` as a row whose non-`vp` fate the CQ1 ADR decides, and CQ1 is resolved the other way; Calavera provides no JS or TS toolchain to any project, and a project without Vite+ runs `vp create` or `vp migrate` first. No non-`vp` path remains to delegate into, so every JS or TS toolchain row that Vite+ covers is `remove`" (`docs/catalog-audit.md`, Modern profile: Oxlint row). The same "Non-`vp` treatment (per CQ1)" column reads, for every one of these rows, "Not offered; run `vp create` or `vp migrate` first (CQ1 resolved in Increment 1)." The rows so classified: Modern profile: Oxlint, Modern profile: Oxfmt, Modern profile: TypeScript config, Classic profile: ESLint flat config, Classic profile: Prettier, Classic profile: TypeScript config, React best practices: Oxlint and ESLint React and JSX-A11y packs, Imports and modules, Promise safety, Node package rules, and Test rules (`docs/catalog-audit.md` Section 3). The audit's summary counts eleven `remove` rows against zero `delegate` rows in scope (`docs/catalog-audit.md` Section 4). The two rows Vite+ does not cover, the Modern and Classic Stylelint rows, are classified `watch` rather than `remove` or `delegate` because they are CSS tooling, not a JavaScript or TypeScript toolchain, and their non-`vp` treatment is recorded as unchanged: "Same as a `vp` project; CQ1 directs a project without Vite+ to run `vp create` or `vp migrate` first, after which the CSS lane applies" (`docs/catalog-audit.md`, Stylelint rows). React Doctor is likewise kept, on the audit's own reasoning, because it is "not a JS or TS toolchain component in the C2 sense" (`docs/catalog-audit.md`, React Doctor row), and its non-`vp` treatment is the same run-`vp`-first recommendation.

Five accepted or proposed removal ADRs carried that classification into the catalog. ADR-0002 removes the `oxlint` catalog entry and its fourteen plugin pack entries. ADR-0003 removes the `oxfmt` catalog entry. ADR-0004 removes the `typescript` catalog entry (the `tsconfig.json` template and the `typecheck` script), covering both the Modern and Classic rows as one entry. ADR-0005 removes the `eslint` catalog entry and the eleven entries that include it (`typescript-eslint`, `eslint-config-prettier`, `eslint-react`, `eslint-jsx-a11y`, `eslint-import`, `eslint-n`, `eslint-promise`, `eslint-unicorn`, `eslint-sonarjs`, `eslint-vitest`, `eslint-jest`), scoped explicitly to the JavaScript and TypeScript ESLint host and excluding `@eslint/css`. ADR-0006 removes the `prettier` catalog entry and its three plugin entries (`prettier-tailwind`, `prettier-svelte`, `prettier-astro`). Each of these five ADRs states, in its own Decision section, that no compatibility flag, deprecated path, or legacy profile survives the removal, and that a recipe naming the removed id is rejected the same way any unknown id is rejected. None of the five carries a non-`vp` fallback: ADR-0003 through ADR-0006 each observe that the removal narrows or closes the gap between the Modern and Classic profiles and explicitly leave the question of profile collapse to CAL-011, without reopening a non-`vp` exception. Between them, the five ADRs remove every catalog entry the audit classified `remove`, so the catalog holds no JavaScript or TypeScript toolchain entry for either a `vp`-managed or a non-`vp` project.

ADR-0001 establishes what `vp create` and `vp migrate` supply, evidence CQ1 depends on to say a project can simply adopt Vite+ rather than receive a Calavera-scaffolded alternative. Its probe against vite-plus 0.3.1 found that a fresh `vp create vite:library` and `vp create vite:monorepo` project, and a `vp migrate` of a plain `create-vite` project, all carry a `vite-plus` dependency, a `vite.config.ts` importing `defineConfig` from `"vite-plus"`, and a `vite` pin to `npm:@voidzero-dev/vite-plus-core@<version>` (ADR-0001, Evidence). Its own referenced evidence from the audit records that `vp check` type-checks through tsgolint and failed a seeded `TS2322` with exit 1, that `vp lint` reports a clean run with no `oxlint.json` present, and that `vp fmt --check` exits 0 (`docs/catalog-audit.md`, TypeScript config and Oxlint and Oxfmt rows, citing `docs/guide/check.md:7-9`, `docs/guide/lint.md:19`, and `docs/guide/fmt.md:7`). `vp migrate` performs the equivalent onboarding for a project that predates Vite+: `migrate-rules.md:32-34` lists ESLint migration among the `--full` setup actions and `migrate-rules.md:280-286` rewrites `eslint`, `prettier`, and other scripts to their `vp` equivalents (`docs/catalog-audit.md`, ESLint flat config and Prettier rows). ADR-0001 also defines the detection this ADR relies on for the consequence below: `inspect_project` gains a `vitePlus` field whose `status` is `"managed"`, `"unmanaged"`, or `"unknown"`, and reports the verdict through finding kinds `vite-plus-managed`, `vite-plus-unmanaged`, `vite-plus-signal-conflict`, and `vite-plus-detection-unknown` (ADR-0001, "What `inspect_project` reports").

## Decision

Calavera scaffolds no JavaScript or TypeScript linter, formatter, TypeScript configuration, or test runner for any project, whether or not that project has adopted Vite+. There is no non-`vp` path that receives Oxlint, Oxfmt, TypeScript configuration, ESLint, Prettier, or any of their plugin packs; the catalog holds none of them, for either profile, per ADR-0002 through ADR-0006. A project that has not adopted Vite+ and wants a JavaScript or TypeScript toolchain runs `vp create` (a new project) or `vp migrate` (an existing one) first; Calavera's own documentation and guidance point there rather than scaffolding a substitute.

This settles the CQ1 question as the second of the brief's two named outcomes: not "the Minimal profile plus the kept integrations and a recommendation," which would still describe Calavera as offering something in the JavaScript or TypeScript toolchain space to a non-`vp` project, but strictly "provides no JS or TS toolchain to any project" (`docs/cross-repo/sequencing-map.md` Section 0). What a non-`vp` project retains from Calavera after this decision is exactly what the audit classified `keep` or `watch` for reasons independent of the JavaScript or TypeScript toolchain: React Doctor (a code-pattern report, not a lint plugin, per the audit's React Doctor row), the CSS lane (Stylelint, kept as `watch` metadata under C3 until Oxlint's CSS language plugin ships, per the audit's Stylelint rows and handoff H8), and the integrations, artifacts, and MCP surfaces C3 names outside this audit's JavaScript and TypeScript scope: the Baseline engine, the apply pipeline and its safety properties, the artifact lifecycle, the MCP server, release verification, EditorConfig, HTML validation, Knip, Varlock, and GitHub governance (`docs/evolution-brief.md` Section 3, C3).

This ADR does not itself change code. The catalog already holds no JavaScript or TypeScript toolchain entry, in scope or out, per the audit and the five removal ADRs; this document is the record Checkpoint 0 requires, not a new removal.

## Consequences

A project that has not adopted Vite+ runs `vp create` or `vp migrate` before any Calavera JavaScript or TypeScript quality gate applies to it; Calavera does not stand in as a substitute toolchain in the interim. `inspect_project`'s `vitePlus.status` reports `"unmanaged"` for such a project (or `"unknown"` when the inspected directory has no readable manifest of its own), and the finding kind `vite-plus-unmanaged` (severity `info`) surfaces that status so a coding agent or a human reading `dry_run_apply` or `explain_recipe` output can state plainly that the project has not adopted Vite+, rather than inferring it from an absent lint script (ADR-0001, "What `inspect_project` reports"). `vite-plus-detection-unknown` (severity `warning`) covers the case where detection could not even determine that much.

CAL-011, not this ADR, decides how `compose_recipe`, `explain_recipe`, and `dry_run_apply` act on that status: whether the Modern and Classic profiles collapse into a single `vp`-aware default now that neither carries a JavaScript or TypeScript toolchain component of its own (a consequence each of ADR-0003 through ADR-0006 already flagged and left open), and what recipe an `"unmanaged"` or `"unknown"` project is offered. This ADR fixes only that no recipe, for any status, contains a JavaScript or TypeScript toolchain integration.

Because no compatibility path survives the five removal ADRs, there is no migration burden this ADR adds: a project on an older Calavera recipe that named `oxlint`, `oxfmt`, `typescript`, `eslint`, or `prettier` (or a dependent pack id) already fails recipe validation as an unknown id, independent of whether the project has adopted Vite+ (ADR-0002 through ADR-0006, Decision sections).

## Alternatives considered

**The reduced Classic path.** The brief's own default proposal for CQ1 was the Minimal profile plus the kept integrations and a recommendation to run `vp create` or `vp migrate`, described as the alternative to a reduced Classic path and preferred "because maintaining two toolchain worlds is the failure mode C1 exists to prevent" (`docs/evolution-brief.md` Section 4, CQ1). A reduced Classic path, keeping some slice of ESLint, Prettier, or TypeScript configuration for projects that decline Vite+, was rejected for the same reason stated there: it would leave Calavera maintaining a second, parallel JavaScript and TypeScript toolchain indefinitely, the exact duplication C1 exists to end, and it would give a project two competing sources of truth for lint and format behavior depending on whether it later adopts `vp`. The audit's classification rule reinforces this: a row cannot be `keep` "if the only reason is that Calavera's implementation is nicer than Vite+'s" (`docs/catalog-audit.md` Section 1), and a reduced Classic path has no other justification once `vp create` and `vp migrate` are shown, per ADR-0001, to produce the equivalent toolchain for both new and existing projects.

**The brief's own default proposal (Minimal plus kept integrations plus a recommendation).** This is the first of the brief's two named CQ1 outcomes and was superseded, not adopted: `docs/cross-repo/sequencing-map.md` Section 0 and the brief's own CQ1 entry both resolve CQ1 the other way, to "provides no JS or TS toolchain to any project" rather than to the Minimal-plus-recommendation shape. The practical difference is narrow, since both outcomes recommend `vp create` or `vp migrate` and neither scaffolds a JavaScript or TypeScript toolchain; the decision the sequencing map records is that Calavera does not even offer the Minimal profile as a JavaScript- or TypeScript-toolchain-flavored artifact distinct from what a non-`vp` project already has by not adopting Vite+. This ADR follows the sequencing map's resolution over the brief's own earlier default because the sequencing map is the later, more specific record of what Increment 1 actually decided and implemented.

## Open questions

Whether the Modern and Classic profiles collapse into a single profile, and what that profile is named, is CAL-011's decision, not this one; ADR-0003, ADR-0004, ADR-0005, and ADR-0006 each raised it and left it to CAL-011, and this ADR does the same.

What `dry_run_apply` should say, in its approval-boundary output, when it runs against an `"unmanaged"` or `"unknown"` project, beyond the `vite-plus-unmanaged` and `vite-plus-detection-unknown` findings ADR-0001 already defines, for example whether it actively recommends `vp create` or `vp migrate` in that output rather than leaving the recommendation to documentation alone, is CAL-011's decision.

The three-way choice ADR-0001 defers for a directory with no manifest of its own (create a manifest and apply there, apply at the ancestor directory, or abandon) is tracked as its own follow-up issue in ADR-0001 and is not reopened here.

Whether and how `doctor` warns when an existing recipe on disk still names a removed JavaScript or TypeScript toolchain entry is the follow-up ADR-0001 names ("doctor warns when a recipe carries JS or TS toolchain integrations in a vp-managed project," issue #431) and is out of scope here.
