# ADR-0020: One Project Phase, Derived from the Project's Files, for Every Doctor

- **Status:** Proposed
- **Date:** 2026-11-21
- **Issue:** https://github.com/schalkneethling/create-project-calavera/issues/1112
- **Decides:** how `doctor`, `artifacts doctor`, and `artifacts status` agree on where a project is in Calavera's lifecycle, so that none of them fails or warns about something that is expected at that point. One function derives the project's phase from the recipe, `.calavera/state.json`, `.calavera/artifacts.lock.json`, the marker that `eject` leaves in `.gitignore`, and the files those records name, and every one of the three commands reads it. Calavera stores no phase (owner decision of 2026-11-21 on #1112 and #994). The phases are `pending-transaction`, `unmanaged`, `ejected`, `bootstrapped`, `composed`, `applied`, `drifted`, and `incomplete`. The same function also classifies each artifact and each managed file and gives the reason, so the two doctors never disagree about an artifact or about the phase. `doctor` reads the lock and fails at the levels #994 set for artifacts. Each command's `--json` result gains a `phase` string, and each item gains a computed `condition` with its reason, which is never persisted. A lock entry the recipe no longer selects, whose files were deleted, becomes a warning (#1111). ADR-0017, Amendment 5, in the same pull request, defines the marker. The owner answered the open questions of the first draft on 2026-11-21 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7069063918), settled the choices the update had to make and corrected the label of decision 3 on 2026-11-22 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7078607351), and ruled on gaps from two independent reviews the same day (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079002369, https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079383325). This ADR records each answer in the decision it belongs to and in "Owner decisions". This document changes no code.

## Context

The owner asked on 2026-11-21, in the review of PR #1103 (#994), for a project lifecycle state, so that the doctors do not fail or report on things that are expected in the project's current phase. The example in #1112 is the time between `init`, which writes the recipe, and `apply`, which installs it. In that phase a selected artifact is not installed yet, and that is normal. `doctor` warns about it, `artifacts status` names it, and before the owner's decision on #994 `artifacts doctor` was about to fail on it.

The owner decided on the same day to derive the phase from the project's files in one shared function, not to store a phase that can go stale, and to decide the design in an ADR first. Two related decisions are already recorded on #994: a selected artifact that is not installed yet passes `artifacts doctor` with a note and exits 0, while missing or edited installed artifacts still fail; and a lock entry the recipe no longer selects, whose files were deleted, becomes a warning rather than a failure (#1111). This ADR builds on both and does not reopen them.

#1112's acceptance criteria ask for one function that derives the phase, used by all three commands, tests for each phase transition including the in-between state after `init`, and that the two doctor commands never give opposite answers about the same project. Its scope excludes "changing what each command checks, beyond reading the shared phase"; owner decisions 4, 5, 10, 13, 14, 15, 16, 17, 19, and 20 extend `doctor`'s checks where this ADR says so. The sequencing map places this ADR in wave 7 of the `cli-experience` release and its implementation in wave 8, with #1111 following it (`docs/cross-repo/sequencing-map.md`, Section 0).

## What exists today

This section describes how each command and each record defines a project's state today, from the code, and then where the commands disagree. The commands run in the project folder, and `--config` names the recipe, which defaults to `calavera.config.json` (`CONFIG_FILE`, `packages/cli/src/project-local-commands.js:8`).

### The records

**The recipe** (`calavera.config.json`) is the person's declaration of what the project should have: a profile, integrations, scripts, and the AI artifacts in its `ai` list. `init` writes it, the Composer saves it, and `apply` writes it when it records an answer. The recipe schema requires `profile` (`apps/composer/public/calavera.config.schema.json`, `required`), and `apply` refuses a recipe without one. Calavera keeps no record of the recipe's text (ADR-0017, "What Calavera writes into a project today").

**The state** (`.calavera/state.json`) records what Calavera wrote: `profile`, `integrations`, `files`, `managedFiles` with a hash for each, `aiArtifacts` with a hash for each, `aiWiring`, `gitignoreBlocks`, and `qualityScript` (`packages/cli/src/state.js:24-34`). Several commands write it. The bootstrap (`--init`) writes it with the base skill's record (`agentBootstrap`, `packages/cli/src/index.js:4661`, written at `:4785`). `apply`, `clean`, `artifacts install`, and `artifacts update` rewrite it, and so do `artifacts status --check-updates` and `artifacts doctor --check-updates`, which record the artifact cache block (`artifact-lifecycle.js:620-632`). The state file's existence therefore does not show that `apply` ran.

Its `profile` does. `stateShowsEarlierApply` returns true when `profile` is set, because no other command sets it and `apply` records it on every run (`state.js:36-49`, written at `index.js:4107` from `recipe.profile`, `index.js:3795`). `apply` already relies on this signal to decide whether the project's scripts are Calavera's to compare (`index.js:3071`, `index.js:3593`). After `apply`, the state also keeps the record of an artifact the recipe no longer selects, so that `clean` can remove its unedited output (#829, `index.js:4092-4099`).

**The lock** (`.calavera/artifacts.lock.json`) records each installed artifact package: its ID, version, channel (`tag`), destination, and hashes (`readLock`, `packages/cli/src/artifact-lifecycle.js:1208`). `apply`, `artifacts install`, and `artifacts update` write it. The bootstrap does not, so the base skill it installs has a state record and no lock entry. Only `artifacts install` and `artifacts update` drop the lock entry of an artifact the recipe no longer selects, and they leave its files in place (#992; `keptEntries: []` at `artifact-lifecycle.js:1001`, reported at `:1013-1015`). `apply` keeps every existing entry (`keptEntries: lock.artifacts`, `artifact-lifecycle.js:360`), and `clean` rewrites only the state and never touches the lock. A person who deselects an artifact and runs `clean` therefore ends with its files and state record removed and its lock entry kept, which is the case #1111 is about.

**Managed files that were edited.** `apply` and `update` refuse to overwrite a managed file whose contents differ from both the planned contents and the hash its state record holds, unless the two are equal JSON or the person passes `--reown-managed-file` for it (`assertSafeManagedFileWrite`, `index.js:2531-2564`). That flag does not keep the edit: it lets the check pass, and `writeManagedFile` then overwrites the file with Calavera's planned contents (`index.js:2652-2673`). The dry run reports the same case as a `managed-file-conflict` error whose message ends "review, remove, or migrate it before applying this recipe" (`inspectManagedFilePlan`, `index.js:2795-2833`). Both checks compare against the planned contents after the project's formatter formats them (`formatManagedFilePlans`, `index.js:2758-2765`, called at `:3642-3645`), and `apply` stops before it writes anything when that formatter cannot load (#838, `index.js:3646-3648`). An edit that matches what `apply` would write does not stop it.

**`eject`** removes the recipe, the state, the lock, and the rest of Calavera's footprint, and keeps the installed tooling and the recipe-selected artifacts other than the base skill (ADR-0017, Decisions 2 and 3). It deletes the recipe with the other footprint files, then the package folders and the lock, and the state last (ADR-0017, Decision 7). Before ADR-0017, Amendment 5, nothing in the project recorded afterward that Calavera managed it. `eject --yes` removes only items that match Calavera's records exactly (ADR-0017, Decision 5). It leaves the recipe, whose text Calavera does not record, and each package folder it cannot check, and it keeps the lock while a package folder stays (`selectEjectItems`, `packages/cli/src/eject.js:1662-1683`). It can still delete the state. A run of `eject --yes` on an applied project can therefore leave a recipe and a lock with no state file.

### `doctor`

`doctor` (`index.js:6045-6165`) builds a list of issues, each with the level `"error"` or `"warning"`, and its result is `{ command: "doctor", ok, issues }`, where `ok` is false only when an issue is an error (`index.js:6162`). The run exits 1 when `ok` is false (#1030, `index.js:7259-7268`). It reads the recipe and, for wiring only, the state. It never reads the lock, and it never recovers a pending artifact transaction.

- **No recipe:** an error, "Missing calavera.config.json. Run create-project-calavera init first." (`index.js:6051-6056`). The only other check that runs without a recipe is the warning for a missing `package.json` (`index.js:6058-6064`).
- **Checks of the recipe itself:** warnings for removed JavaScript and TypeScript toolchain integrations (#431), and errors when a root-only integration or an artifact that writes Git hooks is selected outside the repository root (#997, #1031, `index.js:6085-6104`).
- **A managed file the recipe declares that does not exist:** a warning, "Missing managed file" (`index.js:6106-6118`). The list comes from the recipe (`declaredManagedFiles`), not from the state, so `doctor` cannot tell a file that `apply` has not written yet from one that `apply` wrote and someone deleted. It does not compare hashes, so an edited managed file is not reported. A missing Varlock schema is a separate warning.
- **An output path of a selected AI artifact that does not exist:** a warning, "Missing managed AI skill" (`index.js:6139-6147`). Again the recipe is the source, so a selection that was never installed and an installed artifact whose files were deleted read the same. An edited artifact is not reported, and a lock entry the recipe no longer selects is not looked at.
- **The wiring that `apply` recorded** (ADR-0015, Decision 5): warnings for a missing or edited hook block or Claude Code group, and an error for a hook block whose script does not exist (`artifactWiringFindings`, `packages/cli/src/ai/artifact-wiring.js:571-680`, the error at `:621-625`).

### `artifacts status` and `artifacts doctor`

Both commands first recover a pending artifact transaction, which writes files, and then run the same function, `artifactStatus` (`runArtifactCommand`, `artifact-lifecycle.js:201-210`; `:604-772`). It reads the recipe if it exists, the lock, and the state, and it builds one entry per lock entry and one per selection without a lock entry (`artifact-lifecycle.js:642-736`). Each lock entry gets `installed` (every output path exists), `managed` (every output path has a state record), and `locallyEdited` (an output's hash differs from its state record) (`:644-677`), and `selected`, which is null when there is no recipe (`:694`). A selection without a lock entry gets `version: null` and an install command (`:698-734`).

`isArtifactHealthy` decides whether an entry is a problem: a selection without a lock entry is healthy, and a lock entry is healthy only when it is installed, managed, and unedited (`artifact-status-report.js:153-155`). The result's `ok` is true when every entry is healthy (`artifact-lifecycle.js:765`). `artifacts doctor` exits 1 when `ok` is false, and `artifacts status` always exits 0 (`index.js:7290-7301`). `artifacts doctor` prints a warning that names the selections not installed yet and a verdict line (`artifactDoctorVerdict`, `artifact-status-report.js:293-331`).

The health rule does not look at `selected`. A lock entry the recipe no longer selects, whose files were deleted, is therefore a failure, which is what #1111 changes. The rule also does not distinguish "no recipe" from "a recipe that selects nothing": with no recipe and no lock, the report is "The recipe selects no artifacts, and the artifact lock holds none." and `ok` is true (`artifact-status-report.js:170-173`).

### Where the commands disagree

Each row is a probe run on 2026-11-21 against `main` at `0012c34`, in a folder created for it that holds a `package.json`. The applied project is hand-built: a recipe from `init --yes --profile minimal --ai-artifact skill-code-review`, a state with a `profile`, records for `.editorconfig` and `skill-code-review`, and a lock entry for `skill-code-review` and one for `skill-project-goal`, which the recipe does not select. The `eject --yes` row comes from the review of the first draft, which ran a real `artifacts install`, `apply --yes --no-install`, and `eject --yes`.

| Project                                                               | `doctor`                                                                    | `artifacts doctor`                                                           |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| No recipe, state, or lock (never managed, or after `eject`)           | Error "Missing calavera.config.json", exit 1                                | "The recipe selects no artifacts, and the artifact lock holds none.", exit 0 |
| Bootstrapped with `--init`, no recipe yet                             | The same error, exit 1                                                      | The same report, exit 0                                                      |
| After `init`, before `apply`                                          | Two warnings, "Missing managed file" and "Missing managed AI skill", exit 0 | Warning "Selected artifact not installed yet", exit 0                        |
| Applied, selected artifact's files deleted                            | Warning "Missing managed AI skill", exit 0                                  | `skill-code-review ... files missing`, exit 1                                |
| Applied, selected artifact's files edited                             | Nothing about the artifact, exit 0                                          | `skill-code-review ... locally edited`, exit 1                               |
| Applied, a lock entry the recipe no longer selects, its files deleted | Nothing about the entry                                                     | `skill-project-goal ... files missing, not managed by Calavera`, exit 1      |
| Applied, then `eject --yes`: recipe and lock kept, state deleted      | Nothing about the artifact, exit 0                                          | The kept artifact "not managed by Calavera", exit 1                          |
| A state file with an invalid `aiArtifacts` entry                      | "Calavera state contains invalid aiArtifacts entries.", exit 1              | The same, exit 1                                                             |

Every row except the third and the last is an opposite exit status for the same project, which #1112's last acceptance criterion rules out. The third row is the in-between state the owner named: the two commands agree on the exit status, but `doctor` words an expected step as two problems. The sixth row is #1111. The base skill that the bootstrap installs has a state record and no lock entry, so neither command reports on it unless the recipe selects `skill-calavera`.

## Decision

### 1. One function derives the phase and classifies each item

One function, in its own module of `packages/cli/src`, derives the phase. It takes the recipe path (`--config`) and the project folder. It checks for a pending artifact transaction first, so `pending-transaction` wins over every other finding, including an unreadable record. It then reads the recipe, computes the repository root the way `doctor` does today for root-only integrations and Git hooks (#925, `index.js:6074-6082`), and then reads the state, the lock, the `.gitignore` marker (Decision 2), and the files the records name. It returns:

- the project's `phase` (Decision 2);
- the `condition` of each artifact and each managed file, each with its reason (Decision 3);
- the wiring findings that `artifactWiringFindings` returns today.

`doctor`, `artifacts doctor`, and `artifacts status` each call this function and render its result. None of them derives a phase or an item's condition on its own, so a rule changes in one place. `isArtifactHealthy` becomes a reading of an artifact's condition (Decision 4) rather than a separate rule. The function computes every phase, condition, and reason on each run and persists none of them (owner decisions 7 and 8).

The function itself writes nothing. Two writes stay outside it. `artifacts status` recovers a pending artifact transaction before it calls the function, as it does today, and reports the recovered phase. `artifacts doctor` stops recovering: like `doctor`, it reports the phase `pending-transaction` instead (owner decision 20). The cache block that `--check-updates` records before it resolves packages (#960) stays unchanged in both artifact commands.

#1052 adds the read-only MCP tool for artifact status that ADR-0018, Decision 3 allows, as an adapter over the same core function as `artifacts status`. It returns the same `phase` and `condition` fields. It differs from `artifacts status` in one rule, so #1052's acceptance criterion, that the tool returns the same data as `artifacts status --json`, holds except during a pending transaction: it writes nothing, so it never recovers a pending artifact transaction. While one is pending, it reports `pending-transaction` with the remedy to run `artifacts status`, as both doctors do (owner decision 20).

### 2. The phases and how each is derived

The phase answers "where is this project in Calavera's lifecycle?" It depends on which records exist and, after an apply, on whether the recorded items of the current selection still match the files. The function checks the records in this order and stops at the first phase that fits:

```text
artifact transaction journal exists? ── yes ................................ pending-transaction
└─ no: recipe file exists?
   ├─ no ─┬─ no state file and no lock entries ┬─ eject marker in .gitignore . ejected
   │      │                                    └─ no marker .................. unmanaged
   │      ├─ state without profile, no lock entries,
   │      │  and the base skill it records is present ........................ bootstrapped
   │      └─ otherwise ......................................................... incomplete
   └─ yes ┬─ no state file ┬─ lock entries, or a file Calavera would manage
          │                │  already on disk .................................. incomplete
          │                └─ nothing on disk .................................. composed
          ├─ state without profile ............................................. composed
          └─ state has profile ┬─ an item drifted .............................. drifted
                               └─ otherwise .................................... applied
```

| Phase                 | Derived from                                                                                                                                                                                                                                 | What it means                                                                                                                                                                                                                                                            |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `pending-transaction` | `.calavera/artifact-transaction.json` exists, whatever else the project holds.                                                                                                                                                               | An artifact operation stopped and its rollback has not run, so the lock may describe files that are not there. `artifacts status` recovers it (owner decision 20).                                                                                                       |
| `unmanaged`           | No recipe, no state file, no lock entries, and no `eject` marker.                                                                                                                                                                            | Calavera never managed this project.                                                                                                                                                                                                                                     |
| `ejected`             | No recipe, no state file, no lock entries, and the `eject` marker in `.gitignore` (ADR-0017, Amendment 5).                                                                                                                                   | `eject` finished removing Calavera's footprint, and the project keeps the tooling Calavera installed (owner decision 1).                                                                                                                                                 |
| `bootstrapped`        | No recipe, a state file without `profile`, no lock entries, and the state records the base skill, whose folder exists.                                                                                                                       | `--init` ran and wrote the guidance and the base skill; no recipe is composed yet. `init` is the expected next step.                                                                                                                                                     |
| `composed`            | A recipe, and either a state without `profile`, or no state file, no lock entries, and no file Calavera would manage on disk.                                                                                                                | The recipe is written and `apply` has not run. Artifacts installed with `artifacts install` before `apply` are allowed, because that command writes their state records.                                                                                                 |
| `applied`             | A recipe, a state with `profile`, and every recorded item of a selection matches its files.                                                                                                                                                  | `apply` ran and nothing it recorded for the current selection has changed.                                                                                                                                                                                               |
| `drifted`             | A recipe, a state with `profile`, and at least one item in a drifted condition (Decision 3).                                                                                                                                                 | `apply` ran, and something it recorded for a current selection is missing, edited, or no longer recorded.                                                                                                                                                                |
| `incomplete`          | One of three cases: no recipe, and a state with `profile` or lock entries; no recipe, and a state without `profile` whose recorded base skill is gone; or a recipe, no state file, and lock entries or a file Calavera would manage on disk. | Some of Calavera's records are gone while others, or the files they described, remain: someone deleted the recipe or the state, an `eject` stopped partway or could not write its marker, or `eject --yes` left the recipe and the lock (owner decisions 9, 18, and 19). |

**The marker and the derived phase.** The `eject` marker is the one fact this ADR reads that no other record implies, so it is the closest the design comes to a stored phase. It cannot go stale the way a stored phase would, for two reasons. Only `eject` writes it: it removes everything else, writes the block, and then deletes the state file (owner decision 18; ADR-0017, Amendment 5). The records also take precedence over it: a marker next to a recipe, a state, or a lock entry is ignored, so a project that someone starts to manage again after `eject` reads as `bootstrapped`, `composed`, or `incomplete`, and the next `apply` removes the marker. A deleted, changed, or unpaired marker makes an ejected project read as `unmanaged`; those are the hand edits it cannot survive. The marker is read only in the branch of the phase tree where the recipe and the state file are absent and the lock file is absent or holds no entries; ADR-0017, Amendment 5 states the same condition.

**An edited marker block.** The block's contents are fixed text, one comment line (ADR-0017, Amendment 5). A complete block has paired markers and exactly that text. The phase function reads any block with paired markers as `ejected`, whatever it holds, but it compares the contents with the fixed text, and when they differ the doctors report the edit with its remedy: the person moves their own lines out of the block (owner decision of 2026-11-22, https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079002369). In `ejected`, the phase error names the edit. In a phase where records exist and the marker is otherwise ignored, the doctors report the edit as a note, the level owner decision 5 gives an edited managed file that stops the next `apply`: both are edits the person may have meant, and the remedy is theirs to choose. The doctors' wiring warnings for an edited hook block stay as they are today, because this ADR does not change those checks. `apply` and `eject` stop on an edited block before they write anything (ADR-0017, Amendment 5). A block with an unpaired or changed marker counts as no marker for the phase, but `apply` and `eject` stop on it too, so the doctors report it as a note in every phase, for the same reason, with the remedy to restore or remove the marker lines.

**The signal that `apply` ran.** `profile` is the signal because it is the one `apply` already uses (`stateShowsEarlierApply`), `apply` requires it in the recipe, and no other command writes it. One exception exists, described in `state.js:36-46`: an earlier release did not record the profile for an apply that installed only artifacts into a project whose state had none. Such a project reads as `composed` until its next `apply` records the profile. That is the only effect, because `composed` and `applied` differ in wording, not in exit status (Decision 4).

**A recipe without a state file.** `init` leaves a recipe and nothing else, which is `composed`. A recipe with no state file but with lock entries, or with any file Calavera would manage already on disk, is `incomplete` instead (owner decision 19, https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079383325). "A file Calavera would manage" is a managed file the recipe declares or an output of an artifact it selects. Such a project lost its state, or `eject --yes` left the recipe behind, and reading it as `composed` would tell the person to run `apply`, which then stops on every one of those files. The remedy names restoring the state from version control, or `apply --reown-managed-file`, which accepts that `apply` replaces those files with Calavera's contents. Three consequences follow from the ruling as written. First, a project that holds its own file where a managed file goes, such as its own `.editorconfig`, also reads as `incomplete` after `init`, until its first `apply`, and neither remedy fits it: there is no state to restore, and `--reown-managed-file` would replace the person's own file. Second, `--reown-managed-file` today has an effect only on a file the state records (`assertSafeManagedFileWrite`, `index.js:2554`); accepting a file without a record is a change to what `apply` overwrites, which this ADR does not make, so until a decision makes it, the remedy works only for files the state still records. Third, the rule tests for a missing state file, so a recipe next to a state without `profile`, such as after `--init` and `init` in an ejected project whose kept files remain, reads as `composed`, although `apply` stops on those files as well.

**A state without a recipe.** A state without `profile` and without lock entries is what `--init` leaves, which is `bootstrapped`, but only while the state records the base skill and its folder `.agents/skills/calavera` exists, edited or not. After an `eject` that removed the base skill and could not write its marker, the same state remains, and the project reads as `incomplete` with the remedy to run `eject` again (owner decision 18). Owner decision 18 sets the outcome; using the base skill to tell the two states apart is this ADR's mechanism. A person who deletes the base skill after `--init` also reads as `incomplete`, so the remedy names running `--init` again as well. If #673 stops the bootstrap from installing the base skill, this test needs another signal.

**One `eject --yes` outcome reads as `composed`, or as `incomplete`.** In a project whose only artifact is the base skill from `--init`, there is no package folder (ADR-0017, Decision 5). When the skill matches its record, `eject --yes` removes the skill, the lock, and the state, and leaves only the recipe, because Calavera keeps no record of the recipe's text. A recipe alone is exactly what `init` leaves, so the derivation reads this project as `composed`, and the doctors tell the person to run `apply`. Owner decision 9 covers a recipe and a lock without a state, not a recipe alone. The derivation cannot tell the two causes apart without another signal: the `eject` marker cannot serve, because `eject --yes` writes it only when nothing is left (ADR-0017, Amendment 5), and a marker next to a recipe also follows `init` after an `eject`. This ADR therefore accepts `composed` for this case, as the owner decided on 2026-11-22 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7078607351). Owner decision 19 narrows it: when the managed files that `eject` keeps are still on disk, which is the usual case, the recipe and those files read as `incomplete`, and `composed` applies only when nothing Calavera would manage remains.

**Differences that are not drift.** Two kinds of difference do not make a project `drifted`, because each is the expected result of a recipe edit that a later command resolves. An item the recipe selects that has no record yet is `pending`, as everything is in `composed`; the next `apply` resolves it. A lock entry the recipe no longer selects is a leftover; the next `artifacts install` or `artifacts update` drops it. Both are reported (Decision 4), but the phase stays `applied`. A managed file the recipe no longer declares is not classified, as today, because `doctor` does not look at it and `clean` removes it.

### 3. The condition of each item and its reason

The function classifies two kinds of item that both doctors already look at: artifacts (each lock entry and each selection without one) and managed files (each file the recipe declares, with its state record if there is one). It keeps `selected` as today: true or false when a recipe exists, null when it does not. Each condition comes with a reason, a sentence in Calavera's own words that says what the function found and what resolves it, such as "the lock records version 1.0.0, and .agents/skills/code-review/SKILL.md differs from the hash the state records". A reason names paths, IDs, and versions, and never quotes a file's contents.

| Condition    | Artifact                                                                                                                              | Managed file                                                                                                                                                                                     | Makes the project `drifted`?                                   |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| `pending`    | Selected, and no lock entry.                                                                                                          | Declared, no state record, and the file does not exist.                                                                                                                                          | No                                                             |
| `current`    | A lock entry, and every output exists, has a state record, and matches its hash.                                                      | A state record, the file exists, and the next `apply` would not stop on it.                                                                                                                      | No                                                             |
| `missing`    | A lock entry, or a selection whose outputs have state records, and an output does not exist.                                          | A state record, and the file does not exist.                                                                                                                                                     | Yes, after `apply`, for a selected artifact or a declared file |
| `edited`     | A lock entry, or a selection whose outputs have state records, and every output exists, and one differs from its state record's hash. | A state record, and the next `apply` or `update` would keep the file and stop on it: the same test as `inspectManagedFilePlan`'s `managed-file-conflict` for a recorded file (owner decision 5). | Yes, after `apply`, for a selected artifact or a declared file |
| `unrecorded` | A lock entry, every output exists, and one has no state record. Today's "not managed by Calavera".                                    | Not used.                                                                                                                                                                                        | Yes, after `apply`, for a selected artifact or a declared file |

In the last column, "after `apply`" means the state has a `profile`; the recipe must also select the artifact or declare the managed file. The function classifies only managed files the recipe declares, so that condition always holds for them. The order of the rows is the order of precedence: an artifact whose outputs are missing and unrecorded is `missing`, as today's report lists "files missing" first.

A managed file whose contents differ from its state record but that the next `apply` would not stop on is `current`. That is an edit that matches what `apply` would write, or that is equal JSON. The doctors stay silent about it (owner decision 5). To decide, the function plans the managed files with `apply`'s own planner, formats them with the project's formatter as `apply` does, and runs the same comparison as `inspectManagedFilePlan`, so the two cannot disagree.

**When the formatter loads.** The doctors load the project's formatter whenever `apply` would (owner decision 17, https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079383325): on every run with a recipe, because `apply` loads it even when no managed file needs it (#838, `index.js:3646-3648`). In a project that Vite+ does not manage, the loader returns no formatter and cannot fail (`packages/cli/src/utils/project-formatter.js:64`). In a project that declares `vite-plus` without installing it, loading fails, so the doctors report the error even in `composed`, before the first install, as the earlier ruling intended.

**When the formatter cannot load or refuses a file.** The formatter can fail in two ways. It cannot load when `vite-plus` is declared but not installed, or its package has no `vp` command (`project-formatter.js:69-85`). After it loads, it can refuse a file: Calavera's `.editorconfig` would change how `vp fmt` formats the file (`:156-166`), `vp fmt` fails (`:114-119`), a format run times out (`:108-113`), or `vite.config.ts` prints output that arrives with the formatted text (`packages/cli/src/utils/generated-text.js:58-70`, `json-rewrite.js:53-72`). For each failure, both doctors report a named error from the managed-file classification that names the file, the kind of failure, and that kind's own remedy, such as running `vp install`, saving the `.editorconfig` that Calavera prints, or making `vite.config.ts` print nothing. The error quotes no file text and no raw tool output; today's `apply` messages include the tool's standard error and the start of the returned text, which the doctors leave out. Both doctors exit 1, because `apply` stops on the same thing (owner decisions 15 and 16, https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079002369, https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079383325). `apply` keeps formatting every file before it writes any of them, so one `apply` after the fix does the whole job. `artifacts status` reports the same errors as notes and exits 0, as it does for every finding.

The function still classifies the phase, the artifacts, and the `pending` and `missing` managed files, which need no formatter. A managed file it cannot classify counts as not drifted, so the phase is `applied` unless another item drifted; the named error carries the uncertainty, and both doctors report the same phase.

Before `apply`, a selected artifact installed with `artifacts install` and then edited or deleted is still `edited` or `missing`, and still an error (Decision 4). The project stays `composed`, because `drifted` describes a difference from what `apply` recorded.

A selected artifact whose outputs already exist with a state record, but that has no lock entry, is installed without a lock entry. This happens when the recipe selects `skill-calavera` after the bootstrap installed it, or when the lock was deleted. When its outputs match their state records, it is `pending`, and its reason says that the files are present and that the install command records them in the lock, so the person is not told that an installed artifact is missing. When an output differs from its state record, it is `edited`, an error at #994's level, not `pending`, because an installed artifact that someone edited fails whether or not the lock records it (following owner decision 10 and #994).

Without a recipe, as in an `incomplete` project whose recipe was deleted, no managed file is declared, so the function classifies none and plans none.

A declared managed file that exists without a state record, such as the person's own `.editorconfig` before the first `apply`, is not classified as an item. When there is no state file, it makes the phase `incomplete` (Decision 2), and the phase error names it; when a state file exists, it is not reported, as today, and `apply`'s own conflict handling covers it.

### 5. The agreement rule

The two doctors never disagree about the same artifact or about the phase (owner decision 10). Stated exactly, for each artifact the `condition` in both `--json` results is the same, name and reason; whenever either doctor reports that artifact as an error or a warning, the other reports it at the same level; and `phase` and the level of the phase line are the same in both. During a pending artifact transaction both doctors report the phase `pending-transaction` and no artifact condition, so the rule holds there too (owner decision 20). Neither doctor reads the lock, the artifact files, or the wiring then, because a rollback may still change them; `doctor` still runs its recipe checks, the `package.json` warning, and the managed-file classification. Notes are outside the rule, because they never change a verdict: `artifacts doctor` prints a note for a current artifact the recipe no longer selects, and `doctor` prints nothing for it (Decision 4). The implementation tests the rule on a fixture for each phase and each artifact condition, with both doctors run on the same folder.

Their exit statuses may still differ, but only because of a check that one doctor makes and the other does not, and the output then names that check:

- Both doctors run the managed-file classification, because the phase depends on it, and both report its formatter errors (Decision 3). `doctor` alone reports each managed file's condition, wiring, the root-only and Git-hook refusals, and the recipe's integrations. When one of these is the only error, `doctor` exits 1 while `artifacts doctor` exits 0, and each such error names its check.
- `artifacts doctor` alone plans the `artifact-cache` block with `--check-updates` (`artifact-lifecycle.js:106-126`). When that fails, `artifacts doctor` stops with an error that names the cache block and says that it is not a finding about the project's phase or an artifact.

To make this visible, `doctor`'s verdict names each failing check, for example "Calavera doctor found 1 error, a managed file's condition, which artifacts doctor does not report.", and each issue in `doctor --json` carries a `check` field. The implementation pull request names the checks; this ADR fixes only that each error names the one it came from.

### 7. Unreadable records

When the recipe, the state, or the lock cannot be parsed or fails its shape check, the phase function stops, and all three commands report the same error and exit 1, as both doctors already do for an invalid state (the last row of "Where the commands disagree"). This ADR does not change what that error says. Today the message of a parse failure can include the file's text, because `JSON.parse`'s message is passed through; #1157 fixes that separately.

### 8. How the phase appears in `--json`

Each of the three results gains one field, `phase`, a plain string whose value is one of the eight phase names (owner decision 7), including `pending-transaction` (owner decision 20), so `phase` is always a string. `artifacts status` reports the project's phase, not one computed from artifacts alone (owner decision 8).

Each item gains `condition`, an object with the condition's `name` and its `reason` (Decision 3). In `artifacts status` and `artifacts doctor`, the items are the existing artifact entries, which keep `installed`, `managed`, `locallyEdited`, and `selected` so that current readers keep working. `doctor`'s result gains `artifacts` and `managedFiles`, one entry per classified item, with its ID or path, `selected`, and `condition`, so that a reader can check the agreement rule from the two JSON results alone. `doctor`'s `issues` keep `level` and `message`, add `check` (Decision 5), and `level` gains the value `"info"`. `ok` keeps its meaning: false when any issue, item, or phase line is an error.

The phase, the conditions, and the reasons are computed on every run and never written to any file (owner decisions 7 and 8). None of these results is a frozen surface in the interface contract (`docs/cross-repo/interface-contract.md`), so adding fields needs no cross-repo request.

### 9. #1111 follows this ADR

#1111 implements the "not selected, `missing`" cell of Decision 4: a warning that names the lock entry and the remedy, `artifacts install`, which drops the entry (#992), with exit 0 when nothing else is wrong. As the sequencing map orders it, #1111 follows #1112's implementation in wave 8, so its classification lives in the phase function from the start. Its acceptance criteria hold under this ADR: a selected artifact that is `missing` or `edited` still fails, and `artifacts status` agrees with `artifacts doctor` because both read the same condition. Under this ADR, `doctor` reports the same warning, which it does not today because it never reads the lock.

### 10. How C8 holds

The phase function writes nothing, and its conditions and reasons are never persisted. The three commands add no write. `artifacts status` keeps its transaction recovery, `artifacts doctor` drops its recovery, and both keep the `--check-updates` cache block (Decision 1). `eject` writes the marker as part of the list the person approved, or under `--yes` as Calavera's own new text, as ADR-0017, Amendment 5 describes. Only the CLI writes into projects; no approval boundary (`dry_run_apply`) is involved; no local edit is changed, only reported; nothing is written to `package.json`; and no conflict is resolved, so none needs a hard stop or a migration decision.

## Consequences

Both doctors fail in cases where one of them passes today. `doctor` fails for a selected artifact whose files were deleted, edited, or are unrecorded, which #994 already treats as failures in `artifacts doctor`; for a managed file that `apply` wrote and someone deleted; for an `incomplete` project after `eject --yes` or after a lost state; for a pending artifact transaction, which `doctor` did not check before; for a lock it cannot read, because `readLock` throws on an invalid lock (`artifact-lifecycle.js:1208-1213`) and `doctor` never read the lock before; and for each formatter failure on the managed-file check. `artifacts doctor` fails for an `unmanaged`, `ejected`, `incomplete`, or `pending-transaction` project, and for each formatter failure. It also fails for a selected, installed artifact without a lock entry whose files were edited, which passes today because `isArtifactHealthy` treats a missing lock entry as healthy (`artifact-status-report.js:153-155`). It passes for a lock entry the recipe no longer selects whose files are missing (#1111), edited, or unrecorded (owner decision 6), which fail today. It stops recovering a pending transaction, so it no longer writes files in that case. A project that holds its own file where a managed file goes now fails both doctors after `init` and before its first `apply` (Decision 2). A CI job that runs `doctor` and passed with a deleted skill or a deleted managed file will fail after the change, which is the intent. The implementation's changeset names each new failure.

`doctor` passes in one case where it fails today: a bootstrapped project without a recipe now warns and exits 0.

`doctor` prints fewer lines in `composed`: one warning that names each pending item once, instead of one warning per missing file. It prints a new note for an edited managed file that would stop the next `apply`, so the person learns about the conflict before `apply` refuses.

`doctor` now plans the managed files with `apply`'s planner and formats them with the project's formatter, to decide whether an edit would stop `apply`. That costs the planner's and the formatter's time on each run. Loading the formatter is new for `doctor`, and it loads on every run with a recipe, so a project that declares `vite-plus` without installing it now gets the named error of Decision 3 and exit 1, where `doctor` passed before. `doctor` still writes nothing.

`artifacts status` and `artifacts doctor` read managed files and wiring through the phase function so that they can report `drifted`. That costs file reads, the planner, and the formatter on every run with a recipe. Their item lines still cover artifacts only; a managed file or a wiring block affects their output only through the phase line, which names it when it alone causes `drifted`, and through the formatter errors.

The implementation's tests build a fixture for each phase, run all three commands on it, and check the phase, the exit status, and the agreement rule of Decision 5. Fixtures also cover an edited `ejected` block, each kind of formatter failure, a pending transaction, a lost state with managed files on disk, and an edited installed artifact without a lock entry. They include these transitions:

- `unmanaged` → `composed` through `init`, the path the owner named, and `unmanaged` → `bootstrapped` → `composed` through `--init` and then `init`;
- `composed` → `applied` → `drifted` → `applied`, through `apply`, an edit or deletion, and `apply` again;
- `applied` → `incomplete` when the recipe or the state is deleted;
- `applied` → `incomplete` through `eject --yes` in a project with package folders and through a stopped `eject`, `applied` → `composed` through `eject --yes` in a project whose only artifact is the base skill and whose recipe declares no managed file (Decision 2), and `applied` → `ejected` through a finished interactive `eject`;
- `ejected` → `incomplete` through `init` while kept files remain, and `ejected` → `composed` through `init` in a fixture without kept files, then `applied` through `apply`, which removes the marker.

## Owner decisions

The owner answered the ten open questions of the first draft on 2026-11-21 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7069063918), settled the choices this ADR's update had to make on 2026-11-22 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7078607351), and ruled on gaps from two independent reviews the same day (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079002369 and https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079383325). This ADR applies each answer in the decision named after it.

1. **Ejected projects are their own phase, `ejected`, marked by a line in `.gitignore` that `eject` writes** (Decision 2; ADR-0017, Amendment 5). Rationale: the doctors can then tell a project that left Calavera on purpose from one Calavera never managed, and say so.
2. **A project without Calavera's files fails both doctors, with exit 1** (Decision 4). Rationale: a doctor that finds nothing to check is most likely a leftover CI step, a wrong folder, or a recipe saved elsewhere, and a failure surfaces each of these.
3. **A bootstrapped project warns and exits 0** (Decision 4). Rationale: the next step, `init`, is expected, so the doctors should not fail on it. The owner corrected the label of this answer on 2026-11-22 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7078607351): it applies to `bootstrapped`, which has no recipe, and `composed` also warns and exits 0.
4. **A managed file that `apply` wrote and someone deleted is an error** (Decision 4). Rationale: it is the same kind of breakage as a deleted installed artifact, which fails under #994.
5. **An edited managed file is a note with exit 0, and only when the next `apply` or `update` will keep the file and stop on it; otherwise the doctors stay silent** (Decisions 3 and 4). Rationale: people tune configuration files on purpose, so only an edit that will block the next run is worth the person's attention.
6. **A lock entry the recipe no longer selects, whose files are edited or unrecorded, is a warning** (Decision 4). Rationale: it is a leftover record, not a broken project, the same reason the owner gave for deleted files on #1111. This narrows #994's rule that edited installed artifacts fail to artifacts the recipe still selects.
7. **`phase` is a plain string** (Decision 8). Rationale: an agent branches on one stable value, and the details are in the items.
8. **Each item carries a computed `condition` with its reason, derived on every run and never persisted, and `artifacts status` shows the project-wide phase** (Decisions 3 and 8). Rationale: a computed reason cannot go stale, and one phase for the whole project is the shared answer #1112 asks for.
9. **What `eject --yes` leaves, a recipe and a lock without a state, is `incomplete`, and the doctors name what remains and the remedy** (Decisions 2, 4, and 6). Rationale: the person must choose between restoring the state and finishing `eject`, and the output gives them what they need to choose.
10. **The two doctors never disagree about the same artifact or about the phase; `doctor` reads the lock and fails at #994's levels for artifacts; exit codes may differ only for a check one doctor alone makes, and the output names that check** (Decisions 4 and 5). Rationale: each command keeps its own subject, and a person who sees different exit codes can tell at once which check caused them.

The decisions of 2026-11-22:

11. **The marker is a Calavera block named `ejected` with one comment line, written at the end of `.gitignore`, a file that `eject` creates when the project has none; `eject` writes it only on a run that started from Calavera's records, after it removed everything else; `apply` removes it, and `init` and `--init` leave it** (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7078607351; ADR-0017, Amendment 5). Rationale: a block of its own survives the removal of the `artifact-cache` block and exists in projects without artifacts.
12. **When the base skill is the only artifact, the recipe that `eject --yes` leaves reads as `composed`** (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7078607351; Decision 2). Rationale: it is identical to what a fresh `init` leaves, so no derived signal can tell the two apart. Decision 19 narrows it to projects where nothing Calavera would manage remains (Decision 2).
13. **`ejected` is an error in both doctors; during a pending artifact transaction `doctor` reports a named error and does not read the lock; `condition` is `{ name, reason }`; `doctor --json` gains `artifacts` and `managedFiles` arrays, a `check` field on each issue, and an `info` level** (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7078607351; Decisions 4, 5, and 8). Rationale: each closes a gap the first ten answers left, as the update proposed.
14. **The `ejected` block's contents are fixed text; when they differ, `apply` and `eject` stop with the remedy that the person moves their own lines out of the block, the phase is still `ejected`, and the doctors report the edit** (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079002369; Decision 2; ADR-0017, Amendment 5). Rationale: it is the rule Calavera already follows for an edited recorded block.
15. **When the formatter cannot load while `doctor` checks managed files, the doctors report a named error with the remedy to install dependencies, for the managed-file check only, still classify the phase and the artifacts, and exit 1** (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079002369; Decision 3). Rationale: `apply` stops on the same thing, so a passing doctor would mislead.

The decisions on the second independent review, also of 2026-11-22 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079383325):

16. **A formatter that loads and then refuses a file gets a named error per refusal on the managed-file check, naming the file, the kind of refusal, and its remedy, quoting no file text or raw tool output; the doctors still classify the phase and the artifacts and exit 1** (Decision 3). Rationale: `apply` stops on the same thing, and the error must be safe to log.
17. **The doctors load the formatter whenever `apply` would** (Decision 3). Rationale: a project with `vite-plus` declared but not installed then gets the error the earlier ruling intended.
18. **`eject` removes everything else, writes the block, and then deletes the state file; if the block write fails, the state remains and the project reads `incomplete` with a remedy** (Decision 2; ADR-0017, Amendment 5). Rationale: no failure leaves an ejected project reading as one Calavera never managed.
19. **A recipe, no state file, and any file Calavera would manage already on disk reads `incomplete`; the remedy names restoring the state or `apply --reown-managed-file`, described as accepting that `apply` replaces those files** (Decisions 2 and 4). Rationale: `apply` would stop on those files, so `composed` would mislead.
20. **During a pending artifact transaction the phase is `pending-transaction`, reported the same way by `doctor`, `artifacts doctor`, and the read-only MCP status tool, with the remedy to run `artifacts status`, which recovers it and reports the recovered phase** (Decisions 1, 2, 4, 5, and 8). Rationale: `phase` stays a plain string and the agreement rule holds.

Two rules follow from earlier rulings without a new decision: a selected, installed, edited artifact with no lock entry fails at #994's level instead of passing as `pending` (Decision 3); and the remedies for an edited managed file include the ways to keep the edit, never only ways that discard it (Decision 4).

## Alternatives considered

**Store the phase in `.calavera/state.json`.** Each command that changes the project would write the phase. The owner rejected this on 2026-11-21, because a stored phase goes stale when a person edits or deletes files by hand, and every case in Decision 6 would need a writer. The `eject` marker is not this alternative: it records one event that no other file can show, only the command that causes it writes it, once, and every other record takes precedence over it (Decision 2).

**Fold an ejected project into `unmanaged`.** The first draft proposed this, because after `eject` nothing recorded that Calavera had managed the project. The owner chose a separate phase with a marker (owner decision 1), so the doctors can name `eject` and its remedies.

**Read `eject --yes`'s leftovers as `composed`.** A recipe without a state looks like a project before its first `apply`. This was rejected because the doctors would then tell the person to run `apply` on a project they asked to leave Calavera (owner decision 9).

**Let each command derive its own phase from shared helpers.** This keeps the commands independent, but each command would combine the helpers its own way, and the opposite answers in "Where the commands disagree" came from exactly that. One function that returns both the phase and each item's condition leaves nothing to combine.

**Make the phase alone decide the exit status.** For example, `drifted` fails and every other phase passes. This was rejected because the owner's decisions are per item: a deselected lock entry whose files were deleted passes (#1111), while an edited selected artifact fails, and both can occur in the same `drifted` project. The phase sets the wording and the expected items; each item's condition sets its level.

**Require equal exit statuses from the two doctors.** This would make `artifacts doctor` report managed files, wiring, and the recipe refusals, so it would become a second `doctor`. The owner chose agreement per artifact and per phase instead, with each exit-code difference named (owner decision 10).
