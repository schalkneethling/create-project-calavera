# ADR-0020: One Project Phase, Derived from the Project's Files, for Every Doctor

- **Status:** Accepted (2026-11-22, Schalk Neethling, merged in #1154)
- **Date:** 2026-11-21
- **Issue:** https://github.com/schalkneethling/create-project-calavera/issues/1112
- **Decides:** how `doctor`, `artifacts doctor`, and `artifacts status` agree on where a project is in Calavera's lifecycle, so that none of them fails or warns about something that is expected at that point. One function derives the project's phase from the recipe, `.calavera/state.json`, `.calavera/artifacts.lock.json`, the marker that `eject` leaves in `.gitignore`, and the files those records name, and every one of the three commands reads it. Calavera stores no phase (owner decision of 2026-11-21 on #1112 and #994). The phases are `pending-transaction`, `unmanaged`, `ejected`, `bootstrapped`, `composed`, `applied`, `drifted`, and `incomplete`. The same function also classifies each artifact and each managed file and gives the reason, so the two doctors never disagree about an artifact or about the phase. `doctor` reads the lock and fails at the levels #994 set for artifacts. Each command's `--json` result gains a `phase` string, and each item gains a computed `condition` with its reason, which is never persisted. A lock entry the recipe no longer selects, whose files were deleted, becomes a warning (#1111). ADR-0017, Amendment 5, in the same pull request, defines the marker. The owner answered the open questions of the first draft on 2026-11-21 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7069063918), settled the choices the update had to make and corrected the label of decision 3 on 2026-11-22 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7078607351), ruled on gaps from two independent reviews the same day (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079002369, https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079383325), and replaced one of those rulings later that day (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079621713), then extended the replacement (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7080058262), and ruled on a third independent review (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7082541321). This ADR records each answer in the decision it belongs to and in "Owner decisions". This document changes no code.

## Context

The owner asked on 2026-11-21, in the review of PR #1103 (#994), for a project lifecycle state, so that the doctors do not fail or report on things that are expected in the project's current phase. The example in #1112 is the time between `init`, which writes the recipe, and `apply`, which installs it. In that phase a selected artifact is not installed yet, and that is normal. `doctor` warns about it, `artifacts status` names it, and before the owner's decision on #994 `artifacts doctor` was about to fail on it.

The owner decided on the same day to derive the phase from the project's files in one shared function, not to store a phase that can go stale, and to decide the design in an ADR first. Two related decisions are already recorded on #994: a selected artifact that is not installed yet passes `artifacts doctor` with a note and exits 0, while missing or edited installed artifacts still fail; and a lock entry the recipe no longer selects, whose files were deleted, becomes a warning rather than a failure (#1111). This ADR builds on both and does not reopen them.

#1112's acceptance criteria ask for one function that derives the phase, used by all three commands, tests for each phase transition including the in-between state after `init`, and that the two doctor commands never give opposite answers about the same project. Its scope excludes "changing what each command checks, beyond reading the shared phase"; owner decisions 4, 5, 10, 13, 14, 15, 16, 17, 20, 21, 22, 23, and 25 extend `doctor`'s checks where this ADR says so. The sequencing map places this ADR in wave 7 of the `cli-experience` release and its implementation in wave 8, with #1111 following it (`docs/cross-repo/sequencing-map.md`, Section 0).

## What exists today

This section describes how each command and each record defines a project's state today, from the code, and then where the commands disagree. The commands run in the project folder, and `--config` names the recipe, which defaults to `calavera.config.json` (`CONFIG_FILE`, `packages/cli/src/project-local-commands.js:8`).

### The records

**The recipe** (`calavera.config.json`) is the person's declaration of what the project should have: a profile, integrations, scripts, and the AI artifacts in its `ai` list. `init` writes it, the Composer saves it, and `apply` writes it when it records an answer. The recipe schema requires `profile` (`apps/composer/public/calavera.config.schema.json`, `required`), and `apply` refuses a recipe without one. Calavera keeps no record of the recipe's text (ADR-0017, "What Calavera writes into a project today").

**The state** (`.calavera/state.json`) records what Calavera wrote: `profile`, `integrations`, `files`, `managedFiles` with a hash for each, `aiArtifacts` with a hash for each, `aiWiring`, `gitignoreBlocks`, and `qualityScript` (`packages/cli/src/state.js:24-34`). Several commands write it. The bootstrap (`--init`) writes it with the base skill's record (`agentBootstrap`, `packages/cli/src/index.js:4666`, written at `:4789`). `apply`, `clean`, `artifacts install`, and `artifacts update` rewrite it, and so do `artifacts status --check-updates` and `artifacts doctor --check-updates`, which record the artifact cache block (`artifact-lifecycle.js:620-632`). The state file's existence therefore does not show that `apply` ran.

Its `profile` does. `stateShowsEarlierApply` returns true when `profile` is set, because no other command sets it and `apply` records it on every run (`state.js:36-49`, written at `index.js:4112` from `recipe.profile`, `index.js:3800`). `apply` already relies on this signal to decide whether the project's scripts are Calavera's to compare (`index.js:3076`, `index.js:3598`). After `apply`, the state also keeps the record of an artifact the recipe no longer selects, so that `clean` can remove its unedited output (#829, `index.js:4097-4104`).

**The lock** (`.calavera/artifacts.lock.json`) records each installed artifact package: its ID, version, channel (`tag`), destination, and hashes (`readLock`, `packages/cli/src/artifact-lifecycle.js:1208`). `apply`, `artifacts install`, and `artifacts update` write it. The bootstrap does not, so the base skill it installs has a state record and no lock entry. Only `artifacts install` and `artifacts update` drop the lock entry of an artifact the recipe no longer selects, and they leave its files in place (#992; `keptEntries: []` at `artifact-lifecycle.js:1001`, reported at `:1013-1015`). `apply` keeps every existing entry (`keptEntries: lock.artifacts`, `artifact-lifecycle.js:360`), and `clean` rewrites only the state and never touches the lock. A person who deselects an artifact and runs `clean` therefore ends with its files and state record removed and its lock entry kept, which is the case #1111 is about.

**Managed files that were edited.** `apply` and `update` refuse to overwrite a managed file whose contents differ from both the planned contents and the hash its state record holds, unless the two are equal JSON or the person passes `--reown-managed-file` for it (`assertSafeManagedFileWrite`, `index.js:2535-2567`). That flag does not keep the edit: it lets the check pass, and `writeManagedFile` then overwrites the file with Calavera's planned contents (`index.js:2656-2677`). The dry run reports the same case as a `managed-file-conflict` error whose message ends "review, remove, or migrate it before applying this recipe" (`inspectManagedFilePlan`, `index.js:2799-2837`). Both checks compare against the planned contents after the project's formatter formats them (`formatManagedFilePlans`, `index.js:2762-2769`, called at `:3647-3650`), and `apply` stops before it writes anything when that formatter cannot load (#838, `index.js:3651-3653`). An edit that matches what `apply` would write does not stop it.

**`eject`** removes the recipe, the state, the lock, and the rest of Calavera's footprint, and keeps the installed tooling and the recipe-selected artifacts other than the base skill (ADR-0017, Decisions 2 and 3). It deletes the recipe with the other footprint files, then the package folders and the lock, and the state last (ADR-0017, Decision 7). Before ADR-0017, Amendment 5, nothing in the project recorded afterward that Calavera managed it. `eject --yes` removes only items that match Calavera's records exactly (ADR-0017, Decision 5). It leaves the recipe, whose text Calavera does not record, and each package folder it cannot check, and it keeps the lock while a package folder stays (`selectEjectItems`, `packages/cli/src/eject.js:1652-1673`). It keeps the state while it leaves the base skill or keeps the `artifact-cache` block, and it keeps that block while `.calavera/cache` is a symbolic link (ADR-0017, Amendment 2); otherwise it deletes the state. A run of `eject --yes` on an applied project can therefore leave a recipe and a lock with no state file, or, with a linked cache, the recipe, the state, and the lock together.

### `doctor`

`doctor` (`index.js:6148-6272`) builds a list of issues, each with the level `"error"` or `"warning"`, and its result is `{ command: "doctor", ok, issues }`, where `ok` is false only when an issue is an error (`index.js:6269`). The run exits 1 when `ok` is false (#1030, `index.js:7367-7376`). It reads the recipe and, for wiring only, the state. It never reads the lock, and it never recovers a pending artifact transaction.

- **No recipe:** an error, "Missing calavera.config.json. Run create-project-calavera init first." (`index.js:6154-6159`). The only other check that runs without a recipe is the warning for a missing `package.json` (`index.js:6161-6167`).
- **Checks of the recipe itself:** warnings for removed JavaScript and TypeScript toolchain integrations (#431), and errors when a root-only integration or an artifact that writes Git hooks is selected outside the repository root (#997, #1031, `index.js:6192-6211`).
- **A managed file the recipe declares that does not exist:** a warning, "Missing managed file" (`index.js:6213-6225`). The list comes from the recipe (`declaredManagedFiles`), not from the state, so `doctor` cannot tell a file that `apply` has not written yet from one that `apply` wrote and someone deleted. It does not compare hashes, so an edited managed file is not reported. A missing Varlock schema is a separate warning.
- **An output path of a selected AI artifact that does not exist:** a warning, "Missing managed AI skill" (`index.js:6246-6254`). Again the recipe is the source, so a selection that was never installed and an installed artifact whose files were deleted read the same. An edited artifact is not reported, and a lock entry the recipe no longer selects is not looked at.
- **The wiring that `apply` recorded** (ADR-0015, Decision 5): warnings for a missing or edited hook block or Claude Code group, and an error for a hook block whose script does not exist (`artifactWiringFindings`, `packages/cli/src/ai/artifact-wiring.js:572-681`, the error at `:622-626`).

### `artifacts status` and `artifacts doctor`

Both commands first recover a pending artifact transaction, which writes files, and then run the same function, `artifactStatus` (`runArtifactCommand`, `artifact-lifecycle.js:201-210`; `:604-772`). It reads the recipe if it exists, the lock, and the state, and it builds one entry per lock entry and one per selection without a lock entry (`artifact-lifecycle.js:642-736`). Each lock entry gets `installed` (every output path exists), `managed` (every output path has a state record), and `locallyEdited` (an output's hash differs from its state record) (`:644-677`), and `selected`, which is null when there is no recipe (`:694`). A selection without a lock entry gets `version: null` and an install command (`:698-734`).

`isArtifactHealthy` decides whether an entry is a problem: a selection without a lock entry is healthy, and a lock entry is healthy only when it is installed, managed, and unedited (`artifact-status-report.js:153-155`). The result's `ok` is true when every entry is healthy (`artifact-lifecycle.js:765`). `artifacts doctor` exits 1 when `ok` is false, and `artifacts status` always exits 0 (`index.js:7398-7409`). `artifacts doctor` prints a warning that names the selections not installed yet and a verdict line (`artifactDoctorVerdict`, `artifact-status-report.js:293-331`).

The health rule does not look at `selected`. A lock entry the recipe no longer selects, whose files were deleted, is therefore a failure, which is what #1111 changes. The rule also does not distinguish "no recipe" from "a recipe that selects nothing": with no recipe and no lock, the report is "The recipe selects no artifacts, and the artifact lock holds none." and `ok` is true (`artifact-status-report.js:170-173`).

### Where the commands disagree

Each row is a probe run on 2026-11-21 against `main` at `0012c34`, in a folder created for it that holds a `package.json`. The applied project is hand-built: a recipe from `init --yes --profile minimal --ai-artifact skill-code-review`, a state with a `profile`, records for `.editorconfig` and `skill-code-review`, and a lock entry for `skill-code-review` and one for `skill-project-goal`, which the recipe does not select. The `eject --yes` row comes from the review of the first draft, which ran a real `artifacts install`, `apply --yes --no-install`, and `eject --yes`.

| Project                                                               | `doctor`                                                                    | `artifacts doctor`                                                           |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| No recipe, state, or lock (never managed, or after `eject`)           | Error "Missing calavera.config.json", exit 1                                | "The recipe selects no artifacts, and the artifact lock holds none.", exit 0 |
| Bootstrapped with `--init`, no recipe yet                             | The same error, exit 1                                                      | The same report, exit 0                                                      |
| After `init`, before `apply`                                          | Two warnings, "Missing managed file" and "Missing managed AI skill", exit 0 | Warning "Selected artifact not installed yet", exit 0                        |
| Applied, selected artifact's files deleted                            | Warning "Missing managed AI skill", exit 0                                  | `skill-code-review ... files missing`, exit 1                                |
| Applied, selected artifact's files edited                             | Nothing about the artifact, exit 0                                          | `skill-code-review ... locally edited`, exit 1                               |
| Applied, a lock entry the recipe no longer selects, its files deleted | Nothing about the entry                                                     | `skill-project-goal ... files missing, not managed by Calavera`, exit 1      |
| Applied, then `eject --yes`: recipe and lock kept, state deleted      | Nothing about the artifact, exit 0                                          | The kept artifact "not managed by Calavera", exit 1                          |

Every row except the third and the last is an opposite exit status for the same project, which #1112's last acceptance criterion rules out. The third row is the in-between state the owner named: the two commands agree on the exit status, but `doctor` words an expected step as two problems. The sixth row is #1111. The base skill that the bootstrap installs has a state record and no lock entry, so neither command reports on it unless the recipe selects `skill-calavera`.

## Decision

### 1. One function derives the phase and classifies each item

One function, in its own module of `packages/cli/src`, derives the phase. It takes the recipe path (`--config`) and the project folder. It checks for a pending artifact transaction first, so `pending-transaction` wins over every other finding, including an unreadable record; while one is pending, it reads only the recipe, `package.json`, what the repository-root lookup needs, the journal, and whether each journaled backup exists (Decision 5). It then reads the recipe, computes the repository root the way `doctor` does today for root-only integrations and Git hooks (#925, `index.js:6181-6189`), and then reads the state, the lock, the `.gitignore` marker (Decision 2), the files the records name, the outputs of selected artifacts, and, to compare those outputs, the artifact cache (Decision 3). It returns:

- the project's `phase` (Decision 2);
- the `condition` of each artifact and each managed file, each with its reason (Decision 3);
- the wiring findings that `artifactWiringFindings` returns today;
- the per-file notes of Decision 3 for files Calavera would write that already exist without a record;
- while a transaction is pending, the files a rollback would replace or remove, read from the journal (Decision 5).

`doctor`, `artifacts doctor`, and `artifacts status` each call this function and render its result. None of them derives a phase or an item's condition on its own, so a rule changes in one place. `isArtifactHealthy` becomes a reading of an artifact's condition (Decision 4) rather than a separate rule. The function computes every phase, condition, and reason on each run and persists none of them (owner decisions 7 and 8).

The function itself writes nothing. Two writes stay outside it. `artifacts status` recovers a pending artifact transaction before it calls the function, as it does today, and reports the recovered phase. `artifacts doctor` stops recovering: like `doctor`, it reports the phase `pending-transaction` instead (owner decision 20). The cache block that `--check-updates` records before it resolves packages (#960) stays unchanged in both artifact commands, with one exception. While a transaction is pending, `artifacts doctor`, with or without `--check-updates`, plans no cache block, writes nothing, and resolves no package; it reports only `pending-transaction` with the remedy of owner decision 23. Today that write is safe only because `runArtifactCommand` recovers first (`artifact-lifecycle.js:202`). The write runs inside `artifactStatus` before any classification (`:629-631`), and it commits through `commitArtifactTransaction` (`:931`), which writes a new journal over `.calavera/artifact-transaction.json` and then deletes it (`:1310`, `:1323`). Without recovery first, it would read a half-committed state and overwrite the pending journal, which would orphan the rollback.

A second rule covers every other phase, in both `artifacts status` and `artifacts doctor`. With `--check-updates`, the command first classifies the project with the phase function, which writes nothing. It then writes the cache block, and resolves packages through the project's `.calavera/cache/npm`, only when a state file exists and the phase is `composed`, `applied`, or `drifted`. In every other case, it resolves through a temporary cache that it removes afterward, as a dry run does (`artifact-lifecycle.js:633-637`, `:771`), and it writes nothing into the project. Without this rule, `--check-updates` would recreate Calavera's footprint in a project being ejected. For example, `eject --yes` can leave the recipe, the lock, and a package folder, and delete the state and the `artifact-cache` block (`packages/cli/src/eject.js:1658-1667`). Today `--check-updates` would then plan a new block against an empty state (`artifact-lifecycle.js:131-138`, `:1215-1219`) and write `.calavera/state.json` without a `profile` (`:912-943`), turning that `incomplete` project into `composed`, which decision 9 rules out.

#1052 adds the read-only MCP tool for artifact status that ADR-0018, Decision 3 allows, as an adapter over the same core function as `artifacts status`. It returns the same `phase` and `condition` fields, and it differs from `artifacts status` in two rules, so #1052's acceptance criterion, that the tool returns the same data as `artifacts status --json`, does not hold in the two cases they cause:

- **(a) No recovery.** The tool writes nothing, so it never recovers a pending artifact transaction. While one is pending, it reports `pending-transaction` with the same list and remedy as both doctors (owner decisions 20 and 23), and its `checkUpdates` input resolves no package.
- **(b) No formatter.** The tool runs no project code (owner decision 24, https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7082541321), so it never loads the formatter. Each managed file that needs formatting to classify is `not-checked`, with the remedy to run `doctor`, and any phase that depends on such a file may differ: a `not-checked` file never makes a project `drifted` (Decision 3), so the tool reads `applied` where the CLI, which formats the file, reads `drifted` because of an edited managed file. The tool's phase line says so whenever any managed file is `not-checked`. The agreement rule excludes both the check and that phase for the tool, consistent with ADR-0018, Decision 3.

### 2. The phases and how each is derived

The phase answers "where is this project in Calavera's lifecycle?" It depends on which records exist and, after an apply, on whether the recorded items of the current selection still match the files. The function checks the records in this order and stops at the first phase that fits:

```text
artifact transaction journal exists? ── yes ................................ pending-transaction
└─ no: recipe file exists?
   ├─ no ─┬─ no state file and no lock entries ┬─ eject marker in .gitignore . ejected
   │      │                                    └─ no marker .................. unmanaged
   │      ├─ state without profile, no lock entries,
   │      │  and the base skill it records is present ........................ bootstrapped
   │      └─ otherwise ......................................................... incomplete
   └─ yes ┬─ no state file ┬─ lock entries ..................................... incomplete
          │                └─ no lock entries .................................. composed
          ├─ state without profile ............................................. composed
          └─ state has profile ┬─ an item drifted .............................. drifted
                               └─ otherwise .................................... applied
```

| Phase                 | Derived from                                                                                                                                                                                                                       | What it means                                                                                                                                                                                                                                                                         |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pending-transaction` | `.calavera/artifact-transaction.json` exists, whatever else the project holds.                                                                                                                                                     | An artifact operation stopped and its rollback has not run, so the lock may describe files that are not there. `artifacts status` recovers it (owner decision 20).                                                                                                                    |
| `unmanaged`           | No recipe, no state file, no lock entries, and no `eject` marker.                                                                                                                                                                  | Calavera never managed this project.                                                                                                                                                                                                                                                  |
| `ejected`             | No recipe, no state file, no lock entries, and the `eject` marker in `.gitignore` (ADR-0017, Amendment 5).                                                                                                                         | `eject` finished removing Calavera's footprint, and the project keeps the tooling Calavera installed (owner decision 1).                                                                                                                                                              |
| `bootstrapped`        | No recipe, a state file without `profile`, no lock entries, and the state records the base skill, whose folder exists.                                                                                                             | `--init` ran and wrote the guidance and the base skill; no recipe is composed yet. `init` is the expected next step.                                                                                                                                                                  |
| `composed`            | A recipe, and either a state without `profile`, or no state file and no lock entries.                                                                                                                                              | The recipe is written and `apply` has not run, or Calavera's state was lost without a lock to show it; files cannot tell the two apart (owner decision 21). Artifacts installed with `artifacts install` before `apply` are allowed, because that command writes their state records. |
| `applied`             | A recipe, a state with `profile`, and every recorded item of a selection matches its files.                                                                                                                                        | `apply` ran and nothing it recorded for the current selection has changed.                                                                                                                                                                                                            |
| `drifted`             | A recipe, a state with `profile`, and at least one item in a drifted condition (Decision 3).                                                                                                                                       | `apply` ran, and something it recorded for a current selection is missing, edited, or no longer recorded.                                                                                                                                                                             |
| `incomplete`          | One of three cases: no recipe, and a state with `profile` or lock entries; no recipe, and a state without `profile` that records no base skill or whose recorded base skill is gone; or a recipe, no state file, and lock entries. | Some of Calavera's records are gone while others, or the files they described, remain: someone deleted the recipe or the state, an `eject` stopped partway or could not write its marker, or `eject --yes` left the recipe and the lock (owner decisions 9 and 18).                   |

**The marker and the derived phase.** The `eject` marker is the one fact this ADR reads that no other record implies, so it is the closest the design comes to a stored phase. It cannot go stale the way a stored phase would, for two reasons. Only `eject` writes it: it removes everything else, writes the block, and then deletes the state file (owner decision 18; ADR-0017, Amendment 5). The records also take precedence over it: a marker next to a recipe, a state, or a lock entry is ignored, so a project that someone starts to manage again after `eject` reads as `bootstrapped`, `composed`, or `incomplete`, and the next `apply` removes the marker. A deleted, changed, or unpaired marker makes an ejected project read as `unmanaged`; those are the hand edits it cannot survive. The marker is read only in the branch of the phase tree where the recipe and the state file are absent and the lock file is absent or holds no entries; ADR-0017, Amendment 5 states the same condition.

**An edited marker block.** The block's contents are fixed text, one comment line (ADR-0017, Amendment 5). A complete block has paired markers and exactly that text. The phase function reads any block with paired markers as `ejected`, whatever it holds, but it compares the contents with the fixed text, and when they differ the doctors report the edit with its remedy: the person moves their own lines out of the block (owner decision of 2026-11-22, https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079002369). In `ejected`, the phase error names the edit. In a phase where records exist and the marker is otherwise ignored, the doctors report the edit as a note (owner decision 25, https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7082541321), following owner decision 5: it is an edit the person made, and `apply` stops on it with its own remedy. The doctors' wiring warnings for an edited hook block stay as they are today, because this ADR does not change those checks. `apply` and `eject` stop on an edited block before they write anything (ADR-0017, Amendment 5). A block with an unpaired or changed marker counts as no marker for the phase, but `apply` and `eject` stop on it too, so the doctors report it as a note in every phase (owner decision 25), with the remedy to restore or remove the marker lines.

**The signal that `apply` ran.** `profile` is the signal because it is the one `apply` already uses (`stateShowsEarlierApply`), `apply` requires it in the recipe, and no other command writes it. One exception exists, described in `state.js:36-46`: an earlier release did not record the profile for an apply that installed only artifacts into a project whose state had none. Such a project reads as `composed` until its next `apply` records the profile. That is the only effect, because `composed` and `applied` differ in wording, not in exit status (Decision 4).

**A recipe without a state file.** `init` leaves a recipe and nothing else, which is `composed`. A recipe with no state file but with lock entries is `incomplete` (owner decision 9), because every command that writes the lock also writes the state. A recipe with no state file and no lock entries stays `composed`, even when files sit at managed paths, because files cannot tell a lost state from a project whose own file, such as `.editorconfig`, predates `init` (owner decision 21, https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079621713). Each such file that differs from what Calavera would write gets a note instead (Decision 3).

**A state without a recipe.** A state without `profile` and without lock entries is what `--init` leaves, which is `bootstrapped`, but only while the state records the base skill and its folder `.agents/skills/calavera` exists, edited or not. After an `eject` that removed the base skill and could not write its marker, the same state remains, and the project reads as `incomplete` with the remedy to run `eject` again (owner decision 18). Owner decision 18 sets the outcome; using the base skill to tell the two states apart is this ADR's mechanism. A person who deletes the base skill after `--init` also reads as `incomplete`, so the remedy names running `--init` again as well. If #673 stops the bootstrap from installing the base skill, this test needs another signal.

**One `eject --yes` outcome reads as `composed`.** In a project whose only artifact is the base skill from `--init`, there is no package folder (ADR-0017, Decision 5). When the skill matches its record, `eject --yes` removes the skill, the lock, and the state, and leaves only the recipe, because Calavera keeps no record of the recipe's text. A recipe alone is exactly what `init` leaves, so the derivation reads this project as `composed`, and the doctors tell the person to run `apply`. Owner decision 9 covers a recipe and a lock without a state, not a recipe alone. The derivation cannot tell the two causes apart without another signal: the `eject` marker cannot serve, because `eject --yes` writes it only when nothing is left (ADR-0017, Amendment 5), and a marker next to a recipe also follows `init` after an `eject`. This ADR therefore accepts `composed` for this case, as the owner decided on 2026-11-22 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7078607351). The managed files that `eject` keeps get the notes of Decision 3 when they differ from what Calavera would write.

**Differences that are not drift.** Three kinds of difference do not make a project `drifted`, because each is the expected result of a recipe edit that a later command resolves or the person's own file. An item the recipe selects that has no record yet is `pending`, as everything is in `composed`; the next `apply` resolves it. A lock entry the recipe no longer selects is a leftover; the next `artifacts install` or `artifacts update` drops it. A newly declared managed file that already exists without a record is `unrecorded` (owner decision 22). All three are reported (Decision 4), but the phase stays `applied`. A managed file the recipe no longer declares is not classified, as today, because `doctor` does not look at it and `clean` removes it.

### 3. The condition of each item and its reason

The function classifies two kinds of item that both doctors already look at: artifacts (each lock entry and each selection without one) and managed files (each file the recipe declares, with its state record if there is one). It keeps `selected` as today: true or false when a recipe exists, null when it does not. Each condition comes with a reason, a sentence in Calavera's own words that says what the function found and what resolves it, such as "the lock records version 1.0.0, and .agents/skills/code-review differs from the hash the state records". A reason names paths, IDs, and versions, and never quotes a file's contents. A skill's output is its folder, because the state hashes the folder, so a skill's path in a reason or in `unrecordedFiles` names the folder. A recorded selection is a selected artifact without a lock entry whose outputs all have state records.

| Condition     | Artifact                                                                                                     | Managed file                                                                                                                                                                                                                 | Makes the project `drifted`?                                                                                          |
| ------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `pending`     | Selected, no lock entry, and no output that has a state record is missing or differs from it.                | Declared, no state record, and the file does not exist.                                                                                                                                                                      | No                                                                                                                    |
| `current`     | A lock entry, and every output exists, has a state record, and matches its hash.                             | A state record, the file exists, and the next `apply` would not stop on it; or no state record and the file is identical to what Calavera would write, or equal JSON.                                                        | No                                                                                                                    |
| `missing`     | A lock entry or a recorded selection, and an output does not exist.                                          | A state record, and the file does not exist.                                                                                                                                                                                 | Yes, after `apply`, for a selected artifact or a declared file                                                        |
| `edited`      | A lock entry or a recorded selection, and every output exists, and one differs from its state record's hash. | A state record, and the next `apply` or `update` would keep the file and stop on it: the same test as `inspectManagedFilePlan`'s `managed-file-conflict` for a recorded file (owner decision 5).                             | Yes, after `apply`, for a selected artifact or a declared file                                                        |
| `unrecorded`  | A lock entry, every output exists, and one has no state record. Today's "not managed by Calavera".           | Declared, no state record, and the file exists and differs from what Calavera would write, so `apply` would stop on it as not recorded (owner decisions 21 and 22).                                                          | Yes, after `apply`, for a selected artifact. Never for a managed file: nothing records it yet, as for a `pending` one |
| `not-checked` | Not used.                                                                                                    | A file the formatter is needed for, a recorded file whose hash differs from its record or an existing file without a record, when the formatter failed, or in the MCP status tool, which never loads it (owner decision 24). | No                                                                                                                    |

In the last column, "after `apply`" means the state has a `profile`; the recipe must also select the artifact or declare the managed file. The function classifies only managed files the recipe declares, so that condition always holds for them. Below `pending`, the order of the rows is the order of precedence: an artifact whose outputs are missing and unrecorded is `missing`, as today's report lists "files missing" first.

A managed file whose contents differ from its state record but that the next `apply` would not stop on is `current`. That is an edit that matches what `apply` would write, or that is equal JSON. The doctors stay silent about it (owner decision 5). To decide, the function plans the managed files with `apply`'s own planner, formats them with the project's formatter as `apply` does, and runs the same comparison as `inspectManagedFilePlan`, so the two cannot disagree.

**When the formatter loads.** The doctors load the project's formatter whenever `apply` would (owner decision 17, https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079383325): on every run with a recipe, except while a transaction is pending, when the function reads only what Decision 1 lists and loads no formatter, because `apply` loads it even when no managed file needs it (#838, `index.js:3651-3653`). In a project that Vite+ does not manage, the loader returns a pass-through formatter that leaves text unchanged and cannot fail (`packages/cli/src/utils/project-formatter.js:64`). In a project that declares `vite-plus` without installing it, loading fails, so the doctors report the error even in `composed`, before the first install, as the earlier ruling intended.

**When the formatter cannot load or refuses a file.** The formatter can fail in two ways. It cannot load when `vite-plus` is declared but not installed, or its package has no `vp` command (`project-formatter.js:69-85`). After it loads, it can refuse a file: Calavera's `.editorconfig` would change how `vp fmt` formats the file (`:171-181`), `vp fmt` fails (`:115-119`), a format run times out (`:110-114`), or `vite.config.ts` prints output that arrives with the formatted text (`packages/cli/src/utils/generated-text.js:58-76`, `json-rewrite.js:61-83`). For each failure, both doctors report a named error from the managed-file classification that names the file, the kind of failure, and that kind's own remedy, such as running `vp install`, saving the `.editorconfig` that Calavera prints, or making `vite.config.ts` print nothing. The error quotes no file text and no raw tool output, as `apply`'s own messages already do since #1163 (#1157): a failed `vp fmt` run names how it ended and says that Calavera does not show its output (`project-formatter.js:115-119`), and the checks on returned text describe what went wrong without quoting it (`generated-text.js:58-76`, `json-rewrite.js:61-83`). Both doctors exit 1, because `apply` stops on the same thing (owner decisions 15 and 16, https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079002369, https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079383325). `apply` keeps formatting every file before it writes any of them, so one `apply` after the fix does the whole job. `artifacts status` reports the same errors as notes and exits 0, as it does for every finding.

The formatter is needed only for two kinds of managed file: a recorded file whose hash differs from its record, which may be `edited` or `current`, and an existing file without a record, which may be `unrecorded` or `current`. A recorded file whose hash equals its record is `current` without the formatter, because `apply` accepts it (`index.js:2548-2552`), and `pending` and `missing` need no formatter either. When the formatter fails, each file of the two kinds is `not-checked`, a condition of its own whose reason names the formatter failure. A `not-checked` file does not make the project `drifted`, so the phase is `applied` unless another item drifted; the named error carries the uncertainty, and both doctors report the same phase. The read-only MCP status tool, which never loads the formatter, reports the same files as `not-checked` (Decision 1).

Before `apply`, a selected artifact installed with `artifacts install` and then edited or deleted is still `edited` or `missing`, and still an error (Decision 4). The project stays `composed`, because `drifted` describes a difference from what `apply` recorded.

A selected artifact whose outputs already exist with a state record, but that has no lock entry, is installed without a lock entry. This happens when the recipe selects `skill-calavera` after the bootstrap installed it, or when the lock was deleted. When its outputs match their state records, it is `pending`, and its reason says that the files are present and that the install command records them in the lock, so the person is not told that an installed artifact is missing. When an output differs from its state record, it is `edited`, an error at #994's level, not `pending`, because an installed artifact that someone edited fails whether or not the lock records it (following owner decision 10 and #994).

Without a recipe, as in an `incomplete` project whose recipe was deleted, no managed file is declared, so the function classifies none and plans none.

**Files Calavera would write that already exist without a record.** Every file that Calavera would write, that already exists, that differs from what Calavera would write, and that has no state record gets an info-level note, wherever `apply` would stop on it as not recorded as Calavera-managed (owner decisions 21 and 22, https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7080058262). For a managed file, `apply` stops in `assertSafeManagedFileWrite` (`index.js:2562-2566`), and the file's condition is `unrecorded`. For an artifact's output, `apply` stops in `assertSafeAiWrite` (`packages/cli/src/ai/artifacts.js:501-531`); an artifact without a lock entry stays `pending` for the phase, and each such output gets its own note. An artifact with a lock entry and an output without a record is the `unrecorded` error of Decision 4, as today, and gets no per-output note on top of it. The remedies keep the person's file: rename or move it, deselect the integration or the artifact, or migrate its settings, or for an artifact's output its contents; the note never offers `--reown-managed-file`, which has no effect on a file without a state record. A file identical to what Calavera would write gets no note, because `apply` accepts it.

To tell an artifact output that differs from one that is identical, the function needs the artifact's payload. `apply` downloads it, and the phase function never downloads it, because it stays offline; the version notice of ADR-0019 is a separate request that does not feed the phase. Per-output notes exist only for an artifact without a lock entry, so the only payload source is the artifact cache, `.calavera/cache/npm` (`CACHE_PATH`, `artifact-lifecycle.js:39`). The function compares only under three conditions. It reads the cache with `offline: true`, so it never contacts the registry (`packages/artifact-core/src/registry.js:20-62`, `:93-121`). It first copies the cache into the operating system's temporary folder and reads only the copy, as dry runs do (`artifact-lifecycle.js:529-532`), so the project's `.calavera/cache/npm` stays byte for byte unchanged. It removes the temporary folder afterward. The implementation adds a test that the project's cache is unchanged after a doctor run. The function does not recover a pending transaction, which the tree has already reported (Decision 2). The comparison uses the version that the cached metadata names for the artifact's channel, while `apply` resolves the current version online, so even a match is not proof that `apply` accepts the file: a match still gets a note that names the cached version and says that `apply` resolves the current version online. A `pending` artifact has no lock entry, and the cache rarely holds its tarball before the first `apply`, so in that case the note is usually the conditional one: `apply` stops on the file unless it matches the package, which the doctors cannot check offline. Its remedy adds `apply --dry-run`, which stages the package in a temporary folder and reports the exact refusal without writing to the project, because it runs the same check (`packages/cli/src/ai/artifacts.js:576-582`) and skips only the write (`:593`).

A declared managed file that exists without a state record, such as the person's own `.editorconfig` before the first `apply`, is `unrecorded` when the file differs from what Calavera would write, whatever the phase: `apply` will stop on it as not recorded as Calavera-managed (`index.js:2562-2566`). A file identical to what Calavera would write is `current`, because `apply` already accepts it (owner decision 21); this ADR treats a file with equal JSON the same way, for the same reason, because `apply` accepts it too (`index.js:2544-2556`). The same holds after an `apply`, for a newly declared managed file that already exists without a record (owner decision 22).

### 5. The agreement rule

The two doctors never disagree about the same artifact or about the phase (owner decision 10). Stated exactly, for each artifact the `condition` in both `--json` results is the same, name and reason; whenever either doctor reports that artifact as an error or a warning, the other reports it at the same level; and `phase` and the level of the phase line are the same in both. During a pending artifact transaction both doctors report the phase `pending-transaction` and no artifact condition, so the rule holds there too (owner decision 20); `artifacts doctor` then also plans no cache block, writes nothing, and resolves no package, even with `--check-updates`; in a phase outside `composed`, `applied`, and `drifted`, or without a state file, `--check-updates` resolves through a temporary cache and writes nothing (Decision 1). Neither doctor reads the lock, the state, the artifact files, the managed files, or the wiring then, because a rollback may still change them and the journal covers the state and the lock (`artifact-lifecycle.js:935`, `:1145-1146`): mid-commit the state can be missing, which would misread recorded managed files. `doctor` still runs its recipe checks and the `package.json` warning. For the MCP status tool, the rule excludes the managed-file check that needs the formatter, and the phase when it depends on a `not-checked` file (Decision 1). Notes are outside the rule, because they never change a verdict: `artifacts doctor` prints a note for a current artifact the recipe no longer selects, and `doctor` prints nothing for it (Decision 4). Both doctors also print the per-file notes of Decision 3 for an artifact's outputs, and they print the same notes. The implementation tests the rule on a fixture for each phase and each artifact condition, with both doctors run on the same folder.

Their exit statuses may still differ, but only because of a check that one doctor makes and the other does not, and the output then names that check:

- Both doctors run the managed-file classification, because the phase depends on it, and both report its formatter errors (Decision 3). `doctor` alone reports each managed file's condition, wiring, the root-only and Git-hook refusals, and the recipe's integrations. When one of these is the only error, `doctor` exits 1 while `artifacts doctor` exits 0, and each such error names its check.
- `artifacts doctor` alone plans the `artifact-cache` block with `--check-updates` (`artifact-lifecycle.js:106-126`). When that fails, `artifacts doctor` stops with an error that names the cache block and says that it is not a finding about the project's phase or an artifact.

To make this visible, `doctor`'s verdict names each failing check, for example "Calavera doctor found 1 error, a managed file's condition, which artifacts doctor does not report.", and each issue in `doctor --json` carries a `check` field. The implementation pull request names the checks; this ADR fixes only that each error names the one it came from.

| `eject` stopped after deleting the recipe, in a project that only ran `--init` and `init`                                        | `bootstrapped` while the base skill remains, `incomplete` once `eject` removed it                                                                                                          | The phase line, which names running `eject` again as well as `init`.                                                                                                                                                                                                       |
| `eject --yes` kept the `artifact-cache` block and the state because `.calavera/cache` is a symbolic link (ADR-0017, Amendment 2) | `applied` or `drifted`, from the remaining records                                                                                                                                         | What those records show, such as the base skill as `missing` when the recipe selects it; nothing tells this from an applied project, so the doctors do not name the unfinished `eject`. Running `eject` without `--yes` removes the rest.                                  |
| `eject --yes` left the recipe, the lock, and a package folder, and deleted the state                                             | `incomplete`                                                                                                                                                                               | The phase error, which names the recipe, the lock, and the package folders that remain, and the remedy to run `eject` without `--yes` (owner decision 9).                                                                                                                  |

### 7. Unreadable records

When the recipe, the state, or the lock cannot be parsed or fails its shape check, the phase function stops, and all three commands report the same error and exit 1, as both doctors already do for an invalid state (the last row of "Where the commands disagree"). This ADR does not change what that error says. Since #1163 (#1157), both readers throw a `JSONParseError` that names the file and the position and quotes none of its text (`packages/cli/src/utils/fs.js`), so the error is safe to log.

### 8. How the phase appears in `--json`

Each of the three results gains one field, `phase`, a plain string whose value is one of the eight phase names (owner decision 7), including `pending-transaction` (owner decision 20), so `phase` is always a string in every result. A run that stops before it returns a result, on an unreadable record (Decision 7) or a cache-block step that fails to plan or record, prints an error and no result, so it carries no `phase`. `artifacts status` reports the project's phase, not one computed from artifacts alone (owner decision 8).

Each item gains `condition`, an object with the condition's `name` and its `reason` (Decision 3). In `artifacts status` and `artifacts doctor`, the items are the existing artifact entries, which keep `installed`, `managed`, `locallyEdited`, and `selected` so that current readers keep working. Each artifact entry in all three results also gains `unrecordedFiles`, always present and empty when no output carries the note of Decision 3. Each element is `{ path, comparedVersion, matches }`: `comparedVersion` is the cached version the output was compared against, or null when the doctors could not compare it offline, and `matches` says whether the output equals that version, or is null. `doctor`'s result gains `artifacts` and `managedFiles`, one entry per classified item, with its ID or path, `selected`, and `condition`, so that a reader can check the agreement rule from the two JSON results alone. `doctor`'s `issues` keep `level` and `message`, add `check` (Decision 5), and `level` gains the value `"info"`. `ok` keeps its meaning: false when any issue, item, or phase line is an error.

The phase, the conditions, and the reasons are computed on every run and never written to any file (owner decisions 7 and 8). None of these results is a frozen surface in the interface contract (`docs/cross-repo/interface-contract.md`), so adding fields needs no cross-repo request.

```json
{
  "command": "artifacts doctor",
  "phase": "drifted",
  "ok": false,
  "artifacts": [
    {
      "id": "skill-code-review",
      "selected": true,
      "locallyEdited": true,
      "unrecordedFiles": [],
      "condition": {
        "name": "edited",
        "reason": "The lock records version 1.0.0, and .agents/skills/code-review differs from the hash the state records."
      }
    },
    {
      "id": "skill-project-goal",
      "selected": false,
      "installed": false,
      "unrecordedFiles": [],
      "condition": {
        "name": "missing",
        "reason": "The recipe no longer selects skill-project-goal, and its files were deleted, so artifacts install drops its lock entry."
      }
    }
  ]
}
```

The example shows only the fields this ADR adds or names, and its reasons illustrate the kind of sentence, not final wording. A real result carries every field it carries today.

### 9. #1111 follows this ADR

#1111 implements the "not selected, `missing`" cell of Decision 4: a warning that names the lock entry and the remedy, `artifacts install`, which drops the entry (#992), with exit 0 when nothing else is wrong. As the sequencing map orders it, #1111 follows #1112's implementation in wave 8, so its classification lives in the phase function from the start. Its acceptance criteria hold under this ADR: a selected artifact that is `missing` or `edited` still fails, and `artifacts status` agrees with `artifacts doctor` because both read the same condition. Under this ADR, `doctor` reports the same warning, which it does not today because it never reads the lock.

### 10. How C8 holds

The phase function writes nothing, and its conditions and reasons are never persisted. The three commands add no write. `artifacts status` keeps its transaction recovery, and `artifacts doctor` drops its recovery. Both keep the `--check-updates` cache block, except that `artifacts doctor` writes nothing at all while a transaction is pending, so it can never overwrite the pending journal, and neither command writes the block without a state file or outside `composed`, `applied`, and `drifted` (Decision 1). `eject` writes the marker as part of the list the person approved, or under `--yes` as Calavera's own new text, as ADR-0017, Amendment 5 describes. Only the CLI writes into projects; no approval boundary (`dry_run_apply`) is involved; no local edit is changed, only reported; nothing is written to `package.json`; and no conflict is resolved, so none needs a hard stop or a migration decision.

## Consequences

Both doctors fail in cases where one of them passes today. `doctor` fails for a selected artifact whose files were deleted, edited, or are unrecorded, which #994 already treats as failures in `artifacts doctor`; for a managed file that `apply` wrote and someone deleted; for an `incomplete` project after `eject --yes` or after a lost state with lock entries; for a pending artifact transaction, which `doctor` did not check before; for a lock it cannot read, because `readLock` throws on an invalid lock (`artifact-lifecycle.js:1208-1213`) and `doctor` never read the lock before; and for each formatter failure on the managed-file check. `artifacts doctor` fails for an `unmanaged`, `ejected`, `incomplete`, or `pending-transaction` project, and for each formatter failure. It also fails for a selected, installed artifact without a lock entry whose files were edited, which passes today because `isArtifactHealthy` treats a missing lock entry as healthy (`artifact-status-report.js:153-155`). It passes for a lock entry the recipe no longer selects whose files are missing (#1111), edited, or unrecorded (owner decision 6), which fail today. It stops recovering a pending transaction, so it no longer writes files in that case. A CI job that runs `doctor` and passed with a deleted skill or a deleted managed file will fail after the change, which is the intent. The implementation's changeset names each new failure.

`doctor` passes in one case where it fails today: a bootstrapped project without a recipe now warns and exits 0.

`doctor` prints fewer lines in `composed`: one warning that names each pending item once, instead of one warning per missing file. It prints a new note for an edited managed file that would stop the next `apply`, and for each existing file Calavera would write, a managed file or an artifact's output, that would stop `apply` as not recorded, so the person learns about the conflict before `apply` refuses.

`doctor` now plans the managed files with `apply`'s planner and formats them with the project's formatter, to decide whether an edit would stop `apply`. That costs the planner's and the formatter's time on each run. Loading the formatter is new for `doctor`, and it loads on every run with a recipe, so a project that declares `vite-plus` without installing it now gets the named error of Decision 3 and exit 1, where `doctor` passed before. `doctor` still writes nothing.

`artifacts status` and `artifacts doctor` read managed files and wiring through the phase function so that they can report `drifted`. That costs file reads, the planner, and the formatter on every run with a recipe. Their item lines still cover artifacts only; a managed file or a wiring block affects their output only through the phase line, which names it when it alone causes `drifted`, and through the formatter errors.

The implementation's tests build a fixture for each phase, run all three commands on it, and check the phase, the exit status, and the agreement rule of Decision 5. Fixtures also cover an edited `ejected` block, each kind of formatter failure, a pending transaction, a lost state without lock entries and with differing files at managed paths, an edited installed artifact without a lock entry, and a selected artifact's differing files on disk before the first `apply`. They include these transitions:

- `unmanaged` → `composed` through `init`, the path the owner named, and `unmanaged` → `bootstrapped` → `composed` through `--init` and then `init`;
- `composed` → `applied` → `drifted` → `applied`, through `apply`, an edit or deletion, and `apply` again;
- `applied` → `incomplete` when the recipe is deleted, or when the state is deleted while the lock has entries; `applied` → `composed` when the state is deleted and the lock has none, with a note for each differing managed file and artifact output;
- `applied` → `incomplete` through `eject --yes` in a project with package folders and through a stopped `eject`, `applied` → `composed` through `eject --yes` in a project whose only artifact is the base skill (Decision 2), and `applied` → `ejected` through a finished interactive `eject`;
- `ejected` → `composed` through `init`, with a note for each kept managed file and artifact output that differs from what Calavera would write, then `applied` through `apply` once the person renames, moves, or migrates those files, which removes the marker.

## Items for the implementation issues

The fourth independent review found these low items. Under owner decision 26, they move into the implementation issues, where tests settle them:

- A hook artifact has two outputs. When only one has a state record and that output is missing or edited, no condition in Decision 3 fits it.
- `eject --yes` also keeps the state when the base skill or the `artifact-cache` block is edited (`packages/cli/src/eject.js:1658-1663`), which leaves a project that reads as `applied`, like the linked-cache case in Decision 6. Because that project reads as `applied`, `--check-updates` would then write back the `artifact-cache` block that `eject` removed, since Decision 1 allows the block in `applied`.
- An edited `.gitignore` block without a record stops `apply` but gets no note.
- During a pending transaction the function also reads whether each backup exists, to list what a rollback would replace or remove; the behavior for an unreadable recipe or journal while a transaction is pending is not specified.
- After one formatter refusal, whether every file that needs the formatter becomes `not-checked`, or only the refused file, is not specified.
- Recording the cache block formats the state with the project's formatter (`formatRecordText`, `artifact-lifecycle.js:914`), which can fail. Under `artifacts status`, whose contract is to exit 0, that failure should be a note rather than a stopped run; the implementation decides how it surfaces in `artifacts doctor`.

## Owner decisions

The owner answered the ten open questions of the first draft on 2026-11-21 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7069063918), settled the choices this ADR's update had to make on 2026-11-22 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7078607351), ruled on gaps from two independent reviews the same day (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079002369 and https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079383325), and replaced one of those rulings later that day (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079621713), then extended the replacement (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7080058262), and ruled on a third independent review (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7082541321). This ADR applies each answer in the decision named after it.

1. **Ejected projects are their own phase, `ejected`, marked by a line in `.gitignore` that `eject` writes** (Decision 2; ADR-0017, Amendment 5). Rationale: the doctors can then tell a project that left Calavera on purpose from one Calavera never managed, and say so.
2. **A project without Calavera's files fails both doctors, with exit 1** (Decision 4). Rationale: a doctor that finds nothing to check is most likely a leftover CI step, a wrong folder, or a recipe saved elsewhere, and a failure surfaces each of these.
3. **A bootstrapped project warns and exits 0** (Decision 4). Rationale: the next step, `init`, is expected, so the doctors should not fail on it. The owner corrected the label of this answer on 2026-11-22 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7078607351): it applies to `bootstrapped`, which has no recipe, and `composed` also warns and exits 0.
4. **A managed file that `apply` wrote and someone deleted is an error** (Decision 4). Rationale: it is the same kind of breakage as a deleted installed artifact, which fails under #994.
5. **An edited managed file is a note with exit 0, and only when the next `apply` or `update` will keep the file and stop on it; otherwise the doctors stay silent** (Decisions 3 and 4). Rationale: people tune configuration files on purpose, so only an edit that will block the next run is worth the person's attention.
6. **A lock entry the recipe no longer selects, whose files are edited or unrecorded, is a warning** (Decision 4). Rationale: it is a leftover record, not a broken project, the same reason the owner gave for deleted files on #1111. This narrows #994's rule that edited installed artifacts fail to artifacts the recipe still selects.
7. **`phase` is a plain string** (Decision 8). Rationale: an agent branches on one stable value, and the details are in the items.
8. **Each item carries a computed `condition` with its reason, derived on every run and never persisted, and `artifacts status` shows the project-wide phase** (Decisions 3 and 8). Rationale: a computed reason cannot go stale, and one phase for the whole project is the shared answer #1112 asks for.
9. **What `eject --yes` leaves, a recipe and a lock without a state, is `incomplete`, and the doctors name what remains and the remedy** (Decisions 2, 4, and 6). Rationale: the person must choose between restoring the state and finishing `eject`, and the output gives them what they need to choose.
10. **The two doctors never disagree about the same artifact or about the phase; `doctor` reads the lock and fails at #994's levels for artifacts; exit codes may differ only for a check one doctor alone makes, and the output names that check** (Decisions 4 and 5). Rationale: each command keeps its own subject, and a person who sees different exit codes can tell at once which check caused them.

The decisions of 2026-11-22:

11. **The marker is a Calavera block named `ejected` with one comment line, written at the end of `.gitignore`, a file that `eject` creates when the project has none; `eject` writes it only on a run that started from Calavera's records, after it removed everything else; `apply` removes it, and `init` and `--init` leave it** (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7078607351; ADR-0017, Amendment 5). Rationale: a block of its own survives the removal of the `artifact-cache` block and exists in projects without artifacts.
12. **When the base skill is the only artifact, the recipe that `eject --yes` leaves reads as `composed`** (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7078607351; Decision 2). Rationale: it is identical to what a fresh `init` leaves, so no derived signal can tell the two apart.
13. **`ejected` is an error in both doctors; during a pending artifact transaction `doctor` reports a named error and does not read the lock; `condition` is `{ name, reason }`; `doctor --json` gains `artifacts` and `managedFiles` arrays, a `check` field on each issue, and an `info` level** (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7078607351; Decisions 4, 5, and 8). Rationale: each closes a gap the first ten answers left, as the update proposed.
14. **The `ejected` block's contents are fixed text; when they differ, `apply` and `eject` stop with the remedy that the person moves their own lines out of the block, the phase is still `ejected`, and the doctors report the edit** (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079002369; Decision 2; ADR-0017, Amendment 5). Rationale: it is the rule Calavera already follows for an edited recorded block.
15. **When the formatter cannot load while `doctor` checks managed files, the doctors report a named error with the remedy to install dependencies, for the managed-file check only, still classify the phase and the artifacts, and exit 1** (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079002369; Decision 3). Rationale: `apply` stops on the same thing, so a passing doctor would mislead.

The decisions on the second independent review, also of 2026-11-22 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079383325):

16. **A formatter that loads and then refuses a file gets a named error per refusal on the managed-file check, naming the file, the kind of refusal, and its remedy, quoting no file text or raw tool output; the doctors still classify the phase and the artifacts and exit 1** (Decision 3). Rationale: `apply` stops on the same thing, and the error must be safe to log.
17. **The doctors load the formatter whenever `apply` would** (Decision 3). Rationale: a project with `vite-plus` declared but not installed then gets the error the earlier ruling intended.
18. **`eject` removes everything else, writes the block, and then deletes the state file; if the block write fails, the state remains and the project reads `incomplete` with a remedy** (Decision 2; ADR-0017, Amendment 5). Rationale: no failure leaves an ejected project reading as one Calavera never managed.
19. **Withdrawn and replaced by decision 21.** The ruling that a recipe, no state file, and any file Calavera would manage on disk reads `incomplete` no longer applies (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079621713).
20. **During a pending artifact transaction the phase is `pending-transaction`, reported the same way by `doctor`, `artifacts doctor`, and the read-only MCP status tool, with the remedy to run `artifacts status`, which recovers it and reports the recovered phase** (Decisions 1, 2, 4, 5, and 8). Rationale: `phase` stays a plain string and the agreement rule holds.

Two rules follow from earlier rulings without a new decision: a selected, installed, edited artifact with no lock entry fails at #994's level instead of passing as `pending` (Decision 3); and the remedies for an edited managed file include the ways to keep the edit, never only ways that discard it (Decision 4).

The decision that replaced decision 19, also of 2026-11-22 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7079621713):

21. **With no state file, or a state without `profile`, the phase stays `composed` (or `bootstrapped`); each existing file at a managed path that differs from what Calavera would write gets a note on the managed-file check, with remedies that keep the person's file and never `--reown-managed-file`; an identical file gets no note** (Decisions 2, 3, and 4). Rationale: files cannot tell a lost state from a project whose own file predates `init`, and `--reown-managed-file` does nothing for a file without a state record.

The extension of decision 21, also of 2026-11-22 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7080058262):

22. **The same note applies to every file Calavera would write that already exists, differs from what Calavera would write, and has no record, wherever `apply` would stop on it as not recorded: a selected artifact's files before the first `apply`, where the artifact stays `pending` and the note is per file, and, after the first `apply`, a newly declared managed file that already exists; the remedies keep the person's file, never `--reown-managed-file`, and an identical file gets no note** (Decisions 1, 3, 4, 5, 6, and 8). Rationale: the person learns about every file `apply` will refuse before it refuses, in one rule.

The decisions on the third independent review, also of 2026-11-22 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7082541321):

23. **During a pending transaction, the doctors and the MCP status tool read the journal without writing, list the files a rollback would replace, and tell the person to save edits to them before running `artifacts status`; making the rollback keep edits is #1174** (Decisions 1, 4, 5, and 6). Rationale: the remedy must not destroy the person's work.
24. **The read-only MCP status tool runs no project code: it reports the phase and every condition it can work out without the formatter, and managed files that need formatting are `not-checked`, with the remedy to run `doctor`; the agreement rule excludes that one check for the tool** (Decisions 1, 3, and 5). Rationale: ADR-0018, Decision 3 keeps the tool read-only.
25. **Marker problems, an edited `ejected` block or a broken marker in a managed project, are notes, following decision 5** (Decision 2). Rationale: they are edits the person made, and `apply` stops on them with its own remedy.
26. **The owner accepts this ADR when the next independent review finds no important or medium problem; low findings move into the implementation issues.** Rationale: tests settle edge cases.

## Alternatives considered

**Store the phase in `.calavera/state.json`.** Each command that changes the project would write the phase. The owner rejected this on 2026-11-21, because a stored phase goes stale when a person edits or deletes files by hand, and every case in Decision 6 would need a writer. The `eject` marker is not this alternative: it records one event that no other file can show, only the command that causes it writes it, once, and every other record takes precedence over it (Decision 2).

**Fold an ejected project into `unmanaged`.** The first draft proposed this, because after `eject` nothing recorded that Calavera had managed the project. The owner chose a separate phase with a marker (owner decision 1), so the doctors can name `eject` and its remedies.

**Read a recipe and a lock without a state as `composed`.** A recipe without a state looks like a project before its first `apply`. For a recipe and a lock that `eject --yes` left, this was rejected because the doctors would then tell the person to run `apply` on a project they asked to leave Calavera (owner decision 9).

**Let each command derive its own phase from shared helpers.** This keeps the commands independent, but each command would combine the helpers its own way, and the opposite answers in "Where the commands disagree" came from exactly that. One function that returns both the phase and each item's condition leaves nothing to combine.

**Make the phase alone decide the exit status.** For example, `drifted` fails and every other phase passes. This was rejected because the owner's decisions are per item: a deselected lock entry whose files were deleted passes (#1111), while an edited selected artifact fails, and both can occur in the same `drifted` project. The phase sets the wording and the expected items; each item's condition sets its level.

**Require equal exit statuses from the two doctors.** This would make `artifacts doctor` report managed files, wiring, and the recipe refusals, so it would become a second `doctor`. The owner chose agreement per artifact and per phase instead, with each exit-code difference named (owner decision 10).

## Amendment 1: A Doctor Run That Stops Before It Classifies Prints a Result Without `phase`

- **Date:** 2026-11-23
- **Pull request:** https://github.com/schalkneethling/create-project-calavera/pull/1197 (#1141)

Decision 8 says that a run that stops before it returns a result, on an unreadable record (Decision 7) or a cache-block step that fails to plan or record, "prints an error and no result, so it carries no `phase`". With `--json`, that leaves a CI step or an agent with nothing to parse on standard output. #1141 reported this for `doctor` when it cannot read, parse, or resolve the recipe.

The owner decided on 2026-11-23 that `--json` always prints JSON (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7095375277, https://github.com/schalkneethling/create-project-calavera/issues/1141#issuecomment-7095375796). Decision 8 changes as follows:

- A doctor run that stops before it can classify, because a recipe or a record cannot be read, parsed, or resolved, prints `{ command, ok: false, issues }` and exits 1. The error that stopped it is an issue with the level `error`, after any issue the run found before it, and its message is the same error that Decision 7 describes, naming the file and quoting none of its text.
- That result has no `phase` field, because no phase was derived.
- `phase` is a string in every result that classifies. The sentence "`phase` is always a string in every result" in Decision 8 is narrowed to those results.

The text output reports the same error, after the issues found before it, and the exit status is 1, as Decision 7 already requires.

PR #1197 implements this amendment for `doctor` when the recipe cannot be read, parsed, or resolved, including a recipe `packageManager` that Calavera does not support. Only the records that Decision 7 names, the recipe, the state, and the lock, stop `doctor` before it can classify. PR #1213 (#1206) implements this amendment for the state file.

**Correction, 2026-11-23:** An earlier version of this paragraph also listed unreadable wiring files among the paths that stop `doctor` before it can classify. The owner decided that a recorded wiring file that cannot be read, such as a `.vite-hooks/pre-commit` or `.claude/settings.json` that is a directory, is an error finding instead: `doctor` still classifies, reports every other file, and exits 1 (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7099959255).

## Amendment 2: What the Implementation Settled

- **Date:** 2026-11-25
- **Issue:** https://github.com/schalkneethling/create-project-calavera/issues/1112

The implementation landed in a stack of pull requests: #1300, #1316, #1326, and the pull request that adds this amendment. The owner ruled on the questions the implementation raised on 2026-11-25, recorded on #1112, and four places where this ADR no longer matched `main` were found on 2026-11-24. This amendment records each answer and each correction, so the ADR and the code agree.

### Owner decisions of 2026-11-25

- **A hook with one recorded output out of two.** The recorded output decides the artifact's condition: `missing` or `edited` when that output is, and otherwise `pending`. This settles the first item of "Items for the implementation issues".
- **A pending transaction whose journal cannot be read.** The phase stays `pending-transaction`, and the list of files a rollback would replace is null. This settles the fourth item of "Items for the implementation issues".
- **A file that exists and cannot be read.** An artifact output that exists, has a state record, and cannot be read, or a managed file that exists and cannot be read, such as a folder where a file belongs, gets a new condition, `unreadable`. Its reason names the path and the error code and quotes no file text. After `apply`, it drifts the project, like `missing` and `edited`. Both doctors report an unreadable artifact as an error, because `apply` stops on it, and `doctor` reports an unreadable managed file as an error for the same reason. `artifacts doctor` does not report managed files.
- **A recipe whose managed files cannot be planned.** No managed file is classified, and both doctors report the plan problem as an error, so a phase of `applied` never hides a recipe that `apply` refuses. The problem names the step that failed and the error's code or class, never the recipe's text.
- **After one formatter refusal.** Only the refused file is `not-checked`, and the other files are still compared. A formatter that cannot load makes every file that needs it `not-checked`. This settles the fifth item of "Items for the implementation issues".
- **A formatter failure while `--check-updates` would record the cache block.** `artifacts status --check-updates` reports the failure as a note, writes no block, and exits 0. `artifacts doctor --check-updates` reports it as an error and exits 1. Both resolve packages through a temporary cache. This settles the sixth item of "Items for the implementation issues".

### Corrections found on 2026-11-24

- **The MCP status tool's pending-transaction answer.** The tool returns a successful result with `phase: "pending-transaction"`, `rollbackFiles`, and `remedy`, as the owner decided on PR #1184. Only the two doctors report the phase as an error. The Decision 6 row "An artifact operation stopped before its rollback" reads that way.
- **The legacy-entry refusal.** `doctor` also keeps `apply`'s refusal of a legacy entry that selects an artifact with wiring or inputs (#1140), as an error with the `artifacts migrate` remedy. It joins the list of `doctor`'s other checks in Decision 4.
- **What stops `doctor` before it classifies.** Only a recipe, a state, or a lock that cannot be read, parsed, or resolved stops it, as Amendment 1 says, and so does a recipe `packageManager` that Calavera does not support. A `package.json` that cannot be parsed, which `doctor` reads in a workspace member to name `apply`'s package manager, is an error finding, and `doctor` goes on to classify. `doctor`'s own checks run no Git command, and a missing `git` that the integration inputs need is the plan problem above. Any other error, such as a programming error, still stops `doctor` with an error issue and no `phase`.
- **The listing check.** `doctor`'s text output prints the phase line first, then its issues under the headings "Project:", "Recipe:", "Managed files:", "Artifacts:", and "Records:", and the verdict last. The wiring findings print under their artifact's line in "Artifacts:", without the artifact's ID, and an artifact with wiring findings but no line of its own gets a line that names it. Each managed file and artifact `doctor` reports is therefore named once, so the release rehearsal's listing check (`listingViolations`) passes on its output. Two exceptions remain, and #1331 tracks both: the legacy-entry refusal under "Recipe:" and the Git-hook refusal from a workspace member under "Project:" name their artifact in `apply`'s words, so an artifact they name is printed more than once, its own line under "Artifacts:" included. The drifted phase line does not point to other output, as the `artifacts` commands' line does, because `doctor` lists every drifted item itself. In `composed`, the phase line does not name the pending managed files, as Decision 4 described. Each one has its own warning under "Managed files:" instead. A managed file or artifact whose condition `doctor` does not report, such as `current`, is not printed. As in `artifacts doctor`, a deselected artifact is reported only when it has a problem.

### The checks `doctor` names

Decision 5 left the names of the checks to the implementation. Each issue in `doctor --json` carries one of these values in `check`:

| `check`              | What it reports                                                                                                                           | `artifacts doctor` reports it too |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| `phase`              | The phase line                                                                                                                            | Yes                               |
| `project`            | A missing `package.json`                                                                                                                  | No                                |
| `recipe`             | The removed-profile, removed-toolchain, and unknown-integration warnings, and the legacy-entry refusal                                    | No                                |
| `repository-root`    | The root-only and Git-hook refusals, and a `package.json` that cannot be parsed there                                                     | No                                |
| `managed-file`       | Each managed file's condition, and the missing Varlock schema                                                                             | No                                |
| `managed-file-check` | The formatter failures and the plan problem of the managed-file classification                                                            | Yes                               |
| `artifact`           | Each artifact's condition; each issue names its `artifact`                                                                                | Yes                               |
| `wiring`             | The recorded wiring, in the words `doctor` already used, with the remedies; each issue names its `artifact` and a `detail` without the ID | No                                |
| `marker`             | A note about an edited or broken `ejected` block                                                                                          | No                                |
| `records`            | A record that stopped `doctor` before it classified                                                                                       | Yes                               |

The text verdict names each check that failed and then, in a sentence of its own, the ones that `artifacts doctor` does not make, in the order of each check's first error, such as "Calavera doctor found 2 errors: a managed file's condition and an artifact's condition. artifacts doctor does not report a managed file's condition."

The headings match the groups of the `apply` summary. #1315, which adds headings to `artifacts status` and `artifacts doctor`, is to use "Artifacts:" for their artifact lines too, so the reports share their heading names.

## Amendment 3: The Per-File Notes for Unrecorded Artifact Outputs

- **Date:** 2026-11-26
- **Issue:** https://github.com/schalkneethling/create-project-calavera/issues/1112

The last pull request of the stack implements the per-file notes of Decision 3 and the `unrecordedFiles` field of Decision 8. It settles four points that the decisions leave to the implementation.

- **Each element carries its note.** Each element of `unrecordedFiles` is `{ path, comparedVersion, matches, notCompared, reason }`. Decision 8 names the first three fields. `notCompared` says why Calavera could not compare the file, in its own words with the error code when there is one, or is null when it compared it, so distinct failures stay distinguishable without quoting an error's message. `reason` is the note in Calavera's words, as `condition.reason` is for the condition, so a reader of `--json`, and the text output that has no recipe to build commands from, both get the same words. `doctor`'s issue for the note also names the artifact in `message`, and gives `detail` without it, as its wiring findings do.
- **The channel and the version.** The comparison resolves `latest` offline, the channel an unlocked selection installs from, and `comparedVersion` is the version the cached metadata names for it. A match gets the note that `apply` resolves the current version online. A file whose package the cache cannot supply has `comparedVersion` and `matches` null and gets the conditional note, whose remedy adds `apply --dry-run`. A file that cannot be read, such as a folder where a file belongs, keeps the `comparedVersion` it would have been compared with, has `matches` null, and gets a note that says the file cannot be read, because the cache did supply the package.
- **What stops the comparison.** The comparison only adds notes, so none of its steps may change a verdict or an exit status. A cache miss and a registry or file error, which carry a code, mean that the cache cannot supply the package, and `notCompared` names the code. A package Calavera refuses, such as one whose identity does not match its metadata, gets its own `notCompared`, so a tampered cache does not read like a cache miss. A cache that cannot be copied leaves every file uncompared, with the code. A programming error, a `TypeError` or `ReferenceError` without a code, stops the run, so it is not mistaken for a cache miss. The cache is copied with its links followed, so a linked cache, or a link inside it, never makes the lookup read the project's cache. The copy is removed in every case; when that removal fails, the comparison is kept, and the process removes the copy when it exits (#1081).
- **The MCP status tool.** The read-only `artifact_status` tool carries the same field and compares the same way. It copies the cache into the operating system's temporary folder, outside the project, so it still writes nothing into the project, and it runs no project code.

Two decisions of 2026-11-26, recorded on #1112 and implemented in #1334, settle the `eject --yes` item of "Items for the implementation issues":

- **The cache block stays with the state.** When `eject --yes` keeps `.calavera/state.json` because the base skill or the `artifact-cache` block was edited, it also keeps the `artifact-cache` block, as it already does for a linked cache (ADR-0017, Amendment 2). The project stays a consistent `applied` project, so `--check-updates` has nothing to write back (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7176837197).
- **The `ejected` block comes before the last record.** In a project without a state file, `eject --yes` writes the `ejected` block before it deletes the last remaining Calavera record, the lock or, without a lock, the recipe, and deletes that record last. A failed write or a stop therefore leaves a record, and the next run plans the block again. ADR-0017, Amendment 5 records this in its note of 2026-11-26. The decision was made under the owner's instruction of that evening to decide unambiguous cases with the most consistent and secure answer, and it is open to the owner's review (https://github.com/schalkneethling/create-project-calavera/issues/1112#issuecomment-7176880623).

One item stays open after the stack, because its code belongs to other work: an edited `.gitignore` block without a record, which stops `apply` but gets no note, belongs to the `.gitignore` block code.
