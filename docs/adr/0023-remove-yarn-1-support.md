# ADR-0023: Remove Yarn 1 (Classic) Support

- **Status:** Accepted (2026-11-25, Schalk Neethling, in #1308)
- **Date:** 2026-11-25
- **Issue:** https://github.com/schalkneethling/create-project-calavera/issues/1175
- **Decides:** Calavera stops supporting Yarn 1 (Yarn Classic) as the package manager that starts it. When Yarn 1 starts the CLI or the MCP server, it stops with one message that names Yarn 2 or later, npm, pnpm, and Bun as the remedy, and exits 1: the CLI right after it parses its arguments, so `--json` still gets a JSON result, and the MCP server before it starts. Nothing runs before that message: no prompt, no registry request, no version notice, and no project file read, except that under the Bun runtime the detection reads the `.env` files that Bun may have loaded, without printing anything of its own. Calavera recognizes Yarn 1 from the two variables a package manager sets for the process it starts, `npm_execpath` and `npm_config_user_agent`, with the rule `detectLauncher` already uses, so repository content under npm, pnpm, or Yarn 2 or later cannot make Calavera stop; under the Bun runtime, the variables count only when no `.env` file that Bun may have loaded defines them. Every Yarn 1-specific path goes: the `--new` fallback to npm under Yarn 1, the Yarn failure hint and the two `yarn` reads behind it, the `-W` flag that `eject` reports for a Yarn 1 workspace root, the "Yarn 1 counts as npm" rule of the registry settings loader, and their tests, docs, and changeset text. No flag, setting, or deprecated path brings Yarn 1 support back. Yarn 2 and later keep working unchanged. The owner decided the removal on 2026-11-22 (https://github.com/schalkneethling/create-project-calavera/issues/1064, owner comment of that date) and answered the eight open questions of the first draft on 2026-11-25 (https://github.com/schalkneethling/create-project-calavera/issues/1175#issuecomment-7162646403), each as the draft recommended; each answer is recorded in the decision it belongs to and under "Owner decisions". This document changes no code. The issue's scope puts the ADR and the removal in one issue; this ADR was proposed on its own first so that the owner could answer its open questions before the code changes, and the implementation pull request closes #1175.

## Context

The owner decided on 2026-11-22, after the third review round of PR #1161, that Calavera drops Yarn 1 support, for two reasons. First, Yarn 4 is current, and the Yarn 1 repository says that it is "mostly kept for historical purposes" and "will only accept security fixes" (`README.md` on the default branch of yarnpkg/yarn, read on 2026-11-25; the latest Yarn 1 release, v1.22.22, was published on 2024-03-09). Second, under Yarn 1, a repository's `.yarnrc` can set any environment variable for the process Yarn starts, so Calavera cannot defend its registry and proxy settings against a hostile repository there (#1064).

Since that decision, #1185 removed registry credentials (ADR-0021), and #1186 made the registry settings loader refuse to let repository content choose which package manager's settings it reads. #1186 left Yarn 1 as it was, as the comment on `loadNpmRegistryOptions` says: "Yarn 1 counts as npm here, unchanged by #1064; #1175 removes its support."

The repository rules call for one pull request and one ADR per removal, with no deprecated paths, flags, or legacy modes left behind. This ADR follows the structure of ADR-0021 and ADR-0022.

## What Yarn 1 and Yarn 4 do

Each claim below was read from the published source on 2026-11-25: yarnpkg/yarn at tag `v1.22.22`, and yarnpkg/berry at tag `@yarnpkg/cli/4.19.0`, the latest Yarn 4 release on that date. The Yarn 1 `dlx` behavior comes from the probes that ADR-0010 recorded on 2026-11-13 and 2026-11-15.

**Yarn 1 builds the environment of every process it starts in `makeEnv`** (`src/util/execute-lifecycle-script.js`). `yarn run`, a package bin, and `yarn create` all go through it. It works in this order:

```js
const env = { NODE: process.execPath, INIT_CWD: process.cwd(), ...process.env };
const customEnv = config.getOption("env"); // step 1: the .yarnrc `env` table
if (customEnv && typeof customEnv === "object") Object.assign(env, customEnv);
env.npm_execpath = env.npm_execpath || process.mainModule.filename; // step 2
// step 3: every Yarn and npm configuration key becomes npm_config_<key>
for (const [key, val] of cleaned) env[`npm_config_${cleanKey}`] = val;
```

Three facts follow, and each matters for detection (Decision 2):

- At step 1, the `env` table of any `.yarnrc` that Yarn 1 reads, including one in the project folder or its ancestors (`src/registries/yarn-registry.js`), overwrites any inherited variable, such as `HOME` or `HTTPS_PROXY`. This is the reason #1064 gives for the removal.
- At step 2, `npm_execpath` keeps a value that is already set, from the caller or from the `env` table, so a repository can choose it.
- At step 3, `npm_config_user_agent` comes from the `user-agent` configuration key, whose default is `yarn/<version> npm/? node/<version> <platform> <arch>` (`DEFAULTS` in `src/registries/yarn-registry.js`). Yarn 1 reads that key from its own configuration (`getOption` in `src/config.js`), so a project `.yarnrc` that sets `user-agent` replaces it. Step 3 runs after step 1, so the `env` table itself cannot set this variable, but a `user-agent` key in a `.yarnrc` can.

Step 3 also exports every other configuration key, such as `registry` and `https-proxy`, as an `npm_config_*` variable, and `makeEnv` sets `npm_lifecycle_event`. That is why Calavera's loader treats a Yarn 1 run as one that npm started (`startedByNpm` in `packages/artifact-core/src/npm-config.js`).

**Yarn 1 has no `dlx` command.** It treats `dlx` as a script name and exits 1 with `Couldn't find a package.json file` (ADR-0010, 2026-11-13 amendment and the #740 probe). Its `yarn create` command runs `yarn global add` for the package, which means a registry request and a change to the person's global Yarn packages, and then starts the bin from the global folder through a shell (`src/cli/commands/create.js`). So `yarn create project-calavera` is the way that Yarn 1 starts Calavera without a project dependency; ADR-0010's #740 probe found that only the form without a version works, because a versioned specifier names no bin. A project that lists `create-project-calavera` as a dependency can also start it with `yarn create-project-calavera` or from a script.

**Yarn 4 sets both variables itself, after it copies the environment it starts from.** `makeScriptEnv` (`packages/yarnpkg-core/sources/scriptUtils.ts`) sets `npm_execpath` to the `yarn` shim in its own temporary bin folder and `npm_config_user_agent` to `yarn/<version> npm/? node/<version> <platform> <arch>`. #1186 established that Yarn 4 applies a `.env.yarn` before it sets them, so a repository cannot change them there. A Yarn plugin's `setupScriptEnvironment` hook runs later and could change them, but a plugin is code that the repository already runs.

**Bun's script runner does not load the project's `.env` files.** Read at tag `bun-v1.4.5` of oven-sh/bun. `bun run` and `bunx` set up a run's environment in `configure_env_for_run_impl` (`src/runtime/cli/run_command.rs`), which calls `run_env_loader(true)` with the comment "Always skip default .env files for package.json script runner (the script's own bun instance loads .env)" (lines 730 to 732). The same function calls `seed_script_env` (line 747; `src/install/lib.rs`, lines 836 to 875), which sets `npm_config_user_agent` to `bun/<version> npm/? node/<version> <platform> <arch>` with `put_default`, so a value that the caller already set stays (line 850), and sets `npm_execpath` to Bun's own executable only when it is unset (lines 868 to 873). `path_for_run` (`run_command.rs`, lines 2059 to 2071) replaces `npm_execpath` with Bun's executable when Bun stands in for a missing Node.js. So when `bunx` without `--bun` starts the bin's `#!/usr/bin/env node` line, Calavera runs on Node.js with no value from the project's `.env` files, and the only Bun process that loads them is a Bun runtime that runs Calavera itself.

**Vite+ supports Yarn Classic.** Its package management guide lists Yarn Classic beside Yarn Modern for each command: `vp dlx` falls back to `npx --yes` for Yarn Classic, and `vp add` runs `yarn add` (`docs/guide/package-management/dlx.md` and `add.md` in voidzero-dev/vite-plus at commit `45aa7009e76d`). The litmus test section returns to this.

## Decision

### 1. What a Yarn 1 user sees

When Yarn 1 starts the CLI, the run stops with one message and exit code 1. For a run started through Yarn 1.22.22, the message is:

```text
create-project-calavera does not support Yarn 1.22.22. Use Yarn 2 or later (yarn dlx create-project-calavera), npm (npx --package create-project-calavera create-project-calavera), pnpm (pnpm dlx create-project-calavera), or Bun (bunx create-project-calavera).
```

The message names the Yarn version from the user agent and one command for each supported package manager, each of which runs as printed. A Yarn whose user agent has no readable version is not Yarn 1 under Decision 2, so the message always has a version.

The CLI checks in `runCli`, right after `parseArgs` succeeds and before `startVersionCheck`, and reports the stop through `printStop`, the path that argument errors already take. Without `--json`, the message goes to standard error as plain text. With `--json`, the run prints `{ command, ok: false, issues }` on standard output with the message as an `error` issue, as the pending changesets for #1218 and #1227 promise for every error of a `--json` run (owner decision 6). An argument error still comes first, because parsing reads only the arguments. The check covers every command, including `--help` and `--version`, for the same reason as the Node.js check in `startOnSupportedNode`: one rule for an unsupported environment is easier to state, document, and test than a list of exemptions.

The MCP server checks at the start of `runMcpEntrypoint`, before it writes its start line and before it calls `startServer`. It writes one line to standard error and sets exit code 1 through its `setExitCode` seam, without throwing, so the host's log shows the line and no stack trace. The line gives the commands in the form an MCP host's configuration needs, because the package and the bin have different names (`createPackageRunnerCommand`):

```text
create-project-calavera-mcp does not support Yarn 1.22.22. Use Yarn 2 or later (yarn dlx --package create-project-calavera create-project-calavera-mcp), npm (npx --package create-project-calavera create-project-calavera-mcp), pnpm (pnpm dlx --package create-project-calavera create-project-calavera-mcp), or Bun (bunx --package create-project-calavera create-project-calavera-mcp).
```

Stopping at these two points means that the stop cannot leave a partial result: no prompt has been answered, no project file has been written, and the version notice of ADR-0019 has not asked the registry anything. No project file has been read either, with one exception, under the Bun runtime, which Decision 2 describes.

The MCP stop is not a breaking change to a public tool under ADR-0018, Decision 6. That decision governs removing, renaming, or reshaping an MCP or WebMCP tool, and this stop changes no tool, input, or output; it ends the server's process under a package manager that Calavera no longer supports. Its line names the replacement commands, as ADR-0018's Decision 6 asks a changeset to do for a tool that changes. The bins themselves do not change. `startOnSupportedNode` prints `inspect(error)` for anything its `start` callback throws, so a check there would print a stack trace, could not honor `--json`, and would have to load artifact-core from a module that must stay loadable on unsupported Node.js versions.

An error rather than a warning is the issue's default ("Running Calavera under Yarn 1 should fail early"). A warning would leave Calavera running under the settings that #1064 found it cannot defend.

### 2. How Calavera recognizes Yarn 1

Calavera recognizes Yarn 1 only from the two variables a package manager sets for the process it starts, with the precedence that `detectLauncher` uses since #1186. It treats the run as a Yarn 1 run when all three conditions hold:

1. `npm_execpath` does not name npm or pnpm: its file name does not match `NPM_OR_PNPM_EXECPATH` in `launcher-config.js`.
2. `npm_config_user_agent` starts with `yarn/<major>.`, and `<major>` is 0 or 1.
3. Under the Bun runtime, no `.env` file that Bun may have loaded defines either variable. "The Bun runtime" means what it means in the loader: `runtime === "bun"`, which `loadNpmRegistryOptions` derives from `process.versions.bun`. This is the check that the loader already makes for the launcher variables (#1186, `launcherFromFile` in `npm-config.js`), so the implementation moves it into a function that both use (owner decision 8). Under Node.js, condition 3 does not apply, because no Bun process loaded a `.env` file into Calavera's environment ("What Yarn 1 and Yarn 4 do", Bun).

Condition 3 is the one exception to "no project file is read before the stop". Under the Bun runtime, the detection reads the files of the chains that `bunEnvironmentFileChains` (`environment-files.js`) names: `.env`, `.env.<mode>`, `.env.local` (not in the `test` mode), and `.env.<mode>.local` in the starting folder, and each file that Bun's own `--env-file` option names. It reads nothing else, and it prints nothing of its own: a read or parse problem produces no warning before the stop, because the detection passes a list of warnings that it discards, and the loader reports such problems later, in its own run. When one of those files exists but cannot be read, the detection cannot rule out that it defines the launcher variables, so the variables count as possibly from a `.env` file, and Calavera does not stop on them. This leans toward running, because a wrong stop would let repository content block a supported package manager, which the #1186 decisions rule out.

One function in `packages/artifact-core/src/launcher-config.js`, beside `detectLauncher`, holds this rule and returns the Yarn version or nothing. `runCli`, `runMcpEntrypoint`, and the registry settings loader (Decision 5) call it, so the rule exists once. artifact-core exports only `.` (`catalog.js`) and `./registry` today, so the function is re-exported from `./registry`, which the CLI already imports, rather than through a new public subpath (owner decision 7).

The owner decided on #1186 that repository content cannot choose which package manager's settings Calavera reads. This rule keeps that promise in the direction that matters, so that repository content cannot make Calavera stop under a supported package manager:

| What started Calavera                                              | Can repository content make the stop fire?                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| npm (`npx`, `npm exec`, `npm create`, `npm run`)                   | No. A project `.npmrc` `user-agent=yarn/1.22.22` changes the user agent, but npm sets `npm_execpath` to `npm-cli.js`, so condition 1 fails.                                                                                                                                                                                                                                                                                                                                       |
| pnpm                                                               | No. pnpm's `userAgent` setting changes the user agent, but `npm_execpath` names pnpm.                                                                                                                                                                                                                                                                                                                                                                                             |
| Yarn 2 or later                                                    | No. Yarn sets both variables after it applies `.env.yarn`.                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Bun (`bun run`, `bunx`, or a direct run such as `bun calavera.js`) | No. Under the Bun runtime, a project `.env` file is the only repository content that can set the variables, and a variable that such a file defines does not count (condition 3). Under `bunx` without `--bun`, Calavera runs on Node.js, and Bun's script runner loads no `.env` file, sets the user agent to `bun/…` unless the caller set one, and sets `npm_execpath` to Bun's executable unless the caller set one, so condition 2 fails unless the caller itself is Yarn 1. |
| Node.js with no package manager                                    | No repository content sets the process environment. The caller's own variables decide, as they do for `detectLauncher`.                                                                                                                                                                                                                                                                                                                                                           |

Under Yarn 1 itself, the stop is not a security boundary, and the docs must not call it one. A repository's `.yarnrc` can set `npm_execpath` through its `env` table and `npm_config_user_agent` through its `user-agent` key (step 2 and step 3 in "What Yarn 1 and Yarn 4 do"), so a hostile repository can make a Yarn 1 run look like npm or Yarn 4, and Calavera then runs. That is the reason for the removal, not a gap it can close: Yarn 1 is unsupported because no check of the environment holds under it. The stop serves the person who starts Calavera through Yarn 1 in good faith, who gets one clear message instead of a runner that cannot start or settings that do not apply.

When Yarn 1 runs from inside an npm or pnpm script, it keeps the `npm_execpath` that npm or pnpm set (step 2), so Calavera sees npm or pnpm and does not stop. `detectLauncher` reads the npm settings in that case, as it does today. The values it compares are the ones Yarn 1 passed on at step 3, which come from Yarn 1's own configuration, including a project `.yarnrc`, so this is the same case as the hostile repository above, not npm's own settings.

### 3. What each command does under Yarn 1

None of the commands below keeps Yarn 1-specific code. Under a Yarn 1 launcher, each one meets the stop of Decision 1 before it starts.

- **`--new`.** The fallback to npm under Yarn 1 goes as a supported path, because a Yarn 1 launcher never reaches `newProject`. `launchingPackageManager` keeps its rule that Yarn counts at major version 2 or later, because a `yarn/1` user agent can still reach it: under npm, a project `.npmrc` `user-agent=yarn/1.22.22` makes condition 1 fail, so the run continues, and the runner must then be npm, which did start Calavera. Its comment says that, and says that a user agent without a readable version did not come from Yarn, which sets its own version, so it is treated as an unrecognized launcher. The error for a runner that cannot start says "the package manager that started Calavera, or npm when Calavera does not recognize that package manager". The Yarn failure hint and both reads behind it go (owner decision 1). After the removal, a failed `yarn dlx` gets the same message as a failed `pnpm dlx`: the runner, its exit code, the working folder, and the partial-scaffold warning. That a project file can make `launchingPackageManager` pick the Yarn or Bun runner under npm is a separate, existing gap, which this ADR does not change.
- **`--init` and `apply`.** They stop under a Yarn 1 launcher. Under other launchers, a project that uses Yarn 1 is treated as a Yarn project, as today, so the commands Calavera prints and writes for it are the Yarn 2 or later commands, such as `yarn dlx --package create-project-calavera@<version> create-project-calavera-mcp` in the MCP configuration (`createMcpLaunchCommand`). A project's `packageManager` or `devEngines.packageManager` pin of Yarn 1 does not stop them, because only the package manager that started Calavera decides (owner decision 2).
- **`eject`.** It stops under a Yarn 1 launcher. Under other launchers, `devDependencyRemoveCommand` loses its `yarnClassicWorkspaceRoot` option, and `projectYarnMajor` goes, so the reported command for a Yarn workspace root is `yarn remove create-project-calavera`, or `vp remove create-project-calavera` under Vite+, with no `-W` (owner decision 2). `eject` never stops because of a project pin, so removing Calavera stays possible.
- **The artifact commands.** They stop under a Yarn 1 launcher, before the loader reads any setting.
- **The MCP server.** `create-project-calavera-mcp` stops under a Yarn 1 launcher with the line of Decision 1, before it opens the MCP transport, so the host reports that the server exited, with that line in its log. No `calavera` MCP entry that Calavera writes starts the server through Yarn 1, because Calavera writes `yarn dlx`, which Yarn 1 does not have.
- **The version notice.** It never runs under Yarn 1, because the stop comes before `startVersionCheck` (ADR-0019 is otherwise unchanged).

### 4. The `--new` documentation and confirmation

The confirmation and `--dry-run` output of `--new` need no change: they describe how Vite+ chooses the package manager and never mention Yarn 1. The README and `docs/agent-first-calavera-workflow.md` replace the Yarn 1 text with one statement next to the Yarn commands: "Calavera requires Yarn 2 or later. Under Yarn 1, Calavera stops and names the commands to use instead." The advice to Yarn 1 users to run `npx --package create-project-calavera create-project-calavera` lives in that stop message, not in a separate paragraph.

### 5. The registry settings loader

`loadNpmRegistryOptions` calls the function of Decision 2 before it reads any configuration file and, under Yarn 1, throws an error with this message, which names no bin, because artifact-core does not know which bin called it (owner decision 3):

```text
Calavera does not support Yarn 1.22.22. Use Yarn 2 or later, npm, pnpm, or Bun.
```

The CLI never reaches this, because `runCli` and `runMcpEntrypoint` stop first. The throw protects a direct caller of the published `@schalkneethling/calavera-artifact-core` package, which would otherwise get the npm settings under Yarn 1 with no sign that they are not Yarn's. `detectLauncher` loses its Yarn 1 comment and its `yarn/1` test row, and the loader's test asserts the stop instead.

The comment on `loadNpmRegistryOptions` says that Yarn 1 is not supported and names the stop, in place of "Yarn 1 counts as npm here". The comparison with exported `npm_config_*` values does not change. It applies under npm, and its comment no longer needs to explain why it also caught Yarn 1.

### 6. Tests

The implementation writes these tests first and sees each one fail for the right reason. Every test of the stop sets both `npm_execpath` and `npm_config_user_agent` explicitly, because the CLI tests start Calavera with an environment built from the test runner's, which carries pnpm's `npm_execpath`. A test that set only the user agent would never reach the stop and would pass as an npm run.

- The CLI stop: a run with `npm_config_user_agent` set to `yarn/1.22.22 npm/? node/v24.3.0 darwin arm64` and `npm_execpath` set to a Yarn 1 path exits 1, prints exactly the message of Decision 1 on standard error and nothing on standard output, and makes no registry request and writes nothing, which a test registry and a temporary project prove. The same run with `--json` prints the JSON error result on standard output. A version 0 user agent stops too.
- The MCP stop: `runMcpEntrypoint` under the same environment writes the line of Decision 1, sets exit code 1, and never calls `startServer`.
- The precedence of Decision 2: the same user agent with `npm_execpath` naming `npm-cli.js`, and with each pnpm form that `NPM_OR_PNPM_EXECPATH` accepts, does not stop; nor does a Yarn 2, Yarn 4, or unreadable Yarn version; nor, under the Bun runtime, a user agent that one of the `.env` files of condition 3 defines; nor, under the Bun runtime, a `.env` file that exists but cannot be read, such as a folder named `.env`. Each test fails when its condition is removed from the rule.
- The Bun carve-out: under the Bun runtime, a stopping run prints only the message of Decision 1, even when one of the `.env` files cannot be read or parsed, which proves that no warning reaches the output before the stop. A test with a file outside the chains of condition 3, such as an unreadable `.yarnrc.yml`, proves that the detection reads nothing else. Under Node.js, the detection reads no `.env` file at all, which the same unreadable `.env` proves by stopping.
- The loader: `loadNpmRegistryOptions` throws under the Yarn 1 environment with the message of Decision 5, and reads no configuration file, which a fixture whose files would otherwise fail to parse proves.
- `--new` under Yarn 2 or later and every other launcher keeps its current tests. A `yarn dlx` that exits non-zero gets no Yarn hint and starts no `yarn` read, which the kept test `--new adds no Yarn hint when yarn dlx fails under Yarn 2 or later` asserts.
- `eject` at a Yarn workspace root reports `yarn remove create-project-calavera` and `vp remove create-project-calavera`, with no `-W`, whatever the project pins.

The tests listed under "What exists today" are removed or kept as that list says. The C8 safety-property tests need no change, and the implementation must not modify them.

### 7. What this amends

The implementation adds a dated note, not a rewrite, to each of these, as ADR-0022 did for its own changes:

- **ADR-0010, amendment "The Launching Package Manager Chooses the Runner".** A note under its Decision says that Yarn 1 no longer falls back to npm, because Calavera stops under Yarn 1 (ADR-0023), and that the bullet "An explicit `--package-manager yarn` under Yarn 1 still fails at `yarn dlx`" now applies to a Yarn 1 on the `PATH` with no hint.
- **ADR-0010, section "Probe and Change for the pnpm and Yarn Runners (2026-11-15, #740)".** A note says that "The Yarn row therefore keeps the Yarn 1 behavior that #911 and #909 were written against" and the closing paragraph about the Yarn failure hint describe code that ADR-0023 removed.
- **`docs/architecture/versioned-artifacts.md`.** The "Yarn 2 or later and Bun" bullet replaces "Yarn 1 counts as npm, as before #1064; #1175 removes Yarn 1 support." with: under Yarn 1, Calavera stops before it reads any setting, and the stop is not a security boundary, because a repository's `.yarnrc` can change both variables that Calavera reads. This is a current-state document, so the change goes into the text, not into a note.

ADR-0017, ADR-0019, ADR-0021, and ADR-0022 do not mention Yarn 1 and need no note. `docs/cross-repo/sequencing-map.md` already names Yarn 2 or later in exit-condition item 1, so it needs no change beyond the wave record the orchestrator writes.

### 8. How C8 holds

The project brief's safety invariants (C8, `docs/evolution-brief.md`) hold. Only the CLI writes into projects, and the stop writes nothing: it runs before any command starts. `dry_run_apply` stays the approval boundary, because the stop runs before any dry run and changes nothing after one. Local edits are preserved, because the stop reads and writes no project file, and the `eject` change alters only a command that `eject` reports and never runs (ADR-0017, Decision 4). Nothing is written to `package.json`. No conflict is introduced, so the hard-stop and migration-decision rules are unchanged. The C8 safety-property tests need no change.

## Litmus test

The litmus test asks whether Calavera fights with or reimplements something that Vite or Vite+ does well. It is not what triggers this removal, and the issue's litmus line ("Vite+ and its `vp create` already support current Yarn") is true but leaves out that Vite+ also supports Yarn Classic ("What Yarn 1 and Yarn 4 do"). Calavera does not remove Yarn 1 because Vite+ handles it better. It removes Yarn 1 because Calavera cannot keep its own promise about registry and proxy settings under it (#1064).

The removal does not conflict with the litmus test, because it does not take anything from Vite+: a Yarn 1 project that Vite+ manages keeps every `vp` command. What changes is that Calavera refuses to run when Yarn 1 starts it, and prints the Yarn 2 or later form of the commands it writes for a Yarn project. Calavera still runs in a Yarn 1 project when another launcher starts it, including `vp dlx`, which falls back to `npx --yes` in a Yarn Classic project.

## Consequences

A person who starts Calavera through Yarn 1, for example with `yarn create project-calavera --init`, gets the message of Decision 1 and exit code 1 instead of a run, after Yarn 1 has already installed `create-project-calavera` into the global Yarn packages. That global bin keeps working when the person starts it directly, outside Yarn. Until now, `--init`, `apply`, and the artifact commands worked under Yarn 1 with the npm settings, and `--new` fell back to an npm runner, so this is a working setup that stops working. Each remedy in the message runs as printed.

A person who starts Calavera another way in a project that uses Yarn 1 gets Yarn 2 or later commands in what Calavera writes and prints (Decision 3). Under Corepack with no `packageManager` pin, `yarn dlx` runs Corepack's own Yarn 2 or later, as ADR-0010's #740 probe found, so the MCP entry still starts. With a Yarn 1 pin, or a Yarn 1 installed without Corepack, it fails.

The code shrinks by `yarnFailureHint`, its two reads and their seams, `projectYarnMajor`, and the `yarnClassicWorkspaceRoot` option, and the tests shrink by the 24 Yarn hint test definitions in `new-flag.test.mjs`, several of them run once per table row. The new code is one function of about ten lines, the shared `.env` check that condition 3 moves out of the loader, the calls in `runCli`, `runMcpEntrypoint`, and the loader, and their tests.

**Version bump: major** (owner decision 4). The changeset for both `create-project-calavera` and `@schalkneethling/calavera-artifact-core` says that Calavera requires Yarn 2 or later and quotes the stop line. #1185, #1186, and #1204 already merged major changesets, so the next `create-project-calavera` release is 7.0.0, and the next `@schalkneethling/calavera-artifact-core` release, from 0.6.0, is 1.0.0. This bump changes neither version. The artifact-core changeset also names the new export of Decision 2.

**Pending changesets** (owner decision 5). `.changeset/yarn-hint-corepack.md` and `.changeset/999-yarn-hint-no-auto-pin.md` describe a change that this removal takes back before any release ships it, so the implementation deletes them. `.changeset/new-runner-follows-launcher.md`, `.changeset/1109-new-vite-plus-follows-runner.md`, and `.changeset/1064-registry-proxy-yarn-bun.md` lose their Yarn 1 clauses. Their other content still ships.

## Owner decisions

The owner answered the eight open questions of the first draft on 2026-11-25 in https://github.com/schalkneethling/create-project-calavera/issues/1175#issuecomment-7162646403, and accepted every recommendation. The reasons below come from the first draft's recommendations.

1. **The `--new` Yarn hint: removed completely.** The hint and the two `yarn` commands behind it go, with no fixed sentence such as "yarn dlx needs Yarn 2 or later" in their place. Reason: that sentence is Yarn 1 advice that is wrong for every Yarn 2 or later failure, which is why #936 added the version read, and the README states the requirement next to the Yarn commands. Decision 3 applies this.
2. **A project that pins Yarn 1: only the launcher decides.** `--init` and `apply` do not stop because a project's `packageManager` or `devEngines.packageManager` pins Yarn 1, and `eject` never stops because of a pin. Reason: a pin is repository content, the #1186 decisions keep repository content from choosing the package manager, and most Yarn 1 projects have no pin, because Yarn 1 does not write one, so a pin check would catch few of them while adding Yarn 1 code back. The cost is that a pinned Yarn 1 project gets Yarn 2 or later commands from `--init` and an `eject` command without `-W`, which fail there. Decision 3 and the Consequences apply this.
3. **The loader under Yarn 1: it throws.** `loadNpmRegistryOptions` throws the error of Decision 5 for a direct caller of `@schalkneethling/calavera-artifact-core`. Reason: reading the npm settings is the "Yarn 1 counts as npm" path that this removal exists to end, and a direct caller would otherwise get settings that a repository's `.yarnrc` can change without any sign. Decision 5 applies this.
4. **Version bump: major, for both packages.** Reason: a Yarn 1 user's working `--init` and `apply` stop working, and ADR-0021 and ADR-0022 chose a major bump for a removal with that effect. The next releases are already 7.0.0 and 1.0.0, so the bump changes neither version. The Consequences apply this.
5. **Pending changesets: two deleted, three edited.** The implementation deletes `.changeset/yarn-hint-corepack.md` and `.changeset/999-yarn-hint-no-auto-pin.md` and removes the Yarn 1 clauses from the three others that the inventory names. Reason: they are unreleased, so they are not records of a past state, and keeping them would make the 7.0.0 notes announce a Yarn 1 hint that the same release removes. The Consequences apply this.
6. **`--json` under Yarn 1: the JSON error result.** Reason: the pending changesets for #1218 and #1227 promise a JSON result for every error of a `--json` run, an agent that runs `apply --json` reads standard output, and, unlike the Node.js check, this check runs after Calavera has parsed its arguments, so `printStop` can report it. Decision 1 applies this.
7. **The rule's export: artifact-core's existing `./registry` entry.** Reason: the CLI already imports it, the loader that also uses the rule is behind it, and a new subpath would add a public entry point for one function. Decision 2 applies this.
8. **Bun: the loader's `.env` check.** Under the Bun runtime, a launcher variable that a `.env` file Bun may have loaded defines does not count, so a repository's `.env` cannot fake a Yarn 1 launcher. Reason: skipping Bun runs altogether would leave a Yarn 1 run on the Bun runtime reading the npm settings, which is the "Yarn 1 counts as npm" path this removal ends, while the `.env` check already exists. Decision 2, condition 3, applies this, together with the carve-out that the independent review of #1308 asked for.

## Alternatives considered

- **Keep Yarn 1 support.** Rejected by the owner's decision of 2026-11-22 (#1064): a repository's `.yarnrc` can set any environment variable under Yarn 1, so Calavera's registry and proxy rules cannot hold there.
- **Warn under Yarn 1 and continue.** Rejected: Calavera would keep running under the settings that #1064 found it cannot defend, and the issue asks for an early failure.
- **Keep the fallback to npm for `--new` under Yarn 1.** Rejected: it is Yarn 1-specific behavior, and the repository rules call for complete removals with no legacy modes. A Yarn 1 user would also get an npm project they did not ask for, which ADR-0010's amendment accepted only because no Yarn 1 runner exists.
- **Recognize Yarn 1 from `npm_config_user_agent` alone.** Rejected: npm exports a project `.npmrc` `user-agent`, and pnpm its `userAgent` setting, so repository content could stop Calavera under npm or pnpm, which the #1186 decisions rule out. Decision 2 uses `npm_execpath` first, as `detectLauncher` does.
- **Recognize Yarn 1 by running `yarn --version`.** Rejected: the `yarn` on the `PATH` is not necessarily the Yarn that started Calavera, Corepack can run another Yarn for the same command (ADR-0010, #740 probe), and running it would start a child process on every run of every command.
- **Recognize Yarn 1 from the project's `yarn.lock` header or `.yarnrc`.** Rejected: both are repository content, and they describe the project, not the program that started Calavera.
- **Put the check in the bins, beside the Node.js check.** Rejected: `startOnSupportedNode` prints a stack trace for anything its callback throws, it cannot honor `--json` because it runs before the arguments are parsed, and the bins would have to load artifact-core early. `runCli` and `runMcpEntrypoint` also cover a program that imports `create-project-calavera`'s `./src/index.js` export and calls `runCli`; one that calls other exports directly skips the stop, as it skips argument parsing.
- **Exempt `--help` and `--version`.** Rejected: the help text is static and would be harmless, but the Node.js check sets the precedent that an unsupported environment stops every command, and one rule is easier to document and test than a list of exemptions.
