# ADR-0005: Remove ESLint Flat Config

- **Status:** Proposed
- **Date:** 2026-09-15
- **Issue:** https://github.com/schalkneethling/create-project-calavera/issues/455
- **Decides:** removal of the JavaScript and TypeScript ESLint flat config component and the eleven entries that include it under C1, applying the `remove` classification recorded for the "Classic profile: ESLint flat config" row and the five rule pack rows of `docs/catalog-audit.md`.

## Context

The `eslint` catalog entry writes `eslint.config.js` through `createESLintConfig`, installs `eslint`, `@eslint/js`, and `globals`, adds `lint` and `lint:fix` scripts, and is the Classic profile default. Eleven entries include it: `typescript-eslint`, `eslint-config-prettier`, `eslint-react`, `eslint-jsx-a11y`, `eslint-import`, `eslint-n`, `eslint-promise`, `eslint-unicorn`, `eslint-sonarjs`, `eslint-vitest`, and `eslint-jest`.

`createESLintConfig` wires only two of those eleven, `typescript-eslint` and `eslint-config-prettier`, into the generated file. The other nine install an npm dependency and change nothing else. Selecting one of these entries has never registered a rule in a generated project, in any release up to 2.6.0, since at least the July 2026 monorepo conversion. This is recorded as bug #450, closed by this removal rather than by a fix.

Applying C1 to the surviving two-entry component does not rescue it. `docs/guide/lint.md:7` presents Oxlint as a fast replacement for ESLint for most frontend projects. `migrate-rules.md:280-286` rewrites a project's `eslint` script to `vp lint` during migration. No `vp create` project contains ESLint. The evidence audit found the same pattern here that closed the Oxlint entries in ADR-0002: a project-level configuration file that Vite+ does not consult, generated by a component Vite+ has already replaced with its own linter. `eslint-unicorn` and `eslint-sonarjs` are not curated pack rows in the catalog schema, but they are inert in the identical way, install-only stubs contributing no configuration, and the audit approved removing them together with the component on 2026-09-14.

CQ1 resolved the non-`vp` path for every JavaScript and TypeScript toolchain component in Increment 1: Calavera offers none of them to a project that has not adopted Vite+, and directs that project to `vp create` or `vp migrate` instead. That resolution scopes this ADR to the JavaScript and TypeScript ESLint host only. It does not reach `@eslint/css`, which css-evolve needs as the CSS lint host (C5, Phase 3). C5 assigns Calavera ownership of the css-evolve catalog entry, including the ESLint block that entry installs; that block is a separate integration, installed for CSS verification rather than as a JavaScript and TypeScript linter host, and nothing in this ADR touches it. A later css-evolve integration may reintroduce an ESLint dependency for CSS, and that reintroduction is decided under its own ADR, not implied by this one.

## Decision

Remove the `eslint` catalog entry and the eleven entries that include it: `typescript-eslint`, `eslint-config-prettier`, `eslint-react`, `eslint-jsx-a11y`, `eslint-import`, `eslint-n`, `eslint-promise`, `eslint-unicorn`, `eslint-sonarjs`, `eslint-vitest`, and `eslint-jest`. Remove `createESLintConfig`, the `eslint.config.js` managed file it produces, the `lint` and `lint:fix` script contributions, the Classic profile default that selected the `eslint` entry, the `existing-config` inspection entry for `eslint.config.js`, the Composer options for the entry and its ten dependents, and the schema enum values that accept any of these twelve ids. Tests, documentation, and MCP listings for all of the above are removed with the code they cover, not left in place as dead references.

This removal is the JavaScript ESLint host only. `@eslint/css` and the ESLint block css-evolve needs under C5, Phase 3 are explicitly out of scope; nothing in this decision changes that entry, its dependencies, or its managed files. A later css-evolve integration may reintroduce an ESLint dependency for CSS verification, and doing so is a decision for that integration's own ADR, not a consequence of this one.

No compatibility flag, deprecated path, or legacy profile survives this removal. A recipe that names `eslint` or any of the eleven dependent ids is rejected the same way any other unknown id is rejected; there is no fallback that silently accepts the old name or reproduces the Classic profile's prior JavaScript and TypeScript lint behavior.

The changelog entry for this release names the nine plugin entries that were inert so that a project owner who selected one of them knows the installed dependency contributed no rule and can drop it from `package.json` without waiting on a migration path.

After this removal, the Classic profile keeps only Prettier beyond the shared defaults; ESLint was the other component distinguishing it from a `vp`-managed project's JavaScript and TypeScript tooling. CAL-016 removes Prettier next. Once both removals land, the Modern and Classic profiles are identical in the JavaScript and TypeScript tooling they scaffold, and CAL-011 decides whether the profile distinction itself collapses. This ADR does not decide profile collapse; it removes the component this ADR is scoped to and leaves that later question to CAL-011.

## Consequences

A `calavera.config.json` that names `eslint` or any of the eleven removed dependent ids fails validation with the same unknown-id error any other unrecognized integration produces. This is intentional: the changelog tells a project owner to remove the id from their recipe and rely on `vp lint` for JavaScript and TypeScript linting, rather than offering a migration path that keeps the entry reachable in spirit if not in name.

The nine plugin entries that never wired into `eslint.config.js` leave nothing behind to migrate; a project that selected one of them has an unused npm dependency and no rule that stops firing, because none ever fired. The changelog says so explicitly, which is the only remediation this bug needs.

`@eslint/css` and the css-evolve ESLint block are unaffected. They are a separate integration under C5, installed for CSS verification, not the JavaScript and TypeScript linter host this ADR removes. Nothing here changes their catalog entry, dependencies, or managed files, and nothing here authorizes reintroducing a JavaScript-facing ESLint dependency under that entry's name.

The Classic profile's remaining distinguishing component is Prettier. CAL-016 is the next removal in this sequence; once it lands, CAL-011 decides whether Modern and Classic, now identical in JavaScript and TypeScript tooling, collapse into one profile.

## Alternatives considered

**Keep ESLint as a delegate for non-`vp` projects.** Rejected because CQ1 already resolved this question for every JavaScript and TypeScript toolchain component: Calavera offers none of them to a non-`vp` project, and instead points that project at `vp create` or `vp migrate`. Carving out an exception for ESLint alone would reopen a settled decision rather than apply it.

**Fix the wiring bug instead of removing the component.** Rejected because the component is removed regardless of whether the nine plugin entries are wired correctly. Fixing `createESLintConfig` to import all eleven dependent entries would still generate `eslint.config.js` in a Classic profile project that Vite+ already replaces with Oxlint, and the audit's evidence for removal, no `vp create` project contains ESLint, Vite+ documents Oxlint as the replacement, migration rewrites the `eslint` script to `vp lint`, applies whether or not the plugins are wired. Fixing the bug would produce a correctly configured component this ADR removes in its next release.

**A deprecation period that accepts the old ids with a warning before removing them.** Rejected because `AGENTS.md` states removals are complete: no deprecated path, flag, or legacy mode. A warning-then-remove sequence is a deprecated path by another name.

## Open questions

None. Profile collapse is tracked as CAL-011 and is out of scope here; whether a future css-evolve ESLint need reintroduces a JavaScript-facing dependency is a decision for that integration's own ADR and is out of scope here.
