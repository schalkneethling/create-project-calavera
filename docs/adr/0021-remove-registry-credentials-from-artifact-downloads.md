# ADR-0021: Remove Registry Credentials from Artifact Downloads

- **Status:** Accepted (2026-11-22, Schalk Neethling, merged in #1190)
- **Date:** 2026-11-22
- **Issue:** https://github.com/schalkneethling/create-project-calavera/issues/1185
- **Decides:** Calavera stops reading, expanding, and sending the registry credentials that npm, Yarn, and Bun configuration can hold. The registry settings loader in artifact-core keeps the registry, the registry of the artifact scope, and the proxy settings, and keeps nothing else: every `//host/:` credential key (`_authToken`, `_auth`, `username`, `_password`, `certfile`, and `keyfile`) goes, from every source, together with the two credential invariants and the other code that exists only to protect those credentials. Calavera also refuses a registry value that holds a variable, and removes a username and password from a registry URL with a warning. Artifact tarballs download from the artifact scope's own registry, the one the package document came from. A registry that answers 401 or 403 fails with a message that names the failing origin and says that Calavera sends no credentials, and `artifacts status --check-updates` and `artifacts doctor` say the same for each artifact, with a new `origin` field in `--json`. No flag, setting, or deprecated path brings credentials back. Private mirrors that require authentication become unsupported, and #1165 (Yarn and Bun credentials) stays closed as not planned. Proxy credentials are out of scope, and tarball URLs are limited to https in #1194. The owner answered the open questions of the first draft on 2026-11-22, and each answer is recorded under "Owner decisions". This document changes no code. The issue's scope puts the ADR and the removal in one pull request; this ADR was proposed on its own first so that the owner could answer its open questions before the code changes, and the implementation pull request closes #1185.

## Context

The owner decided on 2026-11-22 that Calavera never needs access to a secret, so it stops reading registry credentials altogether, and that registry and proxy settings stay (https://github.com/schalkneethling/create-project-calavera/issues/1064#issuecomment-7084597069). The owner's rule for secrets is that sensitive credentials are used only through Varlock with 1Password locally, or through a platform's secret store on a platform, and never from plain text on disk. A `//host/:_authToken` line in an `.npmrc` file is exactly that plain text.

Calavera's own artifacts are public packages in the `@schalkneethling` scope on the npm registry, so no Calavera feature needs a credential to work. Credential reading came from #608, which asked that artifact resolution honor "the user's npm registry and auth configuration", so that a person behind a private registry or a mirror could still resolve artifacts. That use case becomes unsupported when the registry demands authentication. It keeps working when the mirror serves the artifact packages without authentication.

The removal follows a run of security reviews on #1064 (PR #1161, merged on 2026-11-22 as edf29cf). Each review found another route by which repository content could reach a credential: a project `.npmrc` that names a `userconfig`, a Yarn 4 `.env.yarn` that sets an http registry or a proxy, a spoofed package manager user agent, and a same-host https-to-http redirect that make-fetch-happen follows with the `Authorization` header still attached. PR #1161 answered the first three with two invariants: no credential over plain http, and credentials only from the account's real `~/.npmrc` when a package manager starts Calavera. The owner accepted the redirect gap "only until #1185 removes credential reading entirely" (https://github.com/schalkneethling/create-project-calavera/issues/1064#issuecomment-7084781247). When Calavera holds no credential key, none of these routes has a credential to carry.

The issue's litmus test is a removal: Calavera must never hold a secret. Vite+ is unaffected, because it does not fetch Calavera's artifacts.

### What npm-registry-fetch does with credentials

`npm-registry-fetch` 20.0.1, the version pacote 22.0.1 installs here, takes credentials from the options it is given and reads no environment variable for them. `getAuth` in `lib/auth.js` looks up `${regKey}:_authToken`, `:_auth`, `:username` with `:_password`, and `:certfile` with `:keyfile` for the request's host and path, and reads the files that `certfile` and `keyfile` name. It also honors a `forceAuth` option, and `lib/index.js` accepts top-level `cert` and `key` options. `lib/index.js` turns a token into `authorization: Bearer` and `_auth` into `authorization: Basic`. The loader passes none of `forceAuth`, `cert`, or `key`. So when the loader's options hold only registry and proxy keys, `npm-registry-fetch` attaches no credential that the person configured.

Two routes stay outside the loader's keys. First, a URL's own user information: minipass-fetch turns `https://user:pass@host/` into an `Authorization: Basic` header (`minipass-fetch/lib/request.js`), whether the URL is a configured registry or a tarball URL that a registry's package document names. Second, a token in a URL's path or query, such as a path-token registry URL, travels as part of the URL. Owner decision 1 covers the configured registry URL. A tarball URL comes from the registry, not from the person's configuration, so it is not one of the person's secrets; #1194 limits it to https.

## Decision

### 1. No credential key is read, expanded, or sent

The loader keeps an allowlist of the keys that decide where a request goes: `registry`, the registry of the artifact scope (`@schalkneethling:registry`), `proxy`, `https-proxy`, and `noproxy`, the Yarn registry and proxy settings, and the Bun registry settings. Calavera reads no Bun proxy setting. The loader drops every other key as it reads each layer: the user `.npmrc`, the project `.npmrc`, the file a `userconfig` names, `npm_config_*` variables (including `npm_config_//host/:_authToken`), `.yarnrc.yml`, `YARN_*` variables, and `bunfig.toml`. It never expands a credential key, never returns one, and never names one in a warning, because naming it would mean that the loader still looks for credential keys (owner decision 4). Under Yarn 2 or later, the loader then reads no `.npmrc` file and no `npm_config_*` variable at all.

The implementation removes:

- `AUTH_KEY`, `CERTIFICATE_KEY`, the project-layer certificate check, and the credential parts of `npmKeys`;
- both invariants: `credentialsLocked`, `credentialHome`, `credentialPath`, `credentialLayer`, the locked-credential and expanded-key warnings, `ACCOUNT_NPMRC`, `accountHomeFolder`, the `userInfo` import, and `requestOptions`. `pacoteTarballUrl` stays for #1194's check, with its target changed (Decision 4);
- the `accountHome` test parameter from `loadNpmRegistryOptions` and the three `registry.js` functions;
- the plain-http credential warning;
- the table half of `credentialsNote`, because it exists only to look for Bun credential keys;
- `nerfDartHost` and the nerf-dart branches of `environmentSettings` and `exportedFrom`, because no `//host/:` key is read any more;
- `packages/cli/scripts/isolated-account-home.mjs` and its load in `packages/cli/scripts/no-version-check.mjs`, because no code reads the account's home folder any more;
- the credential wording in the comments listed under "The loader".

`registry.js` then spreads the loader's options into pacote directly again, because no option can carry a credential, and `extractArtifactPackage` also passes the artifact scope's registry as `registry` (Decision 4). The `artifact-auto-install.test.mjs` fixture changes its warning text to a warning the loader still gives, such as an ignored project proxy. The changeset from #1161 is amended before release, so that the changelog does not announce rules the same release removes.

The tests replace the credential tests with the test that the issue asks for. It plants every credential key (`_authToken`, `_auth`, `username` with `_password`, `certfile` with `keyfile`) for the registry host and for a tarball host, in the user `.npmrc`, the project `.npmrc`, a `userconfig` file, `npm_config_*` variables, `.yarnrc.yml`, and `bunfig.toml`. It runs once for each launcher (npm, Yarn 2 or later, and Bun), because the loader reads a different set of files under each. Against local servers, it runs resolution and extraction and asserts that no request carries an `authorization` header, that no TLS client certificate is presented, and that no planted value appears in any warning, diagnostic, error message, error cause, or `--json` output. A second assertion checks that every key the loader returns is on the allowlist, so the test fails if any credential key, or any option such as `forceAuth`, `cert`, or `key`, comes back.

### 2. Registry URLs carry no credential and no variable

Owner decision 1 extends the removal to the registry URL itself:

- **No variables in registry values.** The loader stops expanding variables in `registry` and the artifact-scope registry, whether the value comes from an `.npmrc` file (`${VAR}`), a `npm_config_*` variable, `.yarnrc.yml` (`expandYarn`), or `bunfig.toml` (`expandBun`). A registry value that contains a variable reference stops the command with an error that names the setting and its layer, never the value, as `assertRegistryUrl` does for a registry that is not an http or https URL. Calavera never ignores such a value and falls back to another layer or to `registry.npmjs.org`, because that would bypass a mirror the person configured, which this ADR rejects under Alternatives considered. The version check applies the same rule: its lookup fails, so the notice stays quiet (ADR-0019, Decision 6), and `CALAVERA_DEBUG` shows the error. In a project file, the branch that today ignores a value with `${...}`, or a Bun value that starts with `$`, with a warning (`npm-config.js`, lines 331 to 336) becomes this stop error for `registry` and the artifact-scope registry; for every other key it keeps ignoring the value with its warning. Owner decision 1 decides that variables stop expanding; stopping with an error rather than ignoring the value is this ADR's rule following that decision. A variable in a registry URL is in practice a way to inject a secret, such as a path token. Proxy values keep their expansion rules, because proxy credentials are out of scope (owner decision 2).
- **npm's exported copy is recognized.** Under `npx`, `npm exec`, and `npm run`, npm expands `registry=${VAR}` from the user `.npmrc` itself and exports the result as `npm_config_registry`. The `exportedFrom` comparison keeps recognizing that exported copy, by expanding the file's value only to compare it with the variable, so the exported value counts as the user file's value, which carries a variable and stops the command. The expanded text is never used as a registry. A test plants `registry=https://npm.example.com/${TOKEN}/` in the user `.npmrc` with a fake token in the variable, sets `npm_config_registry` to the expanded URL and the npm launcher markers, and asserts that the command stops with the named error, that no request is made, and that the token appears in no output. The project `.npmrc` follows the same comparison, which already recognizes npm's expanded copy of a project value.
- **No user information in registry URLs.** A registry URL that contains a username or password is used without them, under npm, Yarn 2 or later, and Bun alike, with a warning that names the setting and its layer, never the value, and says that Calavera sends no credentials. This replaces the refusal in `assertRegistryUrl` and turns the URL half of `credentialsNote` into this warning. minipass-fetch would turn user information into basic authentication, so the URL is never passed on as written.
- **A literal token in a URL path is not detectable.** Calavera cannot tell a token path segment from an ordinary one, so the docs say that a token written literally into a registry URL's path or query travels with the URL, and that Calavera does not support registries that need one.

A mirror that also serves anonymous requests keeps working when its configured URL carries credentials, and an authenticated one fails with the Decision 3 message.

### 3. What a user of an authenticated registry sees

A registry or tarball host that answers 401 or 403 stops the command with an error that names the origin of the request that failed and says that Calavera sends no credentials. artifact-core raises it in `registry.js` from one wrapper that all three pacote calls use, inside `withNpmDiagnostics`, so the artifact commands and the version notice get the same message. For a 401 from the configured registry, it reads:

```text
The registry https://npm.example.com answered 401 for @schalkneethling/calavera-skill-frontend-security.
Calavera sends no credentials to any registry. If this registry requires authentication, Calavera cannot use it: point @schalkneethling:registry in the project .npmrc at a registry that serves Calavera's packages without authentication, such as https://registry.npmjs.org/.
```

For a 403 from a tarball host that the registry's package document named, it reads:

```text
The tarball host https://cdn.example.com answered 403 for @schalkneethling/calavera-skill-frontend-security@1.4.0.
Calavera sends no credentials to any registry or tarball host. The registry https://npm.example.com, from @schalkneethling:registry in the project .npmrc, named this download. If the host requires authentication, point that setting at a registry whose packages download without authentication.
```

The rules for the message:

- It names the origin (protocol, host, and port) of the URL that failed. `npm-registry-fetch` sets `uri` on every HTTP error to the final URL after redirects, and the wrapper reads it before `withNpmDiagnostics` wraps the error. When `uri` is missing, it falls back to the loader's registry origin. The message never prints the path, the query, or user information, because a URL can carry a token.
- It says "if this registry requires authentication", or "if the host requires authentication", not that it does, because a 403 can also come from a repository firewall that blocks a package or from an expired signed tarball URL.
- It calls the failing origin "the registry" and names its setting and layer in the remedy when the origin equals the configured registry origin. Otherwise it calls the origin "the tarball host" and names the configured registry, with its setting and layer, as the one that named the download, because that setting, not the host, is what the person can change. Neither form refers to a line it does not print.
- The loader's `registry` result (`EffectiveRegistry`, `npm-config.js` line 57) gains a `setting` field next to `origin` and `source`, built from the setting name the loader used: `registry` or `@schalkneethling:registry` for npm, and the Yarn and Bun names, such as `npmScopes.schalkneethling.npmRegistryServer`. When the registry is the default, the message says so. The field is for messages only: the CLI's `artifactRegistries` output (`apply --json`, `dry_run_apply`, the examples in `docs/bootstrap-readiness/`) keeps its `origin` and `source` fields and strips `setting`, so that output and its examples do not change.
- The new error keeps `code` (`E401`, `E403`, `EOTP`, or `EAUTHIP`), `statusCode`, and three new top-level fields: `origin` (the failing origin), `setting` (the configured registry's setting name, from the loader's `registry.setting`), and `layer` (its layer, from `registry.source`). The CLI and a debugging run can therefore still tell an OTP demand from an IP block, and a test proves that the three stay distinguishable. `withNpmDiagnostics` (`registry.js`, lines 170 to 192) wraps an error again when the loader has diagnostics, and today copies only `code`, `statusCode`, and `type`; it also copies `origin`, `setting`, and `layer`, so the fields survive that second wrapping. `updateCheckFailure` reads them from the top level of the error it receives, as it reads `code` and `statusCode`.
- AGENTS.md asks that concise errors "preserve underlying causes for debugging", and `formatErrorChain` prints every cause (`packages/cli/src/utils/error-chain.js`, lines 328 to 340), while the original `npm-registry-fetch` error's message holds the full URL, the registry's response text, or the `www-authenticate` header. This ADR resolves the conflict this way: the new error carries a redacted cause that holds only the method, `code`, `statusCode`, and the failing origin, never the URL path, the query, or registry text, and the original error is dropped. The redacted cause carries a `debugOnly: true` marker, and `chainEntries` in `error-chain.js`, which already reads `isDebugEnabled(env)` (line 229), skips a cause with that marker unless debugging is on, so `formatErrorChain` prints it only with `CALAVERA_DEBUG`. The MCP server's `errorChain` follows the same rule. A test proves that the cause appears with `CALAVERA_DEBUG` and not without it, and that no path or registry text appears in either case.
- The version notice still prints nothing for a failed check (ADR-0019, Decision 6). With `CALAVERA_DEBUG` on, it prints this message.

`artifacts status --check-updates` and `artifacts doctor --check-updates` do not stop on a failed lookup; they report it for each artifact through `updateCheckFailure`, which builds its own reason from the error's fields and never prints the error's message. So the per-artifact report must carry the same facts:

- The reason for a 401 or 403 names the failing origin and says that Calavera sends no credentials, for example: "the registry https://npm.example.com answered 401 (E401), and Calavera sends no credentials to any registry". The update check reads only package documents, but a redirect can end on another origin, so the reason follows the same naming rule as the message above: it says "the registry" only when `origin` equals the configured registry origin, and otherwise "the host", followed by the configured registry that the request started from.
- The remedy becomes "If this registry requires authentication, point <setting> in the <layer> at a registry that serves Calavera's packages without authentication, then run: <retry command>", with `setting` and `layer` from the error, or "the registry setting" when the error does not carry them. A test runs the update check against a registry that answers 401 while the loader has a diagnostic, such as an ignored project proxy, and asserts that `origin`, the setting, and the layer still appear in the reason, the remedy, and the `--json` failure object.
- The `--json` failure object (`updateCheckFailure`) gains an `origin` field: the failing origin for an HTTP failure, and `null` for a failure without one, such as a DNS error or a missing tag. Adding a field is not a breaking change under ADR-0018, Decision 6, so the existing fields keep their names and meanings. The README paragraph that lists the fields (line 1256) and `UpdateCheckFailure` in `packages/cli/src/artifact-status-report.js` document it, and the human status report prints the new reason. The MCP artifact status tool returns the same object when it is called with `checkUpdates` (#1052), so `updateCheckFailureSchema` in `packages/cli/src/tool-schemas.js` (line 559) gains `origin` too.
- The tests in `artifact-update-status.test.mjs` that assert the old remedy (lines 562, 582, and 616) change with it, and a new test asserts the reason, the remedy, and `origin` for a 401 and a 403.

Calavera does not warn in advance that it ignored a credential key (owner decision 4); these messages explain the failure when it happens. There is no flag, environment variable, or configuration key that turns credentials back on, and there is no warning period. A person who needs a private registry for their own packages keeps using their package manager for those; only Calavera's artifact and version lookups lose the credential.

### 4. Tarballs download from the artifact scope's registry

pacote rewrites a tarball URL on `registry.npmjs.org` to another registry before it downloads it. In pacote 22.0.1, the fetcher sets `replaceRegistryHost` to `registry.npmjs.org` unless the option names something else, and sets `this.registry` from `opts.registry` (`pacote/lib/fetcher.js`, lines 87 to 91). `RemoteFetcher`, which `pacote.extract` uses for a tarball URL, then replaces the URL's host when `replaceRegistryHost` equals that host, with `new URL(resolvedURL.pathname, this.registry)` (`pacote/lib/remote.js`, lines 13 to 16). `replaceRegistryHost` therefore chooses which host is replaced, as a hostname, `never`, or `always`; only `opts.registry` chooses where the URL goes. `extractArtifactPackage` passes the loader's options, whose `registry` is the default registry, so the artifact scope's registry plays no part today. Behind an authenticated default registry, the workaround in the Consequences would fix the lookup but not the download: the scope registry's document names a `registry.npmjs.org` tarball, pacote moves it onto the authenticated default, and the download gets a 401.

`extractArtifactPackage` therefore passes the artifact scope's own registry as `registry` to `pacote.extract`: the value of the artifact-scope registry setting when one applies, and the default registry otherwise, which is the registry `resolveArtifactPackage` read the package document from. It passes the loader's value, from which Decision 2 has already removed any username and password, so the rewritten tarball URL cannot carry user information either. It leaves `replaceRegistryHost` at pacote's default. The lookup and the download then use the same registry (owner decision of 2026-11-22, https://github.com/schalkneethling/create-project-calavera/issues/1185#issuecomment-7085969047):

- a mirror configured for the scope, or as the default registry with no scope setting, stays the mirror for the download;
- with the `@schalkneethling:registry=https://registry.npmjs.org/` workaround, a `registry.npmjs.org` tarball stays on `registry.npmjs.org`, and the authenticated default registry receives no request;
- a tarball URL on any other host is downloaded as the package document names it, because pacote rewrites only `registry.npmjs.org`.

#1194's rule applies to the final URL, the one pacote fetches after this rewrite: `https` only, except for a loopback host. `pacoteTarballUrl` stays for that purpose: it computes the same rewrite as `remote.js`, now with the scope registry as its target, and loses only its credential comment. pacote keeps the tarball's path and drops any path of the registry URL in the rewrite, so a mirror served under a path, such as `https://mirror.example.com/npm/`, receives the tarball request at the host root; `pacoteTarballUrl` follows pacote exactly, so #1194 judges the URL that is really fetched. The integrity check is unchanged.

Tests prove the design. A unit test checks that `pacoteTarballUrl` maps a `registry.npmjs.org` tarball URL onto the scope registry, leaves a tarball URL on any other host unchanged, and maps onto the default registry when no scope registry applies. A test of `extractArtifactPackage` checks that it passes the scope registry as `registry` to `pacote.extract`. An integration test against local servers, with a default registry that answers 401 to every request and an anonymous scope registry, runs an install and asserts that the default registry receives no request. A further test configures the scope registry as `https://user:pass@` followed by a local host, and asserts that the extract request reaches that host with no `authorization` header.

### 5. What stays

The registry, the artifact-scope registry, and the proxy settings stay, with the precedence and project-file restrictions that `main` defines for them, and with the expansion rules of `main` except for registry values (Decision 2). The tests for registry, scoped registry, and proxy behavior pass unchanged, except where a test asserted a credential, a variable in a registry value, or the user-information refusal, in which case only that assertion changes.

`redact.js` in the CLI stays, because registry and proxy error text can still carry a token that a person put into a URL, and redaction does not depend on what Calavera reads.

Proxy authentication stays (owner decision 2). A proxy URL such as `https://user:pass@proxy.example.com:8080`, from `proxy` or `https-proxy` in the user `.npmrc`, a Yarn proxy setting, or the `HTTPS_PROXY` variable, makes `https-proxy-agent` and `http-proxy-agent` 9.1.0 send a `Proxy-Authorization: Basic` header to the proxy, and a `socks:` proxy URL sends its user information as SOCKS authentication. Removing that would need its own removal issue and ADR.

Two existing rules stay with a new reason, and the implementation rewrites their comments and messages to give it:

- **A project file cannot set a proxy.** This is owner decision 1 on #1064, which this ADR does not reopen. Its comment (`npm-config.js`, lines 343 to 348) gives the user's token as the reason. The remaining reason is that a proxy chosen by a cloned repository sees which packages Calavera fetches, and for an http registry it can change the package documents and tarballs together.
- **A registry set in a project file must use `https`** (owner decision 3). Its comment (`npm-config.js`, line 595) gives the user's token as the reason. The remaining reason is integrity: the tarball's integrity comes from the same package document as the tarball, so on an http registry anyone on the network path can replace both together, and the artifact passes verification. User configuration may still name an `http` registry, because the person chose it.

### 6. What this supersedes

This ADR replaces the credential parts of ADR-0019: "and authentication" in its "Decides" line, "with the same credentials" in Decision 3, "the configured credentials" in its Consequences, and "the configured registry and its credentials" in its Alternatives considered. The version check asks the registry that the configuration names, without credentials. ADR-0019 is an accepted record and is not edited. This ADR also replaces the "auth configuration" half of #608's scope, and the credential invariants that #1161 added under the owner's decision on #1064.

### 7. How C8 holds

The removal touches no write path. Only the CLI writes into projects, `dry_run_apply` stays the approval boundary, local edits are preserved, artifacts are not written to `package.json`, and conflicts still surface as a hard stop or a migration decision. The loader reads fewer keys from the same files and writes nothing. The C8 safety-property tests need no change; the implementation must not modify them.

## Consequences

A private registry or mirror that requires authentication for Calavera's packages no longer works with Calavera. The person sees the message from Decision 3. When the authenticated registry is only the artifact scope's, they change `@schalkneethling:registry`. When it is the default `registry`, as in a common corporate setup that sends everything through one authenticated server, they add this line to their user `.npmrc`, which sends only Calavera's artifact scope to the public registry:

```ini
@schalkneethling:registry=https://registry.npmjs.org/
```

The version notice cannot be fixed that way, because it looks up the unscoped `create-project-calavera` package, which the scope line does not cover. Behind an authenticated default registry, the notice therefore stops appearing, silently, as ADR-0019 Decision 6 specifies for every failed check. A mirror that serves the public registry's packages without authentication keeps working for both.

A registry configured through a variable, such as `registry=${COMPANY_REGISTRY}`, stops every artifact command with an error that names the setting, and the version notice goes quiet. A person who used a variable for a registry URL without a secret in it writes the URL literally instead.

This overlaps with #1186, which asks that `${VAR}` in registry and proxy values expand only in the user's real `~/.npmrc`. This ADR removes expansion in registry values everywhere, so #1186's registry half is met by the implementation, and #1186 keeps its proxy half and its launcher spoofing checks. #1186's proxy half asks that `${VAR}` expand only in the user's real `~/.npmrc`, with the home folder taken from the operating system account, so it will need an account-home lookup like the `accountHomeFolder` and `userInfo` code this ADR removes; #1186 adds it back for that purpose, not for credentials.

Because the download uses the artifact scope's registry (Decision 4), the scope workaround fixes the download as well as the lookup, and a configured mirror keeps serving both. A tarball URL that a mirror's document names on a host other than `registry.npmjs.org` is downloaded from that host, as before.

A person whose `~/.npmrc` holds a `//registry.npmjs.org/:_authToken` for publishing their own packages, and who uses the default registry, resolves Calavera's public artifacts as before, now without sending that token.

The security work of #1161 shrinks. Both credential invariants, the same-host redirect gap, the account-home logic, and the test-only `accountHome` parameter go, because they only protected credentials. #1161's proposed follow-up for the redirect gap is no longer needed. Its follow-ups about error causes and about a project `userconfig` that chooses the user `.npmrc` stay, because causes can still hold a proxy URL with credentials, and that file still chooses the registry and the proxy.

#1165, which would have read Yarn and Bun credentials, was closed as not planned on 2026-11-22.

The loader still reads whole `.npmrc` files, because the registry and proxy keys live in them, so a token's text passes through memory while `ini` parses the file. Calavera keeps no credential key from the parsed result, expands none, logs none, and passes none on. The process environment also holds whatever the caller exported, such as an `NPM_TOKEN`, and Calavera does not read it. "Never holds a secret" therefore means that no Calavera code path reads, keeps, or sends a configured registry credential, not that no credential bytes ever enter the process. Proxy credentials are the stated exception (owner decision 2).

The docs change with the implementation: the "npm registry configuration" section of `docs/architecture/versioned-artifacts.md`, including the "Security model" bullet, drops the credential keys, states that Calavera sends no registry credentials and refuses a variable in a registry value, says that a token written literally into a registry URL is not supported, and rewrites the "Secrets" bullet to say that Calavera reads no registry credential, so none can appear in output. The README drops the credential wording at lines 933 to 941 and line 1256, and its field list at line 1256 gains `origin`. The changeset is a major bump for `create-project-calavera` and `@schalkneethling/calavera-artifact-core`, as ADR-0006's removal was for the CLI, because a setup that worked with an authenticated registry stops working.

Tarball URLs are #1194's subject, not this ADR's. `resolveArtifactPackage` checks only that `dist.tarball` exists before passing it to `pacote.extract`, and pacote chooses a fetcher by the spec's type, so a registry that names a `git+ssh:` or `git+https:` tarball could make pacote run git with the person's SSH agent and git credential helpers. #1194 limits `dist.tarball` to https, except for a loopback host (`localhost`, `127.0.0.1`, or `::1`), which the release rehearsal's local registry and the tests use over http (owner decision 5).

## Owner decisions

The owner answered the five open questions of the first draft on 2026-11-22 in https://github.com/schalkneethling/create-project-calavera/issues/1185#issuecomment-7085649076, accepting each recommendation as written. The comment numbers them differently from the draft; this list follows the comment. The comment records the decisions; the reasons below come from the first draft's recommendations, which the owner accepted with them.

1. **Tokens inside registry URLs.** Calavera stops expanding variables in registry values, and removes any username and password from a registry URL with a warning, the same way under npm, Yarn 2 or later, and Bun. A token written literally into a URL path is documented as undetectable. Reason: a variable in a registry URL is in practice a way to inject a secret, and minipass-fetch would send user information as basic authentication. Removing the user information instead of refusing the URL keeps a mirror that also serves anonymous requests working. Decision 2 applies this.
2. **Proxy credentials.** Out of scope for this removal; removing them would need its own removal issue and ADR. Reason: proxy authentication authenticates the network path rather than the registry, `@npmcli/agent` reads `HTTPS_PROXY` itself rather than through Calavera's loader, and refusing it would cut off everyone behind an authenticated corporate proxy. Decision 5 records it.
3. **https for a registry set in a project file.** Kept, now justified by integrity rather than token protection. Reason: on an http registry, anyone on the network path can replace the package document and the tarball together, and the tarball still passes the integrity check that the replaced document names. Decision 5 records it.
4. **Ignored credential keys.** No warning. Reason: a warning would require the loader to look for credential keys, which the issue's acceptance criteria rule out, and the 401 or 403 message explains a failure when it happens. Decisions 1 and 3 apply this.
5. **Tarball URLs.** A separate issue, #1194, limits `dist.tarball` to https, with one exception that has a valid reason: a loopback host (`localhost`, `127.0.0.1`, or `::1`), which the release rehearsal's local registry and the tests use over http. The Consequences record it.

## Alternatives considered

- **Keep credentials behind the #1161 invariants.** Rejected by the owner's rule: four review rounds each found a new route to a credential, and the redirect gap remains open. Removing the credential removes that class of bug.
- **Keep credentials behind an opt-in flag or environment variable.** Rejected: the repository rules call for complete removals with no deprecated paths, flags, or legacy modes, and an opt-in would keep all the code that protects the credential.
- **Read credentials through Varlock or a platform secret store.** Rejected: Calavera's artifacts are public, so no Calavera feature needs a secret, and adding a secret source would make Calavera hold one.
- **Fall back to the public registry after a 401 or 403.** Rejected: a silent switch would hide which registry served an artifact, and a person who configured a mirror on purpose, for example to block the public registry, would get packages from a source they did not choose.
- **Refuse a registry URL that contains a username or password.** Rejected by owner decision 1: it is stricter, but it breaks a working anonymous mirror because of a line the person may not control, and removing the user information already keeps the credential out of every request.

## Amendment: Values a Repository Supplies Through Files a Package Manager Expands

**Status:** Accepted (decided by the project owner on 2026-11-24 on #1186, implemented in #1225). It amends Decision 2 ("No variables in registry values") and its rule that npm's exported copy is recognized. It extends the same rule to proxy values, and to the files that a package manager or runtime expands before Calavera starts. Decisions 1 and 3 to 5, and the owner decisions above, are unchanged.

### Why Decision 2 is extended

Decision 2 stops Calavera from expanding a variable in a registry value. #1186 showed that a repository can still have a variable expanded into a registry or proxy URL: it names a file that npm, Yarn 4, or Bun expands before Calavera starts, and Calavera then receives the expanded value as an environment variable. Examples are a project `.npmrc` `userconfig`, `globalconfig`, or `prefix`, a Yarn 4 `.env.yarn`, and a Bun `.env`. A registry or proxy chosen this way, with an environment secret in its URL, sends that secret to a host the repository chose. An earlier owner decision on #1186 (2026-11-23) accepted `.env.yarn` values as a repository's choice. The owner reversed that acceptance for values that came from a variable, because it did not account for a repository carrying a caller's variable to a host the repository chose.

### Decision

1. **A user file that the project chose follows the project rules.** When npm starts Calavera and the project `.npmrc` chose the user `.npmrc` with `userconfig`, that file follows the project rules: it cannot set a proxy or a plain-`http` registry, and its variables are not expanded. This also applies when the key is spelled another way, which npm ignores but exports over the caller's `npm_config_userconfig`. The account's own `~/.npmrc` keeps user trust.
2. **A Yarn 4 `.env.yarn` value that came from a variable is ignored.** Under Yarn 2 or later, a registry or proxy variable is ignored, with a warning and a remedy, when an environment file that Yarn may have loaded gives it a value with a `$` in it, escaped or not, because Yarn turns an escaped `\${...}` into a literal one that Calavera would expand. Only the files Yarn loaded for this run count (owner decision of 2026-11-24 on #1186, which replaces judging every file Yarn may have loaded). Calavera derives them from Yarn 4.18.1's `Configuration.find` and from what Yarn passes to the child: `INIT_CWD`, the `injectEnvironmentFiles` lists of the settings files from the home folder and from the root down to `INIT_CWD`, and otherwise the default `.env.yarn` in Yarn's own process folder, which Calavera reads from `/proc` on Linux. On macOS and Windows, where it cannot read that folder, the `.env.yarn` files Yarn could have read for the run count (owner decision of 2026-11-24): those in the project that `PROJECT_CWD` names, and those in `INIT_CWD`, `PROJECT_CWD`, the folder Calavera started in, and every folder above them. A `yarn --cwd` run started in an unrelated folder is outside that set, so it is covered on Linux only. So a variable the caller set still applies when only a file Yarn did not load names it. When Calavera cannot tell which files Yarn loaded, it ignores every registry and proxy variable and says why, with a remedy. That covers a set `YARN_INJECT_ENVIRONMENT_FILES`, a form of `injectEnvironmentFiles` other than a list, a path variable without a value, a changed `HOME` with home settings that list files, a loaded file that sets one of Yarn's inputs, and an unknown process folder whose candidate folders cannot be bounded. A value that such a file sets literally, and a variable that only the caller set, follow the environment rules.
3. **A Bun `.env` value that came from a variable is ignored the same way.** When Bun runs Calavera, the same rule applies to the `.env` files that Bun loads from the folder it started in, for the mode the caller's `NODE_ENV` chose, and to the files that Bun's `--env-file` option names. A direct Bun run sets neither `npm_execpath` nor `npm_config_user_agent`, so Calavera then reads the Bun settings, and a launcher variable that a loaded `.env` file sets counts as repository content. When one of those files, or a `development` file, defines `NODE_ENV`, the value may have come from it, so the `development` files are judged too.
4. **A proxy variable that the agent falls back to is bypassed.** When the ignored variable is `HTTPS_PROXY`, `HTTP_PROXY`, or `PROXY`, which @npmcli/agent reads from the environment, Calavera sends each lookup and download, and every redirect it follows, through an agent without a proxy.

### Consequences

A repository can no longer get a caller's variable expanded into the registry or proxy that Calavera uses, through the files this amendment names. Calavera cannot tell a value the caller set from one such a file set, so the rule errs toward ignoring. While an environment file that Yarn loaded or Bun may have loaded, or a non-expanding `.npmrc`, sets a key with a variable, a value that the caller sets for the same key is ignored too. The warning tells the person to remove the entry. A CI job that names its own user `.npmrc` with `npm_config_userconfig` keeps user trust for that file, but variables in it are not expanded, as before this amendment.
