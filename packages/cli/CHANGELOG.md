# create-project-calavera

## 7.0.0

### Major Changes

- 703249c: Calavera requires Yarn 2 or later and no longer runs under Yarn 1 (Yarn Classic) (ADR-0023). When Yarn 1 starts Calavera, for example with `yarn create project-calavera`, every command stops before it does anything, after only the check of its arguments, and exits 1 with one message:

  ```text
  create-project-calavera does not support Yarn 1.22.22. Use Yarn 2 or later (yarn dlx create-project-calavera), npm (npx --package create-project-calavera create-project-calavera), pnpm (pnpm dlx create-project-calavera), or Bun (bunx create-project-calavera).
  ```

  With `--json`, the same message is the `error` issue of the JSON result. The MCP server stops the same way before it starts, with commands in the form an MCP host's configuration needs. Before this release, Calavera ran under Yarn 1 with the npm registry settings, and `--new` fell back to an npm runner.

  Calavera recognizes Yarn 1 only from `npm_execpath` and `npm_config_user_agent`, so a project `.npmrc` `user-agent` cannot stop it under npm or pnpm, and under the Bun runtime a value that a `.env` file defines does not count. Under Yarn 1 itself, a repository's `.yarnrc` can change both variables, so the stop is not a security boundary.

  These Yarn 1 paths are removed:

  - The hint that `--new` added when `yarn dlx` failed, and the `yarn --version` and `yarn node` commands it ran to choose it. A failed `yarn dlx` now gets the same message as a failed `pnpm dlx`.
  - The `-W` flag in the `yarn remove` command that `eject` reports at a Yarn workspace root. A project that pins Yarn 1 gets the Yarn 2 or later command.

  `@schalkneethling/calavera-artifact-core` exports `unsupportedYarnVersion` from its `./registry` entry, and `loadNpmRegistryOptions` throws "Calavera does not support Yarn <version>. Use Yarn 2 or later, npm, pnpm, or Bun." under Yarn 1 instead of reading the npm settings.

- 1df384b: Calavera no longer reads, expands, or sends registry credentials (ADR-0021). Artifact lookups, artifact downloads, and the version notice read only the registry, the registry of the artifact scope, and the proxy settings, and ignore every `//host/:_authToken`, `_auth`, `username`, `_password`, `certfile`, and `keyfile` key, from every `.npmrc` file and `npm_config_*` variable, and every credential in `.yarnrc.yml` and `bunfig.toml`, without a warning. Under Yarn 2 or later, Calavera reads no `.npmrc` file and no `npm_config_*` variable at all. A private registry or mirror that requires authentication for Calavera's packages no longer works: a registry or tarball host that answers 401 or 403 stops the command with an error that names the origin that answered, says that Calavera sends no credentials, and names the setting to change, and `artifacts status --check-updates` and `artifacts doctor --check-updates` report the same for each artifact, with a new `origin` field in the `--json` failure object. When only your default `registry` requires authentication, add `@schalkneethling:registry=https://registry.npmjs.org/` to your user `.npmrc`. A registry value that contains a variable, such as `registry=${COMPANY_REGISTRY}`, now stops the command with an error that names the setting, never the value; write the URL literally instead. A username and password in a registry URL are removed with a warning. Artifact tarballs now download from the artifact scope's own registry, the one the package document came from, so a configured mirror serves both the lookup and the download. No flag or setting brings credentials back. Proxy settings, including proxy authentication, are unchanged.
- 624fab4: A proxy setting that uses `${VAR}` in a user `.npmrc` outside your operating system account's home folder stops expanding (#1186). This includes a user `.npmrc` that `npm_config_userconfig` names, for example in CI. Calavera now ignores such a proxy entry with a warning that names the key, never the value. To keep the proxy, write its URL without a variable, or remove the entry and set the proxy in `~/.npmrc` in your account's home folder or as an environment variable, such as `npm_config_https_proxy`. Under `npx`, `npm exec`, and `npm run`, the environment variable does not replace the entry while the entry is still in the file. The same rule applies to a `~/.yarnrc.yml` in a `HOME` that is not your account's home folder, such as one that a Yarn 4 `.env.yarn` sets. Calavera still reads the registry and the literal proxy settings of such a file. Under `npx`, `npm exec`, and `npm run`, a proxy with `${VAR}` in npm's global configuration file (`<prefix>/etc/npmrc`, or the file `globalconfig` names) also stops working, because npm expanded it and Calavera no longer trusts the expanded copy: write the proxy URL without a variable, or remove the entry and set the proxy in your own `~/.npmrc` or an environment variable. When the operating system reports no home folder for your account, for example for a container user ID without a password database entry, no user file is your own, so even proxies in `~/.npmrc` stop expanding.

  A project file can no longer change which package manager's settings Calavera reads for artifact lookups, artifact downloads, and the version notice. When `npm_execpath` names npm or pnpm, Calavera reads the npm settings even when the user agent names Yarn or Bun. npm exports a project `.npmrc` `user-agent`, and pnpm its `userAgent` setting, as `npm_config_user_agent`, so that variable alone can come from the repository.

  Under `npx`, `npm exec`, and `npm run`, Calavera now recognizes two more kinds of values that npm passes on from a configuration file. One is a proxy that a chosen user `.npmrc` spells differently, such as `https_proxy`, which is no longer trusted as an environment variable. The other is a project `.npmrc` key with a variable in it, such as `registry${UNSET?}`, which npm expands and which now follows the project rules. Calavera also reads the global npm configuration file that npm used, which a project `.npmrc` can choose with `globalconfig` or `prefix`. When a project file chose that file, or it lies inside the project, its values follow the project rules, so npm's expanded copy of its registry or proxy is no longer trusted as environment. A project proxy written as a list (`https-proxy[]=…`), or with a variable in its key or value whose value changes after npm reads the file, such as `https-proxy${INIT_CWD?}=…` or `${npm_config_https_proxy?}`, is ignored too. When a project `.npmrc` sets `userconfig` in another spelling, such as `USERCONFIG`, which npm ignores but exports as `npm_config_userconfig` over your own value, the user `.npmrc` that Calavera reads follows the project rules.

  A user `.npmrc` that a project `.npmrc` chose with `userconfig` now follows the project rules when npm starts Calavera: its proxy is ignored with a warning, and a plain-`http` registry in it stops the command. Your own `~/.npmrc` keeps working as before, even when the project names it, and so does a user `.npmrc` that you name with `npm_config_userconfig`.

  A registry or proxy variable that a project's Yarn 4 `.env.yarn` sets from a variable, such as `YARN_HTTPS_PROXY=http://${CI_TOKEN}.example.com`, is now ignored with a warning, and so is one whose value holds any `$`, because Yarn turns an escaped `\${...}` into a literal one that Calavera would expand. The same applies to the `.env` files Bun loads when Bun runs Calavera, including the files Bun's `--env-file` option names. Yarn and Bun expand such a value from your environment before Calavera starts, so a repository could otherwise send an environment value to a host it chose. To keep such a setting, write it in the file without a variable, or remove it from the file and set it in your own environment. Under Yarn, only the environment files Yarn loaded for this run count, including under `yarn dlx`, so a variable you set still applies when only a file Yarn did not load names it. When Calavera cannot tell which files Yarn loaded, it ignores every registry and proxy variable with a warning that says why and how to fix it. An example is `YARN_INJECT_ENVIRONMENT_FILES` set in the environment; listing the files in the project's `.yarnrc.yml` fixes it. Calavera reads the folder Yarn ran in from `/proc` on Linux. On macOS and Windows, the `.env.yarn` files Yarn could have read for the run count, and only the variables those files set from a variable are ignored; a variable you set is then also ignored when one of those files sets it from a variable. A value those files set without a `$`, and a variable you set that no such file sets, apply as before. When the ignored variable is `HTTPS_PROXY`, `HTTP_PROXY`, or `PROXY`, Calavera sends its lookups and downloads, redirects included, without that proxy. When a `.yarnrc.yml` setting or `YARN_INJECT_ENVIRONMENT_FILES` names an environment file with a variable in its path, Calavera cannot tell which file Yarn loaded, so it ignores every registry and proxy variable with a warning.

  When Bun runs Calavera directly, such as with `bun calavera.js`, Calavera now reads the Bun settings instead of the npm settings, because no package manager started it. Bun sets neither `npm_execpath` nor `npm_config_user_agent` then, so a project `.env` could set them; a launcher variable that a `.env` file Bun loaded defines is now ignored with a warning that names the file. Under the Bun settings, Calavera reads no proxy from `.npmrc` files or `npm_config_*` variables, as Bun does not, so a `proxy`, `https-proxy`, or `noproxy` in your `~/.npmrc` no longer applies to such a run; a note names each `proxy`, `https-proxy`, and `noproxy` it skips, and `HTTPS_PROXY` and `NO_PROXY` still apply. When a file entry with a variable makes Calavera ignore an `npm_config_*` value under `npx`, `npm exec`, or `npm run`, and that value is not npm's own expansion of the entry, a note now says that a value you set for that variable was ignored too, and how to keep it.

- ee26481: Calavera now requires OpenCode 2 (#1204, ADR-0022). `--init --mcp-harness opencode` writes the `calavera` entry in `opencode.json` under `mcp.servers`, the layout OpenCode 2 documents, with `type` and `command` only: OpenCode 2 connects a server unless it sets `"disabled": true`, so the entry no longer carries `enabled`. The setup notes in `.agents/calavera/mcp.md` show the same entry and say that OpenCode 2 is required. No flag or setting writes the OpenCode 1.x layout.

  When `opencode.json` holds the unedited entry that 2.2.0 through 6.2.1 wrote directly under `mcp`, rerunning `--init` moves it to `mcp.servers` in one write and says so on the `opencode.json` line. OpenCode's migration guide says not to point OpenCode 1.x at files in this layout: OpenCode 1.18.23 and earlier reject such a file as invalid, and later 1.x releases translate it, so install OpenCode 2, or restore `opencode.json` from version control, if you stay on OpenCode 1.x. When `opencode` is on your `PATH`, `--init` runs `opencode --version` once and warns on the `opencode.json` line when it reports a version older than 2; the warning never blocks the write, and `--json` reports the outcome as `mcp.versionCheck`. If `opencode` does not answer within 5 seconds, the check kills it, and on macOS and Linux every process in its process group, such as the native binary npm's `opencode` launcher starts, and moves on. The same happens when `opencode` prints more than 64 KiB, and when `--init` exits or is interrupted, for example by Ctrl+C, before the check ends. Set `CALAVERA_NO_OPENCODE_VERSION_CHECK` to `1` or `true` to skip the check. On Windows, the check runs only `opencode.exe`, so an OpenCode installed as an `opencode.cmd` shim gets no warning.

  `--init` leaves `opencode.json` unchanged, and lists it as skipped with a remedy, when either location holds an edited `calavera` entry, when `mcp.servers` is not an object of servers (such as an OpenCode 1.x server named `servers`), or when the file has comments or trailing commas and holds a `calavera` entry; for that last case, the remedy points at the OpenCode example in the README's MCP Server section, because a run that keeps the file writes no setup notes. A file with comments and no `calavera` entry gets the manual setup notes instead of being reported as JSON that does not parse. `eject` recognizes the entry under `mcp.servers` and the one earlier releases wrote under `mcp` as Calavera's, removes each unedited one, and keeps and reports an edited one with its location.

### Minor Changes

- 72a5e4c: Each entry of `autoInstalledArtifacts` in the `apply --json` result, and in the MCP `dry_run_apply` and `apply_recipe` results, now has a `filesAlreadyMatch` field (#1021). It is `true` when the files in the project already match the version apply locks, so apply writes none of that artifact's files. Apply still locks the version, stores the package under `.calavera/packages/`, and records the artifact in `.calavera/state.json`. The `dry_run_apply` tool now declares an output schema that describes the field. The apply summary reads the same field for its "its files in the project already match" line, so the summary and the JSON result agree. The lock file that apply writes does not change.
- b84d1d5: The MCP server has a new read-only tool, `artifact_status`, that returns the same report as `artifacts status --json`, so an agent can see which artifacts have updates, local edits, or missing files without leaving the MCP tool sequence. Its optional `checkUpdates` input works like `--check-updates` and contacts the npm registry, and its optional `config` input works like `--config`. Its annotations mark it read-only and open-world, and it declares an output schema. The tool writes nothing into the project. With `checkUpdates`, it resolves packages through a temporary cache that it removes afterward and writes no artifact cache block, so its `ignoreChanges` and `pointers` are always empty, and it never loads the project's formatter. While an artifact transaction is pending, it does not roll the transaction back as `artifacts status` does: it returns a result with `phase` set to `pending-transaction`, no artifacts, `rollbackFiles`, which lists the files the rollback would restore or remove, and `remedy`, which says to save any edits to those files and then run `artifacts status`. The Composer's WebMCP tools do not offer it, because the browser cannot read the project. The README, `--help`, the agent-first workflow guide, the `workflow` list in `list_profiles` and `compose_recipe` results now name the tool. The Calavera skill does not need to name it, because it tells the agent to use the tools the server lists (#1053) (#1052).
- 827da59: Artifact lookups and the version notice now use the registry and proxy of the package manager that started Calavera. The `proxy`, `https-proxy`, and `noproxy` settings in your user `.npmrc` and the matching `npm_config_*` variables now apply, except under Bun, which does not support them, so a proxy set only in `.npmrc` no longer makes lookups fail. A `noproxy` in the project `.npmrc` also applies, but a proxy in a project file is ignored with a warning, and it never replaces the proxy in your user configuration. When npm starts Calavera (`npx`, `npm exec`, `npm run`), the project `.npmrc` is now the one npm read at its local prefix, such as the workspace root when you run from a workspace member, so a registry or proxy that npm passes on from that file follows the project rules; before, a workspace root `.npmrc` registry passed on this way was trusted as your environment. A project proxy written with another spelling, such as `https_proxy`, is recognized too, and a `noproxy` list that npm passes on is split into hosts. Under Yarn 2 or later, Calavera reads `npmRegistryServer`, `npmScopes`, `httpProxy`, and `httpsProxy` from your `.yarnrc.yml` files and `YARN_*` variables, and uses Yarn's default registry when none is set. Under Bun, it reads `[install] registry` and `[install.scopes]` from `bunfig.toml`, then the first of `BUN_CONFIG_REGISTRY`, `NPM_CONFIG_REGISTRY`, and `npm_config_registry` that starts with `http://` or `https://`, as Bun does. Warnings and errors name a setting, never its value, because a proxy or registry URL can carry credentials (#1064).
- bc05382: `doctor` now warns about two kinds of recipe value that `apply` refuses, in any project and whatever the Vite+ status (#1082). A removed profile, such as `modern`, is named with its replacement and ADR-0011. A removed JavaScript or TypeScript toolchain integration, such as `eslint` in a project Vite+ does not manage, is named with the ADR that removed it and the advice to run `vp create` or `vp migrate` first (ADR-0009). Any other unknown integration ID is named by its position in `integrations`, so `doctor` does not repeat text from the recipe. In a project Vite+ manages, a removed toolchain integration keeps its existing warning and gets no second one. These warnings stay advisory: `doctor` writes nothing, and its exit status does not change.
- f4cba6a: `artifacts status`, `artifacts doctor`, and the MCP `artifact_status` tool now read the project's phase (ADR-0020). Each report starts with a line that names the phase, such as `composed` or `applied`, and what resolves it. The `--json` and MCP results gain `phase`, `phaseLine`, `phaseNotes`, `formatterFailures`, `managedFilePlanProblem`, and `cacheBlockProblem`, and each artifact gains a `condition` with its reason. No field was renamed or removed.

  `artifacts doctor` now fails in these cases:

  - The project is `unmanaged`, `ejected`, or `incomplete`, for example when `eject --yes` left the recipe and the lock without a state file.
  - The project's formatter cannot load, or it refuses a managed file, because `apply` stops on the same thing.
  - The recipe's managed files cannot be planned.
  - A selected artifact's file cannot be read. Before, `artifacts status` and `artifacts doctor` stopped with an error on such a file.
  - A selected artifact that has no lock entry, but whose files the state records, was edited or deleted.

  `artifacts doctor` now passes for a lock entry the recipe no longer selects whose files are edited or not recorded, and warns about it instead. It also passes with a warning while the recipe is not applied yet.

  `artifacts doctor` no longer rolls back a pending artifact transaction, because the rollback writes files. It reports the files the rollback would restore or remove, and exits 1. `artifacts status` still rolls the transaction back first.

  `--check-updates` now records the artifact cache block only when a state file exists and the phase is `composed`, `applied`, or `drifted`. In any other phase it resolves through a temporary cache and writes nothing into the project. When the project's formatter cannot format the state that records the block, `artifacts status --check-updates` reports it as a note, writes no block, and exits 0, and `artifacts doctor --check-updates` reports it as an error and exits 1. Both resolve through a temporary cache, and the results gain `cacheBlockProblem`.

  A lock entry with an invalid version, or another field Calavera cannot trust, now stops `artifacts status` as well as `artifacts doctor`, with an error that names the entry by its position.

  `artifacts status` and `artifacts doctor` now load the project's formatter as `apply` does, to classify managed files. The read-only MCP tool still runs no project code: it reports a managed file that needs the formatter as `not-checked`, and says to run `doctor`.

- bf192a8: `doctor` now reads the project's phase, as `artifacts doctor` does (ADR-0020). Its report starts with a line that names the phase and what resolves it, and lists what it found under headings. Each wiring finding keeps its remedy and prints under its artifact's line. Its `--json` result gains `phase`, `phaseLine`, `artifacts`, and `managedFiles`. Each issue gains `check`, which names the check it comes from, an artifact or wiring issue gains `artifact`, a wiring issue gains `detail`, the finding without the artifact's ID, and `level` gains `info`. No field was renamed or removed. The closing line names each check that failed, and says which of them `artifacts doctor` does not make.

  `doctor` now fails in these cases:

  - The project has no recipe, state, or lock (`unmanaged`). This replaces the "Missing calavera.config.json" error.
  - `eject` removed Calavera's records (`ejected`), or only some records remain (`incomplete`).
  - A pending artifact transaction exists. `doctor` names the files the rollback would restore or remove.
  - A managed file that `apply` wrote was deleted, or cannot be read.
  - A selected artifact's files are missing, cannot be read, are edited, or have no record. `artifacts doctor` already failed on these.
  - The project's formatter cannot load or refuses a managed file, for example because `vite-plus` is declared but not installed.
  - The recipe's managed files cannot be planned.

  `doctor` now passes in one case where it failed: a project that `--init` bootstrapped and that has no recipe yet. It warns instead.

  The "Missing managed file" and "Missing managed AI skill" warnings are replaced:

  - A managed file that `apply` has not written yet is a warning with the `apply` command.
  - A selected artifact that is not installed yet is a note.
  - An edited managed file that the next `apply` would stop on is a note that lists the ways to keep the edit first.
  - A file of your own at a managed path is a note whose remedies keep your file.

  A `package.json` that cannot be parsed in a workspace member is now a finding instead of a stop, and `doctor` goes on to classify. During a pending artifact transaction, a recipe that `doctor` cannot read, parse, or resolve is an error finding too, so `doctor` reports the phase `pending-transaction`, as `artifacts doctor` does. A changed hook marker line is named, not printed back. A deselected artifact is reported only when it has a problem, as `artifacts doctor` reports it.

- 43ec6e2: `eject` now marks a project it has finished ejecting, so `doctor`, `artifacts status`, and `artifacts doctor` can tell it apart from a project Calavera never managed (ADR-0017, Amendment 5). Once it has removed everything else, `eject` adds a Calavera block named `ejected`, which holds one comment line, at the end of `.gitignore`, creating the file when the project has none, and then deletes its last remaining record: `.calavera/state.json`, or in a project without one, the lock, or without a lock, the recipe. It adds the block only on a run that started from the recipe, the state, or the lock. The dry run and the list you approve show the block's exact lines, and the `--json` result carries them in a new `ejectedBlock` field with what the run did with it. A `--yes` run that leaves items for an interactive approval, or a run in which a removal fails, adds no block, and when the block cannot be written, or the run stops before that last deletion, `eject` keeps that record so the next run adds the block. A second `eject` keeps a complete block and reports nothing to do.

  When `eject --yes` keeps `.calavera/state.json` because the base skill or the `artifact-cache` block was edited, it now also keeps the `artifact-cache` block, as it already did for a linked cache. The project stays a consistent applied project, so `artifacts status --check-updates` has nothing to write back.

  `apply` removes a complete `ejected` block, because a project it writes into is managed again, and its dry run lists the removal. `init` and `--init` leave the block. An `ejected` block that holds other lines, or whose markers are unpaired or changed, stops both `eject` and `apply` before they write anything, with a remedy that names the block and quotes none of your lines.

- f39b74d: `artifacts status`, `artifacts doctor`, `doctor`, and the `artifact_status` MCP tool now print a note for each file of a selected artifact without a lock entry that already exists without a state record, which `apply` stops on unless the file matches the package. The note says whether the file matches the version in the project's artifact cache, compared offline against a temporary copy of the cache, and how to keep the file. Each artifact in the `--json` results gains `unrecordedFiles`, a list of `{ path, comparedVersion, matches, notCompared, reason }`, which is empty when no file needs the note; `notCompared` says why a file could not be compared, with the error code when there is one. The doctors still contact no registry and write nothing into the project, and a note never changes `ok` or the exit status.
- 87c8a51: `doctor` now warns about each JavaScript or TypeScript toolchain integration a recipe still selects in a project Vite+ manages, such as `oxlint`, `oxfmt`, `typescript`, `eslint`, or `prettier` from a recipe written before those integrations were removed. Each warning names the integration and the Vite+ detection signal that matched, and says to remove the integration from the recipe, because `apply` refuses the recipe until then. In a project Vite+ does not manage, `doctor` reports no such warning. These warnings stay advisory: `doctor` writes nothing, and a warning does not change its exit status (#431).
- ccf1ce9: `apply --config <path>` with a recipe saved outside the project, such as one downloaded from the Web Composer, now copies the recipe byte for byte into the project root as `calavera.config.json` and applies it, so later commands find it without `--config`. `apply --dry-run` lists the copy and writes nothing. The project root is the current directory, which must contain a `package.json`: without one, apply refuses and names the directory instead of offering to create `package.json`. When the project already has a different `calavera.config.json`, apply stops without writing anything. When apply asks for a value the recipe does not record, it writes the recipe with that value instead of an exact copy, and leaves the source unchanged. A `--config` path inside the project behaves as before (#603).
- 22cf9a6: The CLI now tells you when it is older than the version the npm `latest` dist-tag names, which happens when a package manager runs a copy it cached earlier (#675). After the command's own output, and after an error too, it prints a notice on standard error that names both versions and repeats your command pinned to `latest`; when Calavera is a project dependency, the notice also gives the command that updates it. The check asks the registry your npm configuration names, waits at most 1.5 seconds, writes no file, and prints nothing when it fails. It is skipped for `--json`, `--help`, `artifacts status` and `artifacts doctor` without `--check-updates`, and the MCP server. Set `CALAVERA_NO_VERSION_CHECK` to `1` or `true` to turn it off. Artifact-core adds `resolvePackageDistTag`, which resolves a dist-tag with the same registry settings as the artifact commands.
- 4eed3a0: The new `eject` command stops Calavera managing a project and keeps every tool it installed (#678, ADR-0017). It removes the state, the recipe, the artifact lock and package copies, the artifact cache and its `.gitignore` block, the bootstrap guidance, the MCP setup notes and the `calavera` MCP entry, a `.coderabbit.yaml` that Calavera created, and the base Calavera skill. `eject --dry-run` lists every deletion and edit, with the exact text each edit removes and the text the file holds afterward, and changes nothing. For an MCP harness file it shows only the lines around Calavera's entry, with values hidden, and `--json` leaves that file's text out, so other servers' tokens stay out of logs (ADR-0017, Amendment 3); it refuses while an artifact transaction is pending, which `eject` without `--dry-run` recovers first. An interactive `eject` shows the same list, marks each item as edited, unedited, or "edits cannot be detected", and removes nothing until the person approves the whole list. Without a terminal, or with `--json`, `eject` refuses unless `--yes` is given, and `--yes` removes only the items that match Calavera's records exactly and lists what it left. `eject` never writes `package.json`: it reports each script that runs Calavera and the `create-project-calavera` development dependency, with the command that removes it for the project's package manager, or `vp remove` under Vite+. It also reports footprint text it keeps, and a footprint elsewhere in the workspace. `--json` prints a structured result. The Calavera skill, and the copy `--init` installs, now tell the agent that `eject` is a CLI command the user runs in their own terminal, not an MCP tool. `clean`'s summary now starts a skip reason with "This item", capitalized, when the reason starts with the item's own path.
- 32d7e02: `artifacts status` and `artifacts doctor` now print each artifact with its locked version and channel instead of a single completion line. With `--check-updates`, each available update shows the installed and latest versions, a link to the release notes in the package's `CHANGELOG.md` on GitHub, and the command that applies it through the recipe's package manager, with `--tag next` for a `next`-channel artifact and `--config` for a recipe at another path. When an update is available and the recipe selects more than one artifact, with every locked one on one channel, status also prints the `--all` command. When every artifact is current, it says so. `--json` adds `releaseNotesUrl`, `updateCommand`, and `installCommand` to each artifact, and `updateAllCommand` and `checkUpdatesCommand` to the result. The link comes from the `repository` metadata of the published package, which `resolveArtifactPackage` in `@schalkneethling/calavera-artifact-core` now returns; without GitHub repository metadata, status still reports the update and its command (#398).
- 572d113: Setting the `CALAVERA_DEBUG` environment variable to `1` or `true` now adds the stack frames of each error in the chain to the CLI's error output and, as a `stack` field, to the MCP server's tool error results. The frames are redacted like the messages. Without the variable, the output is unchanged.

If the rollback itself fails, the error reports both failures, the project may be partly changed, and the next `apply`, `apply_recipe`, or `artifacts` command retries the rollback; a dry run refuses to run until it has. Registry cache entries can remain in an existing `.calavera/cache/npm`. Installing artifacts adds no dependencies to `package.json` and writes nothing to `node_modules`.
