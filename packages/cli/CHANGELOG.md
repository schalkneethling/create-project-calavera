# create-project-calavera

## 6.3.0

### Minor Changes

- 72a5e4c: Each entry of `autoInstalledArtifacts` in the `apply --json` result, and in the MCP `dry_run_apply` and `apply_recipe` results, now has a `filesAlreadyMatch` field (#1021). It is `true` when the files in the project already match the version apply locks, so apply writes none of that artifact's files. Apply still locks the version, stores the package under `.calavera/packages/`, and records the artifact in `.calavera/state.json`. The `dry_run_apply` tool now declares an output schema that describes the field. The apply summary reads the same field for its "its files in the project already match" line, so the summary and the JSON result agree. The lock file that apply writes does not change.
- 87c8a51: `doctor` now warns about each JavaScript or TypeScript toolchain integration a recipe still selects in a project Vite+ manages, such as `oxlint`, `oxfmt`, `typescript`, `eslint`, or `prettier` from a recipe written before those integrations were removed. Each warning names the integration and the Vite+ detection signal that matched, and says to remove the integration from the recipe, because `apply` refuses the recipe until then. In a project Vite+ does not manage, `doctor` reports no such warning. These warnings stay advisory: `doctor` writes nothing, and a warning does not change its exit status (#431).
- ccf1ce9: `apply --config <path>` with a recipe saved outside the project, such as one downloaded from the Web Composer, now copies the recipe byte for byte into the project root as `calavera.config.json` and applies it, so later commands find it without `--config`. `apply --dry-run` lists the copy and writes nothing. The project root is the current directory, which must contain a `package.json`: without one, apply refuses and names the directory instead of offering to create `package.json`. When the project already has a different `calavera.config.json`, apply stops without writing anything. When apply asks for a value the recipe does not record, it writes the recipe with that value instead of an exact copy, and leaves the source unchanged. A `--config` path inside the project behaves as before (#603).
- 22cf9a6: The CLI now tells you when it is older than the version the npm `latest` dist-tag names, which happens when a package manager runs a copy it cached earlier (#675). After the command's own output, and after an error too, it prints a notice on standard error that names both versions and repeats your command pinned to `latest`; when Calavera is a project dependency, the notice also gives the command that updates it. The check asks the registry your npm configuration names, waits at most 1.5 seconds, writes no file, and prints nothing when it fails. It is skipped for `--json`, `--help`, `artifacts status` and `artifacts doctor` without `--check-updates`, and the MCP server. Set `CALAVERA_NO_VERSION_CHECK` to `1` or `true` to turn it off. Artifact-core adds `resolvePackageDistTag`, which resolves a dist-tag with the same registry settings as the artifact commands.
- 4eed3a0: The new `eject` command stops Calavera managing a project and keeps every tool it installed (#678, ADR-0017). It removes the state, the recipe, the artifact lock and package copies, the artifact cache and its `.gitignore` block, the bootstrap guidance, the MCP setup notes and the `calavera` MCP entry, a `.coderabbit.yaml` that Calavera created, and the base Calavera skill. `eject --dry-run` lists every deletion and edit, with the exact text each edit removes and the text the file holds afterward, and changes nothing. For an MCP harness file it shows only the lines around Calavera's entry, with values hidden, and `--json` leaves that file's text out, so other servers' tokens stay out of logs (ADR-0017, Amendment 3); it refuses while an artifact transaction is pending, which `eject` without `--dry-run` recovers first. An interactive `eject` shows the same list, marks each item as edited, unedited, or "edits cannot be detected", and removes nothing until the person approves the whole list. Without a terminal, or with `--json`, `eject` refuses unless `--yes` is given, and `--yes` removes only the items that match Calavera's records exactly and lists what it left. `eject` never writes `package.json`: it reports each script that runs Calavera and the `create-project-calavera` development dependency, with the command that removes it for the project's package manager, or `vp remove` under Vite+. It also reports footprint text it keeps, and a footprint elsewhere in the workspace. `--json` prints a structured result. The Calavera skill, and the copy `--init` installs, now tell the agent that `eject` is a CLI command the user runs in their own terminal, not an MCP tool. `clean`'s summary now starts a skip reason with "This item", capitalized, when the reason starts with the item's own path.
- 32d7e02: `artifacts status` and `artifacts doctor` now print each artifact with its locked version and channel instead of a single completion line. With `--check-updates`, each available update shows the installed and latest versions, a link to the release notes in the package's `CHANGELOG.md` on GitHub, and the command that applies it through the recipe's package manager, with `--tag next` for a `next`-channel artifact and `--config` for a recipe at another path. When an update is available and the recipe selects more than one artifact, with every locked one on one channel, status also prints the `--all` command. When every artifact is current, it says so. `--json` adds `releaseNotesUrl`, `updateCommand`, and `installCommand` to each artifact, and `updateAllCommand` and `checkUpdatesCommand` to the result. The link comes from the `repository` metadata of the published package, which `resolveArtifactPackage` in `@schalkneethling/calavera-artifact-core` now returns; without GitHub repository metadata, status still reports the update and its command (#398).
- 572d113: Setting the `CALAVERA_DEBUG` environment variable to `1` or `true` now adds the stack frames of each error in the chain to the CLI's error output and, as a `stack` field, to the MCP server's tool error results. The frames are redacted like the messages. Without the variable, the output is unchanged.
- 1e2dba1: The catalogs now carry the display labels that the Composer shows. `@schalkneethling/calavera-artifact-core` exports `ARTIFACT_TARGET_LABELS`, which maps each artifact target ID to the tool's own name, such as `claude-code` to "Claude Code". In `create-project-calavera`, each integration from `list_integrations` and `describe_integration` has a `statusLabel`, such as "Recommended" or "Framework-specific", which the MCP output schema declares, and each artifact from `list_ai_artifacts`, and from the `aiArtifacts` of `explain_recipe`, has `targets`, a list of `{ id, label }` objects that is empty for skills. The `compose_recipe` input description now says that an artifact's `target` is one of those IDs, not a directory. Recipe output does not change (#580).
- c02b396: When the directory has no `package.json` of its own but a manifest above it was found, apply no longer creates `package.json` by itself. The dry run, and the MCP `dry_run_apply` tool, name the ancestor manifest and offer three choices in a new `manifestDecision` field, and plan nothing until one is made: `create-here` creates `package.json` in the directory and applies there, with the install command and the `quality` script following the ancestor's Vite+ verdict; `apply-at-ancestor` inspects the ancestor's directory again and applies there without changing the directory, and stops when that directory already has a Calavera recipe or state; `abandon` changes nothing. An apply in a terminal without `--yes` or `--json` asks once; any other apply reports the choices and stops before writing anything. Give the choice with the new `--manifest-choice` flag, which `apply`, `update`, and `init --apply` accept, or with the `manifestChoice` input of `dry_run_apply` and `apply_recipe`. `init --apply` in such a directory runs only with `--manifest-choice create-here`, because it writes the recipe there first. The MCP server now runs one tool call at a time, so a call made in parallel cannot run in another directory. Calavera never chooses for you (#430).
- 88636ce: `--new` now starts Vite+ through the package manager that launched Calavera when no `--package-manager` comes before `--new`. Outside an existing workspace, that package manager becomes the new project's package manager, so a pnpm user no longer gets an npm project by default. Calavera reads the package manager's name from `npm_config_user_agent`, as Vite+ does. npm, pnpm, Bun, and Yarn 2 or later choose their own runner. Calavera falls back to npm for Yarn 1, which has no `dlx` command, for an unset or empty value, and for any other launcher. A `--package-manager` before `--new` still chooses the runner, and Calavera still adds no `--package-manager` to the arguments it forwards. When a runner Calavera chose cannot start, the error says how it was chosen and how to choose another.
- b840ed2: A targeted `artifacts update <id>` no longer installs and locks the selections that have no lock entry. Before, it installed and locked each of them on the channel that its `--tag` named. It still advances only the artifact it names and keeps every other locked selection at its locked version. Selections without a lock entry now stay as they are until `artifacts install` or `artifacts update --all` installs them. When `artifacts status --check-updates` finds an update and the recipe has such selections, it says so after the update commands, in place of the list of selections that an update also installed, and `--json` no longer returns `updateAlsoInstalls`. Local edits still stop an update (#991).
- 6e79ac8: `artifacts install` and `artifacts update` still remove the lock entry of an artifact the recipe no longer selects, but they now name each such entry, as "Removed the lock entry for <id> <version> (<tag>)", or "Would remove" in a dry run, and say that its installed files stay in place. Before, they removed it without a word. `artifacts status` and `artifacts doctor` mark such an artifact as not selected and say that the next install or update removes its lock entry, or only the next install when the recipe selects no artifacts, because `artifacts update` then refuses to run. Without a recipe file, status makes no such claim. `--json` adds `selected` (true, false, or null without a recipe file) to each status artifact and `removedLockEntries` to the install and update result (#992).

### Patch Changes

- 252dbe1: `clean` no longer removes the base Calavera skill that `--init` installs in `.agents/skills/calavera` when the recipe does not select it. The base skill is Calavera's own artifact whatever the recipe selects, so `clean --dry-run` no longer lists it, and `clean` keeps it and its record in `.calavera/state.json`, whether `--init` or a recipe installed it. Only `eject` removes it. Every other artifact that a recipe selected and then dropped is still removed by `clean` when it is unedited (#1007).
- 9133a0c: When `--new` or `--init` leaves MCP to manual setup, or asks you to merge `AGENTS.calavera.md` into an existing `AGENTS.md`, the note that tells you what to do by hand now points to the file listed under "Changes" instead of naming `.agents/calavera/mcp.md` or `AGENTS.calavera.md` a second time. The same text appears in the `mcp.reason` and `pointers` fields of `--init --json` (#1020).
- 70c18a5: `init --apply` now prints its dry run with the same grouped summary as `apply --dry-run`, with Project, Integrations, Files, Scripts, Artifacts, and Notes headings, instead of its old one-line-per-field note. Around that summary, the recipe summary and the closing lines no longer repeat what the dry run names. With `--apply`, the recipe summary shows only the profile, and an input that took its default is listed under its own heading by its place in the recipe. The closing lines no longer repeat the profile, package manager, and integrations, and a pointer the dry run already printed is not printed again after the apply. When init has already written `calavera.config.json`, the dry run headline says so instead of saying that no files were changed.

  A dry run with `--no-install`, from `apply --dry-run --no-install` or `init --apply --no-install`, now says that the packages will not be installed and gives the command to install them later, instead of listing an install command that apply will not run. A real `apply --no-install` or `update --no-install` gives the same command after saying it did not install the packages. Its result, from `--json` or the `apply_recipe` tool with `noInstall`, carries that command in a new `laterInstallCommand` field, and `installCommand` stays `null`, because apply skipped the install. The field is absent from every other result, including dry runs, which keep the planned `installCommand`.

  `init` without `--apply` prints `Integrations: none` for a recipe without integrations, instead of an empty value (#1022).

- 4053dcf: A legacy artifact entry whose `type` or `src` has surrounding white space, such as `{ "type": "skill", "src": " skills/project-goal " }`, now selects the same artifact as the trimmed entry. Recipe validation already trimmed both fields, but the artifact selections that apply, `artifacts install`, `artifacts update`, `artifacts status`, and the apply summary build did not trim the `src`, and neither did `artifacts migrate` or the `aiArtifacts` list of the MCP `explain_recipe` tool. As a result, apply stopped with "Unknown artifact selection." without naming the entry (#1024).
- 4597337: `update --config <path>` with a recipe saved outside the project now copies the recipe byte for byte into the project root as `calavera.config.json` before it applies it, as `apply --config` does since #603. `update --dry-run` lists the copy and writes nothing. The same checks apply: the current directory must contain a `package.json`, a different `calavera.config.json` already in the project stops `update` before it writes anything, and a link or a directory at `calavera.config.json` is refused. The refusals name `update` (#1025).
- 2c7461a: On macOS and Linux, the commands Calavera prints for you to paste, such as the install command, the command that removes a dev dependency, and the version notice's update command, now quote an argument that starts with `=` or holds `==` or `:=`, as the other printed commands have since #1037, so zsh pastes them unchanged. Windows keeps its own quoting. Calavera now uses one rule for whether a path lies inside a folder (#1026).
- e94faed: The `compose_recipe` input description for `integrationOptions` now names the Stylelint Baseline field `available` instead of `availability`, so an agent that follows it no longer gets an "Unknown integrationOptions.stylelint-baseline fields" error. The MCP server and the Composer's WebMCP tool share this description (#1027).
- f2be602: The `--new` confirmation now says which package manager Vite+ uses inside an existing project whose `package.json` has no `packageManager` or `devEngines.packageManager` field and whose folder has no lockfile or package-manager configuration file that Vite+ reads: Vite+ detects none there and uses the runner's package manager, the same one it uses outside a project. Runs of Vite+ 1.6.0 and 1.7.0 confirmed that this case does not fall back to pnpm when a package manager launched Vite+.
- 5449632: `doctor` now exits with status 1 when it reports an error, such as a missing `calavera.config.json`, in both text and `--json` output, so a CI step that runs `doctor` fails instead of passing. When `doctor` reports only warnings, or no issues, it still exits 0 (#1030).
- f8a0cd6: `doctor` run from a workspace member now reports an error when the recipe selects an artifact that writes Git hooks, such as `skill-protected-branch-guard`. The error is the message `apply` stops with in a member that has its own `package.json`, so it names the artifact, the repository root, and the remedy: apply that recipe from the repository root, or remove the artifact from this recipe. When the recipe also selects an integration that applies only at the repository root, `doctor` reports both refusals, although `apply` stops at the first (#1031).
- 14537c2: The structured error that an MCP tool returns keeps the `code` and name of a cause whose message the wrapping error repeats. Before, without `CALAVERA_DEBUG`, such a cause was left out entirely, so a wrapped `EBUSY` and a wrapped `ENOENT` with the same wrapper message looked the same. The cause now appears with an empty message, so the message is still shown once. The printed error text is unchanged (#1032).
- a998558: When Calavera cannot remove one of its temporary folders after apply has written the AI outputs, apply now finishes instead of stopping before the config, the `package.json` scripts, and the state are written. The summary names each folder left behind under Notes with the error code and asks you to remove it. The `--json` result and the MCP `dry_run_apply` and `apply_recipe` tools carry the folders in the new `temporaryFolderLeftovers` field, and the dry run reports the same failure the same way. Apply still exits non-zero when a later step fails, such as a file write or the dependency install, and that error names the folders too. A folder inside the project, such as one under `.calavera/.transactions/`, is reported with a note that Git does not ignore it. Messages about a failed removal now name the temporary folder and the error code instead of repeating the underlying error's message. The base Calavera skill now asks agents to show each entry in `temporaryFolderLeftovers` as a warning with its remedy, after the dry run and after apply (#1033).
- 65a9577: Apply now removes a `.calavera/.staging/<id>` folder that 6.2.1 or an earlier release left after restoring a locked artifact package, but only when the folder holds exactly the package the lock records for `<id>`. Apply rebuilds that package from the artifact cache to compare them. Every other entry in `.calavera/.staging/`, such as an edited folder, a folder no lock entry names, or a symbolic link, is kept and reported with the reason. `apply --dry-run` and `apply` list each entry under Files, and the `--json` result and the MCP `dry_run_apply` and `apply_recipe` tools carry it in the new `stagingLeftovers` field. Apply checks each folder again just before it removes it. A folder it cannot read or remove is reported without stopping apply. The base Calavera skill now asks agents to show `stagingLeftovers` with the rest of the dry run (#1034).
- 3674ff7: Commands that Calavera prints for people to paste now quote a token that starts with `~` or `=`, or that holds `~`, `^`, `==`, or `:=`, so zsh and bash run them as printed instead of expanding the token to a home directory, a command path, or a glob pattern (#1037).
- 9010745: When `apply --manifest-choice apply-at-ancestor` stops because the ancestor's directory holds only `.calavera/state.json`, the message now names the state file, says that Calavera has already recorded state there, and suggests running apply there with a recipe for that directory, instead of claiming that the directory has a Calavera recipe of its own. The bootstrap that `--init` runs writes that state file without a recipe. Apply still stops before writing anything (#1038).
- 1635fb0: Interactive `--init` (`agent-init`) now asks how to add guidance to an existing `AGENTS.md` and which agent harness to configure before it writes any file. Cancelling at either prompt now leaves the project unchanged. Before, the Calavera skill and `.coderabbit.yaml` were already copied, and `AGENTS.md` already changed, when the harness prompt appeared, so a cancel left them in place with no record in `.calavera/state.json` (#1039).
- 15eb705: `--init` and `apply` now add Calavera's path filters to an existing `.coderabbit.yaml` whose `reviews` mapping has no `path_filters` list, whose `reviews` mapping is empty (`reviews: {}`), or which has no `reviews` key, instead of stopping with "reviews.path_filters must be an array" or "Expected YAML collection at reviews". The filters are written as a YAML list, and your other keys and comments are kept. An empty `reviews: {}` becomes a block mapping, so a comment at the end of the `reviews:` line moves below the new list. A `reviews` flow mapping that already holds keys keeps its flow style.

  Apply stops with an error, and changes nothing, when adding the filters would change what the file means elsewhere. That happens when `reviews` has no `path_filters` but uses a `<<` merge key, written as a bare `<<`, as `!!merge <<`, or as `? !!merge`, because a new list would replace the merged one, and when `reviews` or its `path_filters` list carries an anchor, because the aliases would gain the filters too; that error names the filters to add by hand (#1068).

- 5c51e17: `doctor` now accepts a legacy artifact entry, such as `{ "type": "skill", "src": "skills/project-goal" }`, that apply installed. Previously, `doctor` looked for the legacy source path in the project, which no project holds because apply installs the artifact's package, and stopped with "AI item at index 0 references missing skill source: skills/project-goal.", so it exited 1 on a project that apply had set up correctly. `doctor` also treats the wiring that apply recorded for an artifact selected by a legacy entry as selected, instead of reporting that the recipe no longer selects it. An entry whose source no catalog artifact provides still makes `doctor` exit 1 (#1101).
- c5b8930: `--new` now makes Vite+ use the package manager that Calavera's runner and confirmation name. Calavera removes `npm_config_user_agent` from the environment it gives `vp create`, so each runner sets its own value. Before, `npm create` and `bunx` passed on the value of the package manager that started Calavera, and Vite+ chose that package manager instead. This happened when Calavera fell back to npm, under Yarn 1 or an unrecognized launcher, and when `--package-manager npm` or `bun` before `--new` named another package manager than the one that started Calavera. Every other environment variable still passes through unchanged, except `npm_config_package` and `npm_config_call`, which Calavera already removed.
- 72fa3c2: `clean` now keeps the wiring of an artifact that a legacy recipe entry, such as `{ "type": "skill", "src": "skills/protected-branch-guard" }`, still selects. Previously, `clean` compared the legacy path with the catalog ID under which apply records wiring for an entry that names an ID, so after the recipe switched to the legacy entry, `clean` treated the artifact as no longer selected: it planned to remove the artifact's blocks from `.vite-hooks` and its groups from `.claude/settings.json`, and dropped its `aiWiring` record from `.calavera/state.json`. `clean` still removes the wiring of an artifact the recipe no longer selects (#1119).
- b36c246: `apply`, `update`, their dry runs, and the MCP `dry_run_apply` and `apply_recipe` tools now refuse, before writing anything, a legacy AI entry that selects an artifact that needs wiring or inputs, such as `{ "type": "skill", "src": "skills/protected-branch-guard" }`. The error names the entry and tells you to run `artifacts migrate`, which rewrites legacy entries as ID entries. Before, `apply` never wired the artifact such an entry selects, and when a recipe switched from the ID entry to the legacy entry, `apply` removed the artifact's `.vite-hooks` and `.claude/settings.json` wiring and its record. A legacy entry for an artifact with no wiring or inputs still applies as before (#1125).
- b256847: `clean --dry-run` and `clean` now group what they report under the headings "Wiring", "Files", and "Artifacts", and list each file and artifact once. Each wiring file is one line, with the hook blocks and settings groups clean removes from it listed under that line. A skipped item is listed on its own line with its reason, where "this item" stands for its own path, so the summary no longer repeats it in a separate "Kept …" sentence. A reason still names any other file it refers to, such as a hook that still runs a kept skill. The `--json` result keeps its shape and its `message` text, with one addition: when clean keeps every stale item, a kept artifact's entry in `changes` now carries `category`, `aiType`, and `name`, as it already did when clean also removes something (#331).
- 6e232db: The Calavera skill now tells the agent to look for all 14 MCP tools the server registers, including `describe_integration` and the four Baseline tools, `list_baseline_targets`, `describe_baseline_target`, `search_baseline_features`, and `recommend_baseline_target`. The copy that `--init` installs changes the same way, and a test fails when either copy or the README's tool-order list differs from the registered tools (#933).
- 4b567b3: A second run of `--init` or `apply` now names every AI artifact output and `.coderabbit.yaml` that is already up to date, instead of leaving them out (#956).

  - The bootstrap summary that `--init` and `--new` print lists them under "Changes" as skipped, for example `Skipped .agents/skills/calavera: Already up to date.` The `changes` field of `--init --json` and the `bootstrap.changes` field of `--new --json` carry them with `type: "skip"`.
  - The `apply` summary lists `.coderabbit.yaml` under "Files" as `Unchanged .coderabbit.yaml`, and each artifact under "Artifacts" as `Unchanged <id> at <path>`, or `Unchanged <id>:` followed by its outputs. A lock that leaves the files as they are now names them too: `Would lock <id> <version>; its files in the project already match: <path>`, or a trailing colon followed by the outputs. The `changes` field of `apply --json` and of the MCP `dry_run_apply` and `apply_recipe` results carries them with `type: "unchanged"`.
  - The `changes` field of `artifacts install --json` and `artifacts update --json` now also holds an entry with `type: "unchanged"` for each output that already matches and for an up-to-date `.coderabbit.yaml`. Read `type`, not whether `changes` is empty, to tell what was written.
  - An updated `.coderabbit.yaml` in the bootstrap summary no longer ends with ": undefined".

- 6c71ed1: The summary that `--new` and `--init` print now lists `.calavera/state.json` once under "Changes" when the bootstrap writes or updates it, and leaves it out when it is already up to date. The `changes` field of `--init --json` and the `bootstrap.changes` field of `--new --json` carry the same entry (#957).
- a198f9e: When the MCP server fails to start, it now prints the error and each cause under it, redacted, in the same format as the CLI, instead of only the stack of the top-level error. The stack frames of each error are printed only when the `CALAVERA_DEBUG` environment variable is set to `1` or `true` (#959).
- 8f90b51: `artifacts install`, `artifacts update`, and `artifacts status --check-updates` now keep `.calavera/cache/` out of Git themselves. Before they resolve any package into the cache, they write the marked `artifact-cache` block in `.gitignore` and record it in `.calavera/state.json`, as `apply` does, and say why the cache is ignored. `artifacts doctor --check-updates` does the same. Their dry runs list the block and write nothing, and `artifacts status --check-updates --dry-run` no longer fills the project's cache. A block the person edited stops the command before it writes anything (#960).

  `apply` now decides that it ran before from the profile recorded in `.calavera/state.json`, not from the file's existence. `artifacts install`, `artifacts update`, `artifacts status --check-updates`, and the bootstrap also write that file, so before this change the first apply after one of them could rename a `lint` or `lint:fix` script the person wrote (ADR-0013, Decision 6). A state file from an earlier release that apply wrote keeps its renames. Messages about a broken Calavera marker in `.gitignore` now name the command to run again.

- d365ca6: With `--manifest-choice create-here`, the formatter now follows the parent's Vite+ verdict, as the install command and the `quality` script already do. When the manifest above the directory is managed by Vite+, `apply` formats the files it generates with `vp fmt`, and `init --apply` formats the recipe it writes the same way. When the parent is not managed by Vite+, Calavera writes them unformatted, as before. The `package.json` that the package manager's `init` command creates is not formatted (#961).
- 52c007f: The Calavera skill now tells the agent what to do when `dry_run_apply` returns `manifestDecision`: show the user the ancestor manifest and the three choices, `create-here`, `apply-at-ancestor`, and `abandon`, never pick one, and pass the user's choice as `manifestChoice` to `dry_run_apply` and then `apply_recipe`. - c7507ee: The Calavera skill now tells the agent when to use the four Baseline tools: when the recipe selects `stylelint-baseline`, ask the user for a Baseline target, show the targets from `list_baseline_targets` or `describe_baseline_target`, turn the CSS features the user needs into a target with `search_baseline_features` and `recommend_baseline_target`, and record a target other than the default `widely` in `integrationOptions.stylelint-baseline.available`. - d109a43: When a recipe sets `scripts.quality` to `false`, apply still leaves the `quality` script alone, and now also keeps the `qualityScript` record in `.calavera/state.json` when that record holds the project's current value. Before, apply overwrote the record with `null`, so no later apply could remove a `quality` value that Calavera wrote. Now, when the recipe turns `quality` back on and the plan omits it, apply removes that value (#968).
- cfa45d8: `agent-init` now formats `.calavera/state.json` before it copies the Calavera skill files. When the project's formatter cannot format the state, `agent-init` stops with nothing written, instead of leaving the skill files and `.coderabbit.yaml` in the project with no state record.
- e6b7b1f: `artifacts migrate` now writes `calavera.config.json` through the project's formatter, as `apply` writes it, so the Vite+ pre-commit hook no longer rewrites the migrated recipe. A dry run formats the recipe too, so a formatter that cannot format it stops the dry run and the migration before either writes anything (#987).
- 7bebfa0: The `--init` prompts now show the catalog's display labels instead of raw IDs. Each integration's hint shows its status label, such as "Framework-specific" instead of `framework-specific`. - 3679738: Remove the Oxlint integration and its fourteen plugin pack entries (`oxlint`, `oxlint-eslint`, `oxlint-typescript`, `oxlint-unicorn`, `oxlint-oxc`, `oxlint-import`, `oxlint-react`, `oxlint-jsx-a11y`, `oxlint-node`, `oxlint-promise`, `oxlint-vitest`, `oxlint-jest`, `oxlint-nextjs`, `oxlint-vue`, `oxlint-jsdoc`). Calavera no longer writes `oxlint.json` or adds `oxlint` to the `lint` and `lint:fix` scripts; on a Vite+ project, `vp lint` and `vp check` provide JavaScript and TypeScript linting. A `calavera.config.json` that names any removed id now fails validation as an unknown id: remove the ids and rely on `vp lint`. The Calavera skill no longer lists `oxlint.json` among the files to inspect. See [ADR-0002](../docs/adr/0002-remove-oxlint.md) and the catalog audit for the evidence.
- 12d4226: Remove the Oxfmt integration (`oxfmt`). Calavera no longer adds `format` and `format:check` scripts that run Oxfmt and no longer rejects a recipe for selecting both Oxfmt and Prettier, since only Prettier remains until its own removal; on a Vite+ project, `vp fmt` and `vp check` provide formatting. A `calavera.config.json` that names `oxfmt` now fails validation as an unknown id: on a Vite+ project, remove the id and rely on `vp fmt` and `vp check`; a project that has not adopted Vite+ and uses the Classic profile keeps Prettier until CAL-016 removes it. Once CAL-016 lands, Calavera provides no formatter to any project, and a project without Vite+ runs `vp create` or `vp migrate` first. The Calavera skill no longer describes Oxfmt as an option. See [ADR-0003](../docs/adr/0003-remove-oxfmt.md) and the catalog audit for the evidence.
- 4ae0d07: Remove the TypeScript configuration integration (`typescript`). Calavera no longer writes `tsconfig.json`, no longer installs `typescript` and `@types/node` for that entry, and no longer adds a `typecheck` script; the recipe's `scripts.typecheck` option is removed from the configuration schema because it had no other subject. On a Vite+ project, `vp create` writes `tsconfig.json` and `vp check` type-checks through tsgolint. A `calavera.config.json` that names `typescript` now fails validation as an unknown id; one that still sets `scripts.typecheck` validates but the flag is ignored and no `typecheck` script is generated. Remove both and rely on `vp check`. Entries that depend on the TypeScript package, such as `typescript-eslint` until its own removal, keep installing it themselves. The Calavera skill no longer lists `tsconfig.json` among the files to inspect. See [ADR-0004](../docs/adr/0004-remove-typescript-configuration.md) and the catalog audit for the evidence.
- aa1545c: Remove the JavaScript and TypeScript ESLint flat config integration (`eslint`) and the eleven entries that include it (`typescript-eslint`, `eslint-config-prettier`, `eslint-react`, `eslint-jsx-a11y`, `eslint-import`, `eslint-n`, `eslint-promise`, `eslint-unicorn`, `eslint-sonarjs`, `eslint-vitest`, `eslint-jest`). Calavera no longer writes `eslint.config.js` or adds `eslint` to the `lint` and `lint:fix` scripts; on a Vite+ project, `vp lint` and `vp check` provide JavaScript and TypeScript linting. Nine of the removed plugin entries (`eslint-react`, `eslint-jsx-a11y`, `eslint-import`, `eslint-n`, `eslint-promise`, `eslint-unicorn`, `eslint-sonarjs`, `eslint-vitest`, `eslint-jest`) installed a dependency but never entered the generated configuration; projects that selected them can remove that dependency. A `calavera.config.json` that names any removed id now fails validation as an unknown id. This removal is the JavaScript ESLint host only; the CSS lint host css-evolve needs (`@eslint/css`) is unaffected. See [ADR-0005](../docs/adr/0005-remove-eslint-flat-config.md) and the catalog audit for the evidence.
- 4264b1c: Remove the Prettier integration (`prettier`) and the entries that include it (`prettier-tailwind`, `prettier-svelte`, `prettier-astro`). Calavera no longer writes `.prettierrc.json` or `.prettierignore` and no longer adds `format` or `format:check` scripts for any project; the recipe's `scripts.format` and `scripts.format:check` options are removed from the configuration schema because no integration can satisfy them, and a recipe that still sets them validates but produces no script; on a Vite+ project, `vp fmt` and `vp check` provide formatting. A `calavera.config.json` that names any removed id now fails validation as an unknown id: remove the ids and rely on `vp fmt`. With this change the Modern and Classic profiles have identical defaults; their collapse is decided separately. See [ADR-0006](../docs/adr/0006-remove-prettier.md) and the catalog audit for the evidence.
